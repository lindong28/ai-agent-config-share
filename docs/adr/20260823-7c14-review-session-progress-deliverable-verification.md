# ADR 20260823-7c14: `/custom:review-session-progress` 增加 opt-in 交付物验证模式，其**未启用状态**由取证脚注恒出一格承载

- 状态：accepted（2026-08-23）；decision-review **两轮完整 gate**。v1：blocker 判据 7 + 应修 3/4/5/6 + 无法判断 2；用户裁决改变决定（加脚注恒出格）后按契约重走完整 gate。v2：**同样** blocker 判据 7 + 应修 3/4/5/6 + 无法判断 2。应修四条已全部吸收；**判据 7 与判据 2 由用户显式 waive**（见 §Waive），据此放行
- Component：`claude/commands/custom/review-session-progress.md`（**只此一个文件**）
- 关系：验收方法**归** `claude/references/evidence-sufficiency.md`「完成断言的观察通道由交付物的消费者决定」那一条所有，本 ADR 与命令**均不复述**、只给指针；与 `docs/issues/harness-issues.md` 的 `HARNESS-20260823-8a91`（现场读数无回流通道）**语义分工 + 输出合流**：本决策负责**取得**读数，8a91 负责**回流**

## 背景

`/custom:review-session-progress` 的证据面被定义为 transcript + 台账 + 评审轮，**没有任何一槽指向被审 session 的产品**。2026-08-23 实测代价：**连续 5 次**用该命令分析 session `53e93100`（次数实测，非估计：按 `<command-name>/custom:review-session-progress</command-name>` 数 session `12b3104d` 的 transcript），全部未发现其已部署交付物的两个功能缺陷（服务不看图、不会说话）——缺陷由同事实际使用时报出。

关键在于**规则早已存在**：消费者通道那条是 BINDING（`CLAUDE.md`「观察面要匹配断言的确切对象」，带 0/6→4/4、Fisher p=0.005 的对照读数）。缺的不是规则，是**本命令从不产生一个「关于交付物」的断言**，于是那条规则的触发条件永不成立。分诊者甚至在报告里引用过被审方「12/12」当质量证据（而那 12 次同一张图、均无对白，在两个缺陷维度上方差为零），也报过长度差却归因成文风。

## 决策

1. 增加 opt-in 模式，触发形态为**显式 flag `--verify-deliverable`**。不给 flag 时分析行为逐字不变。
   - 选 flag 而非自然语言关键词：`CLAUDE.md`「模式匹配只用于有 spec 的对象」禁止把自由文本的「关注点」拿去正则分类，但明确允许"被指令要求原样输出的 token"。仓内两种先例均有（`--long-task`、「给我 N 份方案」）。
2. **取证脚注新增一格，无条件出现**，四态字节可分：已跑读数 / `未启用(可加 --verify-deliverable)` / `n/a(本模式未覆盖：<类型>)` / `未核实(<安全属性哪一条不满足>)`。
   - 这一格沿用本命令脚注的既有契约（`harness-issues.md` 里 `grep "每格填值、不填对勾"` 那一条——`fork ✓` 这类恒真标记在跑过与没跑过时字节相同）。**不写行号**：该文件正被并发写入，本轮起草时引的两个行号在写完到复核之间就已各自指向别处。
3. 三项证据**地位不等**（v1 把它们并列，是判据 3 判不成立的直接原因）：
   - **E1 消费者通道读数 = 唯一验收证据**；方法不在本命令定义，只给指针。且**单次正常样本不算数**。
   - **E2 声明 vs 实现边界对账**、**E3 验收样本维度方差** = **覆盖缺口信号，明写不可当作「缺陷不存在」的证据**（无缺陷系统用单一样本同样零方差；两份自陈文本也可以一致地错）。三者**不得聚合成一个绿灯**。
4. **E1 的读数只覆盖它实际跑过的样本与明确写出的条件**，不得据此写「交付物通过」（v2 判据 3：两个取值可能仍落在同一等价类 / 格式 / 边界侧）。
5. 安全属性四条（幂等 / 不花钱 / 不改业务状态 / 不占配额）**各自要有肯定依据**；**判不准即 fail-closed**：不调用，脚注写 `未核实`。「不改状态」明确指**业务状态**；目标侧日志、缓存、惰性初始化属**已知副作用面**，须在报告里点名。
6. 与命令既有只读边界「不替它跑评审或测试」的关系**显式写明**（v2 判据 5 指出的直接冲突）：本模式做的是**消费者侧的使用**，不是代目标 session 跑它自己的评审或测试套件；后者仍禁止。
7. 输出不新增槽位、不renumber：E1 读数作为 §4「顺不顺」的证据之一；可转交读数块并入 §6（其出现条件由「§5 非空」放宽为「§5 非空**或**本次启用了本模式」），与 8a91 合流。

## 作用域

- **已实测**：一个 HTTP 服务形态的交付物，一次。
- **实验性、逐实例未核实**：可调用 CLI（v2 判据 6：无输入的 CLI 无法满足"两个不同输入取值"）。
- **本模式未覆盖**：库、文档、数据集、模型权重。脚注写 `n/a(本模式未覆盖：<类型>)`——**不写"非可调用"**，那个术语与真实消费者模型不一致（v2 判据 6）。
- 不改既有消费者通道规则；不建探针程序；不改本命令只读边界主条款。
- 不覆盖：如何**修**发现的缺陷（归目标 session）。

## Waive（用户显式裁决，2026-08-23）

**判据 7（blocker，连续两轮）**：脚注恒出一格**只在执行者遵守输出契约时**消解同形性；无独立观察者检查该格是否存在，缺整格时「执行者漏填」与「功能根本不存在」对用户仍同形。这是「机械可解析」而非「机械核验」。

用户选择 waive 并本轮落地，理由：① **command 正文是被整段注入 context 的**（不同于 reference 须主动打开），故判据 2 援引的反例 `HARNESS-20260823-b1e4`（reference 文件名出现 107 次、正文打开 0 次）对本场合只成立一半，残余风险是"读到了没照做"而非"读不到"；② 新格与既有脚注同级、同样靠契约而非程序，不引入新一类风险；③ 成本为零且今天即可用。**代价照写：漏填仍无人拦。**

**判据 2（无法判断）**：无法在实现前证明未来 session 真会执行 E1–E3。部分答案（脚注格机械可核 ⇒ 未执行不再无痕）被评审判为不足——填了格子 ≠ E1 做得对。一并 waive。

被否决的备选（两轮共四条）：默认全开（与"用户可选"相抵、把只读命令变成有副作用、高频轻量场景变重）· 独立新命令（「顺不顺」本就要它作证据，拆开两份报告各自不完整）· 只加 prose 提醒（无脚注格则"跑了"与"没跑"字节相同，正是本文件通篇要防的形态）· 跑目标 session 的测试套件（executor 侧读数，与消费者通道同形失败；且违反只读边界）。

blocker 未消解这件事**另记 harness issue**，不当它不存在；候选修法（Stop hook 校验脚注格是否齐全）作用域超出"只改一个 command"，需另走 gate。机制已存在**两处，均实测可达**：本命令 frontmatter 的 `analysis-target: third-party` 已被 stop-gate 读取（该 frontmatter 自身的注释即其契约）；`harness-issues.md` 里 `grep "activeCommandName"` 那条记着按活跃命令名探测的实现与其 4 MB 窗口上限。

## 已知未验证项

1. 本模式只在一个可调用 HTTP 服务上实测过一次；CLI 子类未实测。
2. 未实测耗时代价（上次实调约 6 分钟，含两次 schema 试错与一次超时重跑）。
3. E3 的"输入维度"在被审 session 未公开其验收样本时不可得，只能写未核实；发生率无读数。
4. 判据 2 全项（见 §Waive）。
5. **本决策自身缺一个对照读数**——没有「加了这个模式后新 session 是否真会发现同类缺陷」的前后对照，不同于 `CLAUDE.md` 那条消费者通道规则有 0/6→4/4。
