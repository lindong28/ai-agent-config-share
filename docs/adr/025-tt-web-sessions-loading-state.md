# ADR-025: Sessions 冷加载保留实时解析，并把等待与失败显式呈现在表格内

- 状态：accepted（2026-08-19）
- 决策评审：独立 reviewer 首轮要求补齐升级条件、回退边界与状态转换测试；窄复核确认闭合后放行
- Component：`tt-web/web/sessions.html`、`tt-web/web/app.js`

## 背景

用户打开 `/sessions?range=30d` 时看见空的 Session details 表格。受影响的真实服务在同一时刻能从 `/api/sessions?range=30d` 返回 2577 条记录，但进程冷启动后的首轮请求需要扫描仍存在的原始 Claude Code 与 Codex session 日志，本轮实测约 30 秒。浏览器在等待期间多次离开页面还会让服务端记录 `BrokenPipeError`；缓存变热后，相同页面能正常显示 100 条首屏记录与 2577 条总数。

现有页面在请求结束前不渲染任何表格状态：初始 `<tbody>` 为空，`initSessions()` 等待接口成功后才调用 `renderSessions()`。因此加载中、请求失败和真正没有 session 三种状态在读者面前同形。既有 ux-contract A3/A5 已要求页面正常渲染、错误和真实空数据可见；加载状态由本 ADR 补充决定。

## 备选

| 方案 | 收益 | 代价与边界 |
|---|---|---|
| A. 前端显式呈现加载、失败重试和真实空数据状态；保留实时解析路径 | 直接消除用户看到的假空表格，不改变数据身份、保留期或刷新语义 | 冷启动的实际等待时间不缩短 |
| B. 为 sessions 增加持久缓存或改读聚合 rollup | 可缩短冷启动等待 | 改变 freshness、失效、删除、兼容与隐私边界；rollup 也不具备 session drilldown 所需的原始身份 |
| C. 只提高接口或浏览器超时 | 可能减少超时失败 | 等待期间仍是空表格，且本轮没有证据表明接口本身超时 |

## 决策

采用方案 A。页面首屏和每次 reload 都先在 Session details 表格内显示 `Loading sessions…`，并禁用分页与行筛选；成功且有数据时替换为 session rows，成功但没有数据时显示明确的空状态；请求失败或 payload 不是预期的 session row 数组时在同一表格内显示错误与 `Retry`，重试仍走同一个 `/api/sessions` 入口。重叠 reload 只允许最新一代请求提交结果，较早请求的迟到成功或失败不得覆盖更新后的表格状态。

本次不引入 sessions 持久缓存、不改读聚合 rollup，也不自行设定新的冷启动延迟目标。只有用户以后给出明确的冷启动时延要求，或实测冷路径发生 API 失败/超时，才重新评审持久化方案；单独观察到约 30 秒等待不构成扩大数据层改动的授权。

## 成功与回退

可观察成功标准是：冷页面立即出现加载状态；同一 API 返回 200 后加载状态被 rows 或明确空状态替换；接口失败或 payload 非法时显示表格内错误和 Retry；Retry 后接口成功可恢复到 rows；旧请求在新请求完成后才返回时不改变新结果。服务端回归测试继续钉住 sessions 使用 live raw entries，而不是 rollup。

本方案回退只需撤销前端状态渲染，服务端与数据不需要迁移。若未来选择持久缓存，必须重新评审 session 身份与 drilldown、失效与 freshness、schema/兼容/删除回退和隐私；原始解析器仍须保留为事实源，缓存必须能无损禁用。

## 已知未验证

- 本次未承诺也未测量可接受的冷启动时延上限；约 30 秒只是当前机器的一次实测，不是产品目标。
- 尚未证明不同日志规模、磁盘或机器上的冷加载耗时相同。
- 浏览器离开页面导致的 `BrokenPipeError` 不是本次处置对象；它不解释仍停留页面上的假空表格。
