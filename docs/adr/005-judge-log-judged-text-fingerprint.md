# ADR-005：judge-gate 日志记录被判文本的 SHA-256 指纹（仍不记原文）

- 状态：已采纳（2026-08-10），**尚未实施**
- 决策评审：`decision-review` gate，一轮全审（0 blocker + 6 应修）→ 两轮复核 → **放行**
- 影响面：`claude/hooks/lib/judge-log.js` 与写 `judge-gate.jsonl` 的 6 道判官闸

## 决策

在 `judge-gate.jsonl` 的记录里新增字段 **`judged_text_sha256`**：被判文本的完整 SHA-256 hex。**保留「不记被判原文」纪律不变。**

字段口径（各闸送审的对象不同，逐闸定义）：

| 闸 | 被判文本 |
|---|---|
| `ask-recommend-gate` | `JSON.stringify(tool_input)`（PreToolUse 闸，没有 `lastMsg`） |
| `stop-gate` / `prose-choice-gate` / `capability-claim-gate` / `continuation-claim-gate` / `reverse-assertion-gate` | 各闸实际交给判官的那段 `lastMsg` |

- hash 的是**被判对象**，不是 `callJudge` 收到的完整 prompt——故字段名不叫 `input_sha256`，那会让读者以为它覆盖整个判官输入。
- UTF-8 字节，**不做 trim / 规范化**。
- 实现形态：`logVerdict` 增加可选第 5 参；**不传即不写该字段**。判官前早退、确定性兜底（未闭合工具调用 / 声明不需回应）等路径本就没有被判文本，不写。

**存在性语义**：该字段表示「`callJudge` 被调用时的被判对象指纹」，**不表示「判官真的作答了」**——当前 `judge_unavailable` 合流了「后端无响应」与「判官返回协议外文本」两种情形，那个区分做不出来。

## 目的（已按评审收窄）

**在原文仍可取得时，定位并校验实际送审文本的同一性；为 eval 场景收割提供稳定指纹。**

**明确不承诺**：它不实现"历史裁决重放"。`capability-claim-gate` 的裁决还依赖整份转录里的工具调用集合、`continuation-claim-gate` 还依赖当时的运行态——相同文本在这些状态不同时可得不同裁决。它也不能恢复已被清理的原文。

## 为什么

现状是**有 verdict、没有输入标识**。字段集为 `ts / gate / event / session_id / transcript_path / agent_* / verdict / backend / model / reason`，没有任何东西指向"判的是哪一条消息"；`ts` 是 hook 触发时间，而 `stop-gate.js` 头注释记着一次实测——落盘与触发相隔 1.27s，判官读到的是上一条。

实际后果（2026-08-10 该 session 内三次撞上）：从真实开火收割 eval 场景时只能靠特征串在转录里 grep，**且实际取错过一次**；1000 余条历史 flag 无法用于回归；判官漂移无基线可比，而这道闸的失效是静默的。

## 为什么不删掉「不记原文」纪律

它有两条真实理由，删掉会一起丢：

1. **日志是会被粘贴出去的 artifact，转录不是。** 按"每字节被外传的概率"算，两者差几个数量级。
2. **日志 append-only，生命周期长于转录。** 转录确实会被清理（实测有已失效的路径记录），把原文写进日志＝让密钥活得比转录还久。

同时承认它的边际收益有限：对 key/签名样式做存在性计数（只输出计数、不回显值），`judge-gate.jsonl` 命中 0，而同信任域内 1054 个转录、3.4 GB、同为 0600，仅前 60 个文件就命中 15。且每次判官调用本就把被判文本发给 GLM（第三方 API）——纪律禁的是最安全的处置，最危险的处置在它视野之外。**结论是"纪律留着、但缺的字段要补"，不是"纪律该删"。**

## 已知代价与未验证项

- **确定性无密钥 hash 对低熵文本可被"候选确认"**（拿候选原文算 hash 比对）。判为可接受：被判文本是自由散文、熵高。注意 `0600` 只覆盖本机静态存储，**不覆盖日志被粘贴出去之后**的候选确认——这一点显式接受，不是未处理项。
- **覆盖不均匀**：部分闸只依赖文本，另一些还依赖转录或运行态；`permission-gate` 调 `callJudge` 但不写这份日志，不在本决策范围内，另案。
- **定位能力对 subagent 记录有约 10% 覆盖不到**：`agent_transcript_path` 实测 35/352 失效（9.9%，涉 9 个 session）；主 `transcript_path` 失效 0。（作者最初报"恢复失败 0%"，用的是"两个路径字段任一还在"这个 OR 谓词，掩盖了 subagent 记录必须靠 agent 转录这一点——主转录不含其内容。原口径作废。）
- **完整 SHA-256 可称"校验同一性 / 高置信指纹"，不得表述为绝对"证明"。**
- 34 个 `logVerdict(` 调用点里真正"判过文本"的是哪几个，未逐一核。

## 实施前置（未完成）

1. **部署时归档现有活日志并重开**，沿用本仓上次增加 `backend/model` 时的做法。否则字段缺席会同时表示「历史记录」「未经判官」「调用点漏传」三种状态，三者同形。
2. **写入端 + 6 道闸的确定性控制流测试**，正反对照钉住：同文本同 hash / 不同文本不同 hash / 判官前早退与确定性兜底无该字段 / 回落读转录时 hash 的是实际 `lastMsg` / `capability-claim-gate` 判官后的两个 `skipped` 按明确语义处理 / 消费者（`gate-stats`、`gate-verdict`、eval runners）忽略新增字段。
