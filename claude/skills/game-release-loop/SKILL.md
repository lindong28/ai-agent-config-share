# 游戏发布闭环

围绕用户可观察的发布门槛推进游戏：每条 `P0` 旅程（用户确认必须通过的旅程）都要在发布目标矩阵上通过，且不能遗留已观察到的 Critical、High 或 Medium 问题。严重度定义采用 `~/.claude/commands/custom/test-ux.md` 的「issue 字段契约（codex session 必须遵守）」；代码覆盖率只是回归证据，不能证明用户体验。

定义范围或开始测试前，先读 [references/game-profile.md](references/game-profile.md) 并按该模板为本游戏填出配置档——它承载产品意图、交付边界、探索目标矩阵与暂定旅程，是本闭环全程的判据来源。配置档尚不存在时先建立它，不要凭对代码的印象开测。

## 输入

| 输入 | 要求 | 缺失时的行为 |
|---|---|---|
| 可运行产物 | 必需：已部署 URL 或可在本地提供服务的构建产物 | 安全时自行启动本地服务；否则请求真实产物 |
| 发布目标矩阵 | 得出发布结论时必需 | 初步发现阶段仅使用配置档中的探索目标矩阵；测试前先确认发布目标矩阵 |
| 产品意图 / GDD | 判断玩法质量或平衡性时必需 | 将本轮限制在平台/功能问题；或仅在用户确认后创建没有规格锚点的 UX 验收契约 |
| 源码项目 | 源码级修复和代码覆盖率声明时必需 | 先按预检能力门判 `build-only` 还是 `unknown`，两者可做的事不同（见该门的表），不要在未判定时就开始改 |
| UX 验收契约 | 执行完整测试—修复发布闭环时必需 | 仅诊断时使用配置档；发布工作前先创建或审查契约 |

## 控制骨架

`source`、`build-only`、`unknown` 是产物能力模式；`diagnostic-only`、`fix-enabled` 是修改授权模式。
证据状态统一为：静态线索是 `Candidate`，经真实用户入口复现后是 `Observed`，
必需路径无法执行时是 `Blocked`。

```text
预检能力门
  ├─ unknown → 只读诊断 → 发布结论与证据包
  └─ source | build-only
       → 可运行入口门
       ├─ 依赖嵌入宿主（父应用 / SDK 容器）
       │    → 游戏 server → 宿主内真实入口 → 互操作证据
       │    ├─ simulated → 仅证明模拟路径可运行
       │    └─ blocked → Blocked
       └─ 其它 → 直接使用已确认的可运行产物
       → 意图与目标门
       → 发布目标探索与分诊
       ├─ diagnostic-only / 无需修复 → 发布结论
       └─ fix-enabled → 修复能力门
            ├─ 无法安全修复 → 问题清单 / 源码请求 → 发布结论
            └─ 可以修复 → 测试先行修复 ⇄ 同目标复测 → 发布目标探索与分诊

发布结论：所有门通过 → READY；缺证据 → PARTIALLY VERIFIED；门失败 → NOT READY
```

### 预检能力门

检查仓库与产物，把输入归类为 `source`、`build-only` 或 `unknown`。项目自带构建审计脚本时可用它取线索，但**静态发现只是预检信号**：真正限制可修范围的是经仓库检查确认的能力边界。

| 模式 | 允许 | 禁止的声明/动作 |
|---|---|---|
| `source` | 发现问题、源码级修复、回归测试、代码覆盖率测量 | 除常规项目约束外无额外禁止项 |
| `build-only` | 发现问题，以及对压缩业务逻辑之外部分做可逆改动，例如 HTML 外壳 | 不得编辑压缩 bundle，也不得声称完成源码级修复或获得游戏代码覆盖率 |
| `unknown` | 只读诊断 | 找到可运行产物前不得进入修复闭环 |

### 可运行入口门

游戏依赖嵌入宿主（父应用、小程序容器、SDK host）才能进入真实 UI 时，入口不是游戏自己的 URL。先确认宿主侧的真实入口，并把宿主能力边界写成机器可读证据：哪些宿主调用被真实支持、哪些只是被模拟、哪些不支持。

- **SDK 等待页 / 握手未完成的页面不算可运行产物。**
- 只被模拟的宿主调用，其 `simulated` 状态**只**证明该模拟路径可运行，不能单独让任何产品旅程判 `Pass`。
- 宿主不支持的能力对应的旅程是 `Blocked`，不是 `Fail`，也不是 `Pass`。
- 入口 URL 必须取自宿主程序自己输出的地址，不要自行拼接。

### 意图与目标门

从用户请求中判断授权属于 `diagnostic-only`（不修改产品）还是 `fix-enabled`（用户已授权修复）。修改授权不清楚时，改文件前使用 `AskUserQuestion`。

只有当前请求或已审查的 UX 验收契约明确写出可运行产物/版本和发布目标矩阵时，才把它们视为已确认；矩阵中的每个目标都是「交付模式 × 设备/浏览器」的组合。否则使用 `AskUserQuestion` 展示发现的候选项，标出推荐项与取舍并让用户选择；选错会让每条旅程和每个目标产生倍增返工。

开展发布工作时，没有契约就应用 `~/.claude/commands/custom/create-ux-contract.md`，由它负责领域路由和审查闭环；已有契约就应用 `~/.claude/commands/custom/review-ux-contract.md`。游戏领域文件按 `~/.claude/references/domain-registry.md` 的「路由表」加载。本技能的显式调用即授权组合这些流程。只有用户或已审查契约尚未决定产品意图、P0 选择、支持承诺、平衡性改动或较弱验收门槛时，才使用 `AskUserQuestion` 给出选项、推荐和取舍。

### 发布目标探索与分诊

应用 `~/.claude/commands/custom/test-ux.md` 中的「端到端真实使用」「用户操作覆盖面」「Persona」「codex session 派发与裁决」和「issue 字段契约（codex session 必须遵守）」。用户确认哪些旅程属于 P0 后，以首次玩家和回流玩家身份执行配置档中的暂定旅程。同时加载领域注册表路由到的游戏测试模式，包括「多端交付失配」。

维护「旅程 × 目标」覆盖账本。每轮发现选择风险最高的未覆盖单元格继续，直到每个必需单元格都成为 `Pass`、`Fail`、`Blocked` 或等待用户决定；代码覆盖率永远不能代替该账本。

为保持发现过程独立，向 UX 测试代理提供产品配置档、旅程、发布目标矩阵、预期来源、本轮实际测试入口及宿主能力边界，但不泄露预检 bug 结论；在分诊时再合并两组证据。

**领域模式必须随 prompt 交到测试代理手上**：`test-ux` 的派发 prompt 只带通用 patterns，所以 domain registry 路由出的游戏模式文件（`~/.claude/references/game/ux-test-patterns.md`，含 GP1–GP6 与「多端交付失配」）要作为该代理的必读输入显式传入并给出路径。只在本文写一句「加载游戏模式」不构成传递——隔离的代理读不到你的 context，而漏掉「多端交付失配」正是多目标游戏最容易据此误判 READY 的一条。

### 修复能力门

一般的「产品问题还是修复问题」判断，遵循 `~/.claude/commands/custom/execute-ux-contract.md` 的「Supervisor 裁决（test → fix 之间）」。在 `fix-enabled` 模式中，只有目标行为和修改授权都毫无歧义时，才自动修复机械性问题。

项目覆盖规则：`build-only` 模式下，压缩业务逻辑内部的问题只产出可直接编码处理的问题说明和源码请求。

当静态缺陷与更安全行为都明确无歧义时，可以对 `build-only` Candidate 做可逆的 HTML 外壳缓解。把它记录为缓解措施，证据类别仍保持 `Candidate`；只有在真实目标上复现验证后，它才可用于支持 `READY`。

### 测试先行修复与同目标复测

源码级修复使用项目自身测试框架，并应用 `~/.claude/skills/tdd-workflow/SKILL.md` 中的 `Run Tests (They Should Fail)` 与 `Run Tests Again`。存在代码覆盖率基础设施时，记录修复前后结果、防止整体回退，并覆盖变更行为；不存在时不得声称获得代码覆盖率。对 `build-only` HTML 外壳修复，先添加能复现 `Observed` 问题或已授权 `Candidate` 缓解措施的最小可执行回归检查，并确认它先失败。

每次修复后重新运行：

1. 新增回归测试。
2. **先把修复物化成新产物，再重新绑定版本**——需要重新构建 / 重启 dev server / 重新部署的，先做完；然后从真实入口重新确认版本标识（build stamp / 资产 hash / 版本号）确实是修复后那一份。跳过这步就可能对**旧产物**复测：`test-ux` 明确规定版本不能只靠问，此处同理。绑不上版本时该旅程记 `Blocked`、不记 `Pass`。
3. 在同一目标上通过真实用户入口重走受影响旅程。
4. 变更面跨目标共享时，再测一个相邻目标。

完整测试—修复发布闭环使用 `~/.claude/commands/custom/execute-ux-contract.md`。注意它的输入契约只收 ux-contract 路径，所以**配置档、用户确认的 P0 旅程、完整发布目标矩阵、宿主能力边界这四项必须由本 skill 显式补进去**——补给 supervisor、test 代理与修复代理三方，并在开跑前逐项核对齐全。ux-contract 未逐项重复整张矩阵时，缺的单元格会同时从 test plan 和测试 prompt 里消失，而账本仍可能推导出 READY。同时向修复代理提供经仓库确认的能力边界与本节回归要求；缺少必要回归证据的修复必须拒绝。

### 发布结论与证据包

`READY` 要求每条用户确认的 P0 旅程在所有发布目标上通过；声称支持 iPhone 时，至少包含一次真实 iPhone Safari 测试。不得遗留已观察到的 Critical、High 或 Medium issue；范围内每个 Critical/High/Medium Candidate 必须完成以下之一：复现并处理、缓解并在真实目标验证、证伪，或按已确认支持契约排除。因缺证据而阻塞的 Candidate 会得到 `PARTIALLY VERIFIED`。每个修复都必须同时通过回归检查和真实用户入口复测。

缺少必需覆盖面时结论为 `PARTIALLY VERIFIED`；任一门失败时为 `NOT READY`。用户可以显式接受发布风险，但该决定不会把结论改成 `READY`。

诊断或 `build-only` 运行时，在 `plans/<YYYYMMDD>-game-release-loop/` 下写入以下产物：

| 产物 | 含义与消费者 |
|---|---|
| `issues.md` | Observed → 分诊/修复；Candidate（含静态预检线索）→ 修复前先复现（HTML 外壳缓解规则除外）；Blocked → 移除依赖后复测。每条记录证据状态、复现入口与所属目标 |
| `validation.md` | 已测产物/矩阵、旅程×目标账本、修复/复测、限制、发布结论，以及面向开发者的白话总结 |

白话总结必须说明：游戏是否可发布、发现或修复了哪些明显问题，以及哪些内容仍因缺少源码、设备、服务、凭据或产品决定而阻塞。完整 UX-contract 运行使用 `execute-ux-contract` 自己管理的产物，并把 `validation.md` 写在该次运行的 `plan.md` / `state.md` / `journal.md` 旁边，再从这些产物推导游戏专用的旅程×目标账本和发布结论。
