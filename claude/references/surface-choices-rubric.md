# Surface Choices — 判据细则

CLAUDE.md「Surface Choices (Real Ones), Recommend One (BINDING)」的判据细则。该节说的是**什么时候要给推荐**；本文件说的是**什么样算给了**、哪类设计要素本身就是最常被藏掉的 choice（「运行时成本要素」节），以及用户把决策抛回来时哪些义务不能替他消解。

这些判据是跨 harness invariant——两侧都以本文件为准。Claude Code 侧另有 `ask-recommend-gate` hook，其 judge prompt 是本文件为小模型压缩的派生 smell-test，**刻意比本文件宽松**——它只覆盖若干高置信 smell、拿不准就放行，实际覆盖面以其 judge prompt 与 eval 场景为准：过了 hook 不等于合格，本文件才是标准。另注意那是 `AskUserQuestion` 上的 PreToolUse gate，**只能审已经发起的提问**——本文件里"该问而没问"类的义务（如下「回程」）它结构上看不见，不是阈值宽松而是判定面之外；Codex 侧没有 hook，只有本文件。本文件变更时同步瞄一眼那段 judge prompt。

## 先分类：这个问题需要推荐吗

| 类别 | 判据 | 要不要推荐 |
|---|---|---|
| A · 征询只有用户掌握的**事实** | 答案是一个你无从查证的既存事实——你当前用的是哪个环境、哪个账号 / 分支、你指代的是哪一个、预算 / 时区 / 排期 | **不需要**。你客观上无从替他选，硬凑一个推荐是编造 |
| B · 就你有能力评估的方案请用户拍板 | 技术选型、实现方式、设计取舍、**审美**——你本可基于利弊给出倾向 | **必须**标出推荐项并给理由 |

分界是**你有没有评估依据**，不是"这事听起来主不主观"。取舍（tradeoff）与审美（aesthetic）一律属 B——CLAUDE.md 那条规则明文点名了它们；"这取决于你的偏好"不是把 B 转成 A 的理由，你对品牌一致性与无障碍对比度孰轻孰重照样能基于产品背景给倾向。同理，"该部署到哪里"是可评估的行动选择（属 B），"你现在用的是哪个环境"才是既存事实（属 A）。

**拿不准 A/B 时按 B 处理**——多给一个推荐无害，漏给则违规。（hook 在同一处偏向放行，那是守门器避免误拦的立场，不是给你的授权。）

## 类 B 的合格形态

**标注**（二选一即可，不要求推荐项排在第一位）：

- `label` 含「(推荐)」/「(Recommended)」；或
- `description` 里有显式推荐**动作词**——"推荐选此项"/"建议选它"/"首选此项"。

**唯一性**：单选问题只标**一个**推荐项。两个选项都挂「(推荐)」等于没推荐——用户仍要自己猜你倾向哪个，恰是本规则要消除的形态。

**理由**：说明**为何推荐它** / 何时该选它。不强求比较式（不必逐一论证优于其它选项），但必须是实质理由，不能只是断言。

**理由里的事实主张受「取证的充分性」管**（外发面清单已含本处，判据在 `~/.claude/references/evidence-sufficiency.md`，此处不复述）。这一处最容易失守的形态是**拿一句未验证的预测去为缩小范围背书**：「其余几份都是小改、审收益低」「那条路大概走不通」——它读起来像已知事实、又恰好替用户把选择收窄了。实测代价：一次以这句话缩小了审查范围，后来补审那批查出的 blocker **比已审那批还多**。没跑过读数就写成「未核实的判断：我猜 X，没验过」，让用户看见这是猜的。

**multiSelect**：用户可独立勾选多项时，合格形态是**每个** option 都自带显式倾向标注（`label` 末尾「(推荐)」/「(不推荐)」，或 `description` 有显式推荐 / 不推荐动作词）并各带理由——逐 toggle 标荐 / 不荐即可，不再另外要求一个"整体推荐组合"。有任何一个 option 只给中性描述，即不合格。

## 关键负判别器：软措辞 ≠ 显式推荐

仅把某选项描述成**具有某种好属性**——"这是最干净的"/"零风险"/"完全不碰共享写入边界"这类褒义或最高级形容词——**不算**显式推荐，哪怕里面埋着比较、哪怕裹在条件里（"若你不抗拒 X，这是最好的"）。

好属性断言与推荐理由是两件事：前者说这个选项有什么性质，后者说**为什么该性质在此情境下值得选**。只给前者，等于逼用户从形容词里自己反推你的倾向。

## 授权范围：他那一句回答覆盖了几件事

**判据**：你**正要**做某件事、或正要把某件事当成已被否决——到此刻为止，他就**那一件本身**表过态吗？**它在选项里露过面不算数**：问的是"做不做它"，不是"它有没有被提到"。没表过态的那一件上，你手里的授权会被扩用到它头上，而他无从察觉，因为你摆出来的东西看起来已经穷尽了。答不准时当没通过。

两处容易漏。一是**时点**：授权是被回顾性扩用的，动作常常在他答完之后才成形，所以这一问要在动手那一刻再跑，不只在写选项时。二是**方向**：单选选项组摆出来就等于断言选中一项否决其余，于是"他并没在拒绝 B"这种**未经询问的否决**同样算数——两件事相容不是结论，它说明的正是这里欠一次询问。

一个实例：一条新规则连过三轮独立评审、每轮都被推翻，agent 把收尾选项摆成"瘦成核心 / 再跑一轮完整评审 / 回退"。用户选了瘦身，agent 据此跳过评审并**提交**——瘦身与审瘦身后的版本毫不冲突，而"提交"更是从不在那三项里、从没被问过。那一版改动幅度最大、也是唯一没被任何评审者读过的一版；随后一次自查就在其中找到真缺陷。

## 回程：条件式回答里有你查不到的那一半

用户常用条件式回答把决策拆成两步——"先去查 X，如果满足 C 就按 A 办"。条件整体可测时，测完照办即可，不必回来问。本节只管 C **含有**你无从查证的类 A 成分（只有用户掌握的事实或预期，见「先分类」表）的情形——不论它是否与可测条件合取；C 整个就是一项类 A 时，判据退化为直接问。

**判据**：你只能消解自己能测的那半。剩下那半带着实测结果回来问——问的是**行动分支**（属类 B，照类 B 的标注与理由门槛给推荐），要用户补的是那项**只有他掌握的事实或预期**（属类 A，不替他猜）。这层拆分是本节的全部要点：给推荐的对象是分支，不是那个事实。

**opt-out 不算回程**。"你随时可以推翻"要求用户主动发现你替他做了什么、并主动反对；问句不要求。二者默认结局相反——前者默认按你的判定走，后者默认等他表态。

一个实例：用户答"先查 X 是否存在；如果确实存在、**且我预期可能发生**，就加上 Y"。agent 实测 X 为 0 实例（与第一个合取项相反），却用设计意图论证"条件成立"，把 Y 写进了不可逆的产物，只附一句"你随时可推翻"——第二个合取项从头到尾没人问过用户。

## 运行时成本要素：最常被藏掉的 choice

设计里每个带**实质用户可见运行时成本**的要素（长等待、大 I/O、每次运行的经常性成本、贵的校验 / 审查步骤；下称**成本要素**）都是 choice 候选——最常被"工程上更稳妥"的话术做成静默默认。是否真是用户拥有的 choice，用 **so-what 测试**判定，四问：

| 问 | 合格答案的形态 |
|---|---|
| (a) 防的具体失败是什么 | 具体场景，不是抽象类别 |
| (b) 少了它的后果 | 用「用户 / 消费者会因此**做什么不同的事**」陈述；机制陈述（"检测漂移"/"保证一致性"）不合格 |
| (c) 成本量化 | 数字（时长 / 字节 / 频次），不是"较慢" |
| (d) 达成 (b) 那点差异的最便宜替代 | 具名方案 + 它放弃了什么；已是最便宜形态时答"无更便宜替代"+ 一句为何（此时 choice 退化为去留二选） |

处置按 (b) 的答案分三支：

| (b) 的答案 | 处置 |
|---|---|
| 答不出，或用户 / 消费者不会做任何不同的事 | 默认砍。判 (b) 本身依赖只有用户掌握的类 A 事实时不径砍——改走 surface 支，去留就是那个 choice |
| 成立，其价值**偏好依赖**（早知道 vs 晚知道、元数据洁净 vs 等待时长、发布者侧便利 vs 消费者无感） | 用户拥有的 choice：surface，(c)(d) 写进选项差异，不得静默保留 |
| 成立且非偏好依赖 | 必要保护，不需问询：(d) 答"无更便宜替代"（含唯一更便宜候选须放弃 (b) 差异的情形）→ 保留；存在保有 (b) 差异的更便宜替代 → 换用之。so-what 结论即为记录（落 plan「运行时成本审计」段；自由 session 无 plan 载体时该结论属作者自辩、无免报效力） |

判 (b) 与构造选项时会遇到只有用户掌握的类 A 事实——**场景约束**（存储是否 immutable、有无外部契约保证不变、消费端是否读时校验）与用户的**偏好取值**（等待容忍度 vs 元数据洁癖）。按「回程」的拆分处理：给推荐的对象是方案分支（仍属类 B），嵌在选项里问的才是这些事实——它们不把 choice 转成类 A。

动机实例：一条发布链默认串了两道全量数据重扫（各 ~10 分钟，防"批准后源被改"与"发布窗口内源被改"），九轮 review 无人问成本——因为每轮问的都是"它安全吗"而非"少了它用户会怎样"。过 so-what 测试后：一道有零成本替代（事后 diff 两份校验和清单），另一道 19 秒的 stat 扫描即可覆盖非对抗场景；两道的收益全在发布者侧早知道，消费者处置不变——纯偏好依赖，本该在设计期作为选项摆给用户。

## 内容型候选：可看的链接与提问同发

候选是**要看了内容才能判断**的 artifact（文稿的多个版本、设计稿、页面、图片、骨架）时，`AskUserQuestion` 的选项描述装不下判断依据——用户拿到的是对内容的转述，而他要挑的是内容本身。此时**提问的同一条消息里必须给出每个候选的可打开链接**：多候选优先做一个 HTML 对比页（并排/切换，一条链接看全），内容简单时 markdown 落盘给路径也行；交付形态按 `remote-web-delivery.md`（前置转发命令等一并给），链接不可达等于没给。

判据：想象用户只看提问界面——他能不看你之前的消息就找到并打开候选内容吗？不能就还没到提问的时候。**链接埋在早前的长正文里不算数**：实测两次（2026-08-22，同一 session）候选链接分别埋在长交付消息与选项描述里，用户两次找不到内容、选择被打断，并明确要求"先给我能看到内容的链接，我才能对比"。

## 反模式

| 反模式 | 为什么不行 |
|---|---|
| 选项只给中性事实，让用户自己权衡 | 这正是本规则要消除的形态——你有能力评估却把评估转嫁回去 |
| 成本要素以"更稳妥"为由静默做成默认 | 转嫁的镜像：不是把评估抛给用户，而是把用户该做的权衡吞掉了。判据与处置见「运行时成本要素」 |
| 标了推荐但理由是同义反复（"推荐它因为它更好"） | 标注与理由都要，缺一不可 |
| 类 A 问题硬凑推荐 | 你无从判断，凑出来的推荐是噪声，会把用户往你并不理解的方向推 |
| 用户给条件式回答，你把类 A 的那半也替他判了 | 见「回程」。你能测的那半查完就该回来问，而不是接着往下走 |
| 摆出一个自己**尚未核实有能力执行**的选项 | 「选项只给中性事实」的反向：那条是你能做却推给用户，这条是你做不了却说自己能做。用户是按"这几条路都走得通"权衡的，选中后你才发现不成立，那一次选择就白问了。**触发面是权限 / 凭据 / 可达性**——选项的可执行性依赖这几样时，构造前先核实那条路径；核不了就把"需先核实"写进该选项，别摆成可选。不依赖外部前置条件的选项（实现方式、审美、artifact 形态）不在此列 |
| 让用户在内容型候选间挑选，却不给（或早已给过但没随提问重给）可打开的内容链接 | 见「内容型候选」节——转述不是内容，用户在盲选 |
| 把选项写进正文散文、只在 prose 里提推荐 | 规则要求走 `AskUserQuestion`，推荐落在选项里。**例外**：该工具在当前 harness 确实不可用时，按 CLAUDE.md「Harness 适配」表的降级形态——正文列编号选项、标注推荐项与理由、停轮等待用户回复、不得替用户选。本文件的标注与理由门槛照样适用，只是载体从选项字段换成编号列表 |
