# Surface Choices — 合格形态与理由门槛

CLAUDE.md「Surface Choices (Real Ones), Recommend One (BINDING)」的判据细则。该节说的是**什么时候要给推荐**；本文件说的是**什么样算给了**，以及用户把决策抛回来时哪些义务不能替他消解。

这些判据是跨 harness invariant——两侧都以本文件为准。Claude Code 侧另有 `ask-recommend-gate` hook，其 judge prompt 是本文件为小模型压缩的派生 smell-test，**刻意比本文件宽松**——它只覆盖若干高置信 smell、拿不准就放行，实际覆盖面以其 judge prompt 与 eval 场景为准：过了 hook 不等于合格，本文件才是标准。另注意那是 `AskUserQuestion` 上的 PreToolUse gate，**只能审已经发起的提问**——本文件里"该问而没问"类的义务（如下「回程」）它结构上看不见，不是阈值宽松而是判定面之外；Codex 侧没有 hook，只有本文件。本文件变更时同步瞄一眼那段 judge prompt。

## 先分类：这个问题需要推荐吗

| 类别 | 判据 | 要不要推荐 |
|---|---|---|
| A · 征询只有用户掌握的**事实** | 答案是一个你无从查证的既存事实——你当前用的是哪个环境、哪个账号 / 分支、你指代的是哪一个、预算 / 时区 / 排期 | **不需要**。你客观上无从替他选，硬凑一个推荐是编造 |
| B · 就你有能力评估的方案请用户拍板 | 技术选型、实现方式、设计取舍、**审美**——你本可基于利弊给出倾向 | **必须**标出推荐项并给理由 |

分界是**你有没有评估依据**，不是"这事听起来主不主观"。取舍（tradeoff）与审美（aesthetic）一律属 B——CLAUDE.md 那条规则明文点名了它们；"这取决于你的偏好"不是把 B 转成 A 的理由，你对品牌一致性与无障碍对比度孰轻孰重照样能基于产品背景给倾向。同理，"该部署到哪里"是可评估的行动选择（属 B），"你现在用的是哪个环境"才是既存事实（属 A）。

**拿不准 A/B 时按 B 处理**——多给一个推荐无害，漏给则违规。（hook 在同一处偏向放行，那是守门器避免误拦的立场，不是给你的授权。）

## 类 B 的合格形态

**标注**（二选一即可，不要求推荐项排在第一位）：

- `label` 含「(推荐)」/「(Recommended)」；或
- `description` 里有显式推荐**动作词**——"推荐选此项"/"建议选它"/"首选此项"。

**唯一性**：单选问题只标**一个**推荐项。两个选项都挂「(推荐)」等于没推荐——用户仍要自己猜你倾向哪个，恰是本规则要消除的形态。

**理由**：说明**为何推荐它** / 何时该选它。不强求比较式（不必逐一论证优于其它选项），但必须是实质理由，不能只是断言。

**multiSelect**：用户可独立勾选多项时，合格形态是**每个** option 都自带显式倾向标注（`label` 末尾「(推荐)」/「(不推荐)」，或 `description` 有显式推荐 / 不推荐动作词）并各带理由——逐 toggle 标荐 / 不荐即可，不再另外要求一个"整体推荐组合"。有任何一个 option 只给中性描述，即不合格。

## 关键负判别器：软措辞 ≠ 显式推荐

仅把某选项描述成**具有某种好属性**——"这是最干净的"/"零风险"/"完全不碰共享写入边界"这类褒义或最高级形容词——**不算**显式推荐，哪怕里面埋着比较、哪怕裹在条件里（"若你不抗拒 X，这是最好的"）。

好属性断言与推荐理由是两件事：前者说这个选项有什么性质，后者说**为什么该性质在此情境下值得选**。只给前者，等于逼用户从形容词里自己反推你的倾向。

## 回程：条件式回答里有你查不到的那一半

用户常用条件式回答把决策拆成两步——"先去查 X，如果满足 C 就按 A 办"。条件整体可测时，测完照办即可，不必回来问。本节只管 C **含有**你无从查证的类 A 成分（只有用户掌握的事实或预期，见「先分类」表）的情形——不论它是否与可测条件合取；C 整个就是一项类 A 时，判据退化为直接问。

**判据**：你只能消解自己能测的那半。剩下那半带着实测结果回来问——问的是**行动分支**（属类 B，照类 B 的标注与理由门槛给推荐），要用户补的是那项**只有他掌握的事实或预期**（属类 A，不替他猜）。这层拆分是本节的全部要点：给推荐的对象是分支，不是那个事实。

**opt-out 不算回程**。"你随时可以推翻"要求用户主动发现你替他做了什么、并主动反对；问句不要求。二者默认结局相反——前者默认按你的判定走，后者默认等他表态。

一个实例：用户答"先查 X 是否存在；如果确实存在、**且我预期可能发生**，就加上 Y"。agent 实测 X 为 0 实例（与第一个合取项相反），却用设计意图论证"条件成立"，把 Y 写进了不可逆的产物，只附一句"你随时可推翻"——第二个合取项从头到尾没人问过用户。

## 反模式

| 反模式 | 为什么不行 |
|---|---|
| 选项只给中性事实，让用户自己权衡 | 这正是本规则要消除的形态——你有能力评估却把评估转嫁回去 |
| 标了推荐但理由是同义反复（"推荐它因为它更好"） | 标注与理由都要，缺一不可 |
| 类 A 问题硬凑推荐 | 你无从判断，凑出来的推荐是噪声，会把用户往你并不理解的方向推 |
| 用户给条件式回答，你把类 A 的那半也替他判了 | 见「回程」。你能测的那半查完就该回来问，而不是接着往下走 |
| 把选项写进正文散文、只在 prose 里提推荐 | 规则要求走 `AskUserQuestion`，推荐落在选项里。**例外**：该工具在当前 harness 确实不可用时，按 CLAUDE.md「Harness 适配」表的降级形态——正文列编号选项、标注推荐项与理由、停轮等待用户回复、不得替用户选。本文件的标注与理由门槛照样适用，只是载体从选项字段换成编号列表 |
