# Evidence Sufficiency

`CLAUDE.md`「取证的充分性」落到操作层的做法。

**什么时候读**：读的时点由 `CLAUDE.md`「取证的充分性」单一持有——它绑在**事实主张外发之前**（外发面的清单见该节，此处不复列）。**本文件不另立触发点**，以免同一义务在两处漂移。

时点之外，下面的条目适用于任何取证动作，包括你正准备跑的那条确认命令。判不准算不算时按适用处理。

**为什么绑在"外发前"而不是"跑命令前"**：后者在一个跑上百条命令的 session 里等于每分钟触发一次，实测退化成 **0 次打开**（一次 128 条 Bash 的 session 里，本文件被读 0 次）；而"事实要外发了"低频、可识别，且恰好是错了才有代价的那一刻。

**最容易漏的触发形态**，因为你不觉得自己在取证：**把一条并非为该问题而跑的命令的输出读成了结论**——摸底、survey、顺带 dump。此时区分度检查的优先级**更高**，不是更低：那次读数没有为这个结论设计过，你也就没有"我在取证"的自觉。实测的失守全部落在这一类（一条命令并列问三四件不相干的事，输出被略读，其中一段进了决策），而主动跑对照的几次全部发生在已经处于测量循环里的时刻。

这些条目此前住在 `coding-guidelines.md`；那个文件名让人在非编码相位直接判定它不适用，而这几条恰恰在那个相位最常失守。

- 证据要在结论宣称成立的环境里取得：当前 shell、venv 等既存状态是结论的隐藏前提，不是"干净环境 / 全新安装 / 换台机器"的证据。同理，**已在运行的进程**带的是它启动那一刻的环境与代码，而修复常靠"下次启动时加载"生效——"修复已提交"因此不等于"修复已生效"。要断言某个跑着的东西已被修好，证据得取自那个进程（启动时间晚于修复，或直接观察它的当前行为），不是取自仓库；长寿的 tmux pane、daemon、worker 能带着过期环境跑上数天而毫无征兆。
- 据一次检查下结论前，先证明这个仪器报得出**相反**的结局：它报失败 / 空 / null 时，跑一次阳性对照（已知良好条件下它确实报成功）；它报通过时，跑一次阴性对照（预期失败时它确实报失败）。**阴性对照要选对施扰的轴、而且真的越界**：轴要取缺陷**可能所在**的那个，它未必等于断言名义上守的那个量，两者不一致正是下面第二例的失效点；输入则要真能把那个量顶过阈值——被检对象"计数非零"只证明查过了，不证明这次输入够得着阈值（这是本节后面"先断言数量非零"那条的另一半：计数必要而不充分）。实测两例：一条名为「配图不得主导视口」的断言 `max(imgH / innerH) <= 0.4`，上一行就是 `assert media.count() >= 1`、计数这一关是过的，而夹具里 100 多条只有 2 条有图、每条 1 张、图 URL 指向 discard 端口永不加载——于是它在"图确实不主导"与"根本没有配图"两种情况下读数相同。另一例在感知轴上：为音画同步探针施的扰动是"整体时移 +5 s"（检出 −5 s，通过），而缺陷在"时间线断口"轴上，两个探针都把音视频重建成连续流、恰好抹平了那个轴——控制通过 ≠ 对本题材有区分度。阳性与阴性两个方向都有各自的骗法：探针有 bug、读取窗口太小、请求被代理拦截会让健康的对象呈现为坏的；而两种结局下都相同的恒定读数（典型是观测手段自己进了被观测集合）会让坏的呈现为好的。多个本应独立的字段同时为空时，先把"仪器或 scope 取错"当作待证伪的假设，再读成缺陷加剧——但它只是假设：确实存在整片同时为空的真故障。

  **同一个同形还有一条被动来路：不是施扰失败了，是验收集自己没有方差。** 上面整段讲的是主动施扰（我去破坏一次，看仪器响不响），于是读者在"我这次做阴性对照了吗？做了啊"这一步就判定本条已满足。但**验收集在某个被断言覆盖的维度上只有一个取值**时，无需任何人施扰，读数在"这个维度工作正常"与"这个维度被完全忽略"两种情况下就已经相同——上面那个 `media.count() >= 1` 的夹具正是它——注意方差为零的**不是**"有没有图"（那一维有方差：2 条有、100 多条没有），而是"**图有没有真的加载出来**"：那 2 条的 URL 全指向 discard 端口，渲染出来的张数恒为 0。轴名取错会让你以为这一维已经覆盖过了。三件事跟着这条走：

  - **轴的清单从交付物自己声明的输入面逐个抄下来**——函数签名、API schema、请求体字段；测试套件的输入面就是它的 fixture / 参数空间——不靠"想想缺陷可能在哪"。上一段要求"轴要取缺陷**可能所在**的那个"，却把轴的**枚举**留给了直觉；而漏掉的那一维，恰恰是你没想到要列进来的那一维。**这份清单是下限不是上限**：并发、时序、冷热状态、上一轮遗留的状态都抄不到任何声明面上，得自己补——"照抄"replace 的是直觉**枚举**，不是免除你想第二遍。
  - **触发形态按断言的形状认，不按用词认**：`12/12`、`136 passed`、"全部通过"、乃至单次"验证通过"都算——**凡是一句覆盖某个输入集的通过主张**。越含混的说法越要写，因为触发强度与证据强度天然反向：写得出 `12/12` 的人通常真数过，说"跑通了"的人往往没有，而后者恰是输入集塌缩最容易藏身的地方。
  - **报通过率时，同段写出输入集在每个声明维度上的取值数**，形如 `n=12（image: 1 unique · text: 12 unique · dialogue: 0 有 / 12 无）`。**某维取值数为 1 时，该维不得进入被断言的范围**——**但"把结论写窄"只是便宜的那一档出口，它有一个不适用的情形**：塌缩的那一维**正是这个交付物的主语**时（图生 prompt 服务的 `image` 维），把它排除出去，剩下的断言不指向任何东西，形式合规、实质是空断言。**那一档必须补样本。** 强制力与下面 `page-acceptance` 那行同源：缺了这个格子，"12/12 通过"在输入集健全与输入集塌了两种情况下逐字相同，而**没有格子的那一项就是被跳过的那一项**。
  - **修复的手法是"满足某条件时改变或取消行为"时，该条件的两侧各要有验收样本。** 只验被修的那一侧，与"这个 fix 制造了第二个缺陷"同形——此时阴性对照**即使轴选对了也救不了你**：它证明的是"这个 fix 解决了原缺陷"，不是"这个 fix 没有造出新缺陷"。（同一判据在 `create-eval-harness.md` 的「双向守卫」里已有一份，但那条的射程锁死在 LLM 判官组件上，够不着普通代码分支。）

  实测（缺陷全部由使用者在交付后报回）：一个 (首帧图, 文字) → prompt 的 HTTP 服务，冷启动验收 **12/12**（dgx 上一个干净目录里的临时进程），另有一次消费者通道读数 **5/5**（从另一台机走 HTTP 打常驻实例，5 种请求 / **3 张图**）。**两次读数里对白那一维的取值数都是 0，图那一维分别是 1 和 3。**而那 12 次调用**用的是同一张图**（报告自己写着"n = 12，同一张首帧图"）；对白那一维的方差同样是零，且是结构性的——该端点构造的 intent 从不带 `dialogue` 键，所以 12 条产出无一含对白，想变化也变化不出来。真相（**当时**的状态，两条现均已修复——这里记的是事故，不是那个服务今天的样子）：writer 不读取像素，代码里当时写着 `pixels_available_to_current_writer: False`；同一句文字配两张互斥的真实首帧图，两份产出都写 `dark blazer over a light-colored blouse`，**各自图片的识别属性命中 0/4**。而那次修复的手法正是"`dialogue_markers` 为空就取消整条对白规则"，该端点上它恒空，于是服务失声：请求里带台词，**产出的 `<d>` span 数 0/4**，台词被改写成一个手势。（**别把产出里那句 `<Picture 1> … is fully referenced` 读成"它自称看过图"**——那是官方 spec 的逐字 literal，语义是对下游视频模型的任务条件；真正的后果是我方 prompt 自相矛盾：header 承诺首帧被完全参考，body 描述的却是另一个人。）两个缺陷都由使用者在交付后报回。完整读数在 `philo-prompt` 仓：`docs/issues/general.md` 那两条 open 条目最全，另见 `plans/20260821-h3-prompt-writer-service/` 的 `state.md`、`journal.md` 与 `delivery/` 下那份交付报告（"n = 12，同一张首帧图"与"5 种请求 / 3 张图"两个数字只在后两者里）。
- **取到了正确的样本，不蕴含读完了取到的样本。** 上一条管仪器本身；这一条管取回来之后——仪器可以完全正确、区分度可以已经验过，失守发生在它之后那一步。仪器给了 N 个样本（介质无关：N 帧、N 条日志、N 个 case、N 条返回），读到第 k 个恰好支持某个方向就停下写结论——剩下的 N−k 个从未被看过，而结论读起来与读完了 N 个完全相同：它自洽、有具体出处、落得到时刻，看不出任何缺失。没有下游能发现它，因为缺席的是一次没有发生的阅读，不留痕迹。**适用面由结论的量词划**：「它发生过」这类存在性结论，拿到一个有效见证即可停——没读的那些推翻不了它；而结论依赖整组样本时必须读完——全称判断、聚合、比较，以及任何形式的「它没有发生」。别拿一个计数交差：`取 4 读 4` 在真读了 4 个与只读了 1 个两种情况下都写得出来，正是本条刚说的那种同形。要报的是**每个样本各一句读数**（`帧0：手在腰腹；帧1：抬到胸口；…`）；写不出某个样本的读数，就是没读它。N 大到正文写不下时，逐样本读数落一个持久载体，正文给总数、最强反例与那个载体的路径——没有载体就只能称抽样检查，不得声称读完："计数 + 最反对的那一条"单独拿出来，在读完了全部与只读了一部分两种情况下同形。它由方向触发：读到一个支持既有假设的样本时，继续读剩下的在当下感觉不增加信息——而那正是最该继续读的时刻，同一批样本里的反例只会出现在你还没读的那部分。实测：一次视频判读取了 4 帧、只读 1 帧就断言"这一侧全程停在腰腹"，被同组另一帧当场推翻；同一天同一批素材上连错五次，其中至少两次的取样是对的（逐次形态见 `~/private-project-a/docs/generation-realtime.md` 的「观察视频的方法」）。
- **一个已证成立的下游根因不是搜索终止条件。** 同一症状可以有多个成因，而"根因已查清"本身就是一条反向断言（"没有别的原因了"），它没有下游能打脸。真根因带来的满足感恰恰会终止搜索——这比查不出根因更危险：查不出会继续找，查出来就不找了。判据同「据一次检查下结论前，先证明这个仪器报得出相反的结局」那条：**再问一次这个症状，在"只有这一个成因"和"还有别的成因"两种情况下，你手上的读数会不同吗**。实测：唇音不同步查到容器时间戳空洞（真实、已修、已验证）后即收工，从未追问音频源本身是不是产品的那一个——而它确实不是。
- **溯源因果时先找显式引用载体，时间共现是弱证据。** 结论形如"A 促成了 B"（这条规则出自那个项目、这次改动源于那次故障）时，最顺手的读数是两侧时间线的同期性——而它在"真有因果"与"只是同期发生"两种情况下读数相同，且同期性几乎总能找到（活跃项目每天都有 commit）。**先找显式引用**：issue 台账里写着修法落在哪个仓的哪个 sha、ADR 里点名的触发案例、commit body 里引的编号——这类载体是当事人自己写下的归属，比时间戳硬一个量级。**反向同样要查**：候选在主题上再贴合，也先查它的诞生时间——比被溯源的事件更早就直接排除（实测一个命令主题完美契合、时间也像，一查生日早于项目启动三周，不查就会写进对外文章）。找不到显式载体时，如实报"仅有同期性"，别把它写成因果。

- **发现候选的检索至少两轮，第二轮要产出一个能失败的读数。** 判据同上一条的反向断言，只是换了对象——从"还有没有别的成因"换成"还有没有别的候选"：结论形如"这几个就是相关的候选"（可参考的产品、可行的方案、prior art、同类实现）时，返回的那几个个个成立、凑成一篇自洽的对比，于是"名单完整"与"漏了整个品类"读数相同，而完整性没有下游能打脸。两处同形各堵一半，下面两步按同样的次序各堵一处：

  | 同形来源 | 为什么察觉不到 |
  |---|---|
  | 品类是隐式的 | 你不觉得自己选了一个品类，只觉得自己描述了对象；而默认继承的是手头既有物的自称，那恰恰是要被替换掉的那个东西的自我定位 |
  | 检索式自带候选名 | 它只能证实这些名字存在，结构上不可能报出名单外的东西 |

  两步，每步都要留下第三方能重算的读数：

  1. **定品类**：从对象的**功能句**推导——它做什么、为谁产出什么——并把那句原文引进结论。**不接受自称与品类标签**：待查对象常常就是要被替换的那个既有物，它 README 的首句往往正是要拒斥的那个自我定位（下面实测里 "data lineage" 就是）。没有成文功能句时，自己写一句请用户确认。
  2. **品类内枚举**：query 不含候选名，且落在与第一轮不同的表述轴上（换功能描述、换使用场景——同义改写不算）。**报的不是数字，是名字**：① 第二轮**开跑之前**那份名单，逐字列出；② 两轮 query 各自的原文与请求的 top-k；③ 该轮返回的全部名字，逐个列出（口径：结果标题里**属于第 1 步那个品类**的产品 / 项目专名，聚合类文章按它列出的条目展开；不同品类的专名单独记一行"越界命中"，它们不计入下面的判据，但**连着出现就是换轴换过头的信号**——那一轮的品类已经漂走，不作数）。收敛判据：③ 里有 ① 之外的名字就再来一轮；③ 非空而全落在 ① 内，才算**品类内**收敛；③ 为空是仪器没响，不作数。

     报数字不行，三处都在数字上失守：不冻结 ①，跑完把认得的名字追认进去就得 0；不报 top-k，第二轮压到 3 条也得 0（本条自己的实测正是"不在前 8 条"）；而"换没换轴"根本没有机械判据——按名字算交集时"交集小"与"新名多"是同一件事、不可能同真，按结果条目算又绕得开（两轮命中不同文章、列着同一批产品）。名字与 query 都摆在结论里，这三种失败就是**可见**的，虽然不是被自动检出的。这也正是下面那条「先断言被检对象的**数量非零**」要的分母，与上面那条「阴性对照要选对施扰的轴」要的轴。

  **第 2 步不覆盖品类那一轴**：它在已选定的品类内收敛，品类错时照样收敛，给一份错名单发完整性证书。第 1 步的引文只证明你读了定义，不证明由它推出的品类是对的——要覆盖这一轴，得在报出品类时先写下"按这个品类，名单里应当出现 `X`"，`X` 没出现就是品类或检索有问题。`X` 要同时满足三条才有信息量：**来源在本次检索之外**（领域常识、用户给的、另一份文档）、**写在那一轮开跑之前**、且**当前名单里还没有它**——否则挑一个已经看见的名字，这条检查恒真。一个 `X` 都提不出来本身就是读数（说明这个品类不预言任何名单外的东西），不是免检。存在**权威全集**时（厂商文档列全的 region、规范列全的 mode、仓内某目录下的全部实现）直接用那份全集，它比上面整套都强，此时本条只用来核对全集本身选对了品类没有。

  实测：为一个自称 "data lineage"、实为 ML artifact 血缘的服务找可参考的商业产品，写死候选名的那一串返回了自洽但错的品类；改用该仓 README 自己的定义（"哪个模型由哪批数据、经哪次运行产出"）后品类换对（MLflow / Comet）——而真正的头部产品 W&B 仍不在前 8 条，直到品类内再枚举一轮才出现。注意这个例子里"品类错了"是靠人读 README 发现的，不是靠任何读数报出来的——这正是上一段说第 2 步不覆盖那一轴的原因。

  **这套处方自己跑过一次对照，结果是它报了失败**（同一个案例）：品类取 "ML artifact / run lineage tracking"，`X` 预言 `Kubeflow Metadata`，第二轮把 query 从产品品类描述换成使用场景描述。读数——top-k=10，返回的同品类专名只有 `Databricks`（已在名单内），另有 `Augment Code`、`Microsoft Teams` 两个越界命中，而 **`X` 没出现**。判据据此拒收那一轮，诊断也对得上：那句 query 换轴换过头，漂到了 audit / governance 这个相邻品类，返回的是合规指南与银行监管文章。**"越界命中"这一格就是这次实测加上去的**——没有它，那两个专名会被算成"新名字"而逼出一轮无用的重跑。
- **你消费的任何报告里那句「未核实」，是派给你的活，不是给你的免责声明。** 探针自打的「不覆盖」行、子代理返回的「未核实 / 我这一侧够不着」、工具的告警行——产出方不同，形状同一个：一句诚实的自报缺口，读起来像"已披露、可以往下走了"。**判据不看它是谁写的**，看你能不能走一遍那条通道（判据见下面「够不着才退」）。三个出口，各自要在交付物里留下**不同**的东西：

  | 情形 | 出口 | 交付物里留下 |
  |---|---|---|
  | 你自己走得了 | 去走完 | 那条通道上取到的读数 |
  | 确实走不了（无凭据、需真实设备、消费者尚不存在） | 降级 | **你试了什么、撞上了什么**——命令 / 请求及其回应 |
  | 感知轴（要人耳人眼判定），或做完它的成本该由用户拍 | 交用户 | 按下面「通道是感知性的」摆机械事实 + 可抽查样本；成本按 `CLAUDE.md`「Surface Choices」问他 |

  第二行那句"试了什么"是承重的，不是格式要求：**裸一句「未核实 + 差在哪一层」在"确实走不了"与"走得了却没走"两种情况下逐字相同**——而后者正是本条要抓的那次事故。同一道理下面 `n/a(<形态>)` 那条已经用过一次。**抄进交付物同样不算处置**：CHANGELOG 的"已知限制"、报告的免责段、commit message 里那句坦白，是它最容易伪装成已处置的形态——写下来那个动作，感觉上等价于消化掉它。**子代理的返回尤其容易停在这里**，caller 侧的义务写在 `delegation-policy.md`「Return contract」里「未验证边界与不确定性」那条旁边，别只读上半。实测两例：一次探针自打的「不覆盖」行正好点名了当轮漏掉的那一层，被读成免责声明（`HARNESS-302`）；一次四位评审者各自写下"没有实跑过一次、我这一侧够不着"，caller 把它抄进 CHANGELOG 的「已知限制」就提交了——随后补跑，那条规则当场报出失败，并暴露一个四轮纯文本评审都没发现的缺陷。
- 取证命令的输出会原样进入 transcript、日志和工件，因此凡回显配置、环境或远端状态的读取都先假定它带值输出——`tcb fn detail`、`vercel env`、`env | grep`、`ps eww`，以及 `${VAR:-…}` 这类在变量已设置时展开成值的 shell 构造。只需要存在性时用只产出布尔或计数的写法（`[ -n "$V" ] && echo set`、`grep -c`）；确实需要值时也不整份回显——先取只含名字的脱敏清单（如 `sed -n 's/=.*/=<set>/p'`，`-n`+`p` 不可省：不带它们时多行值的续行不发生替换、被原样放行），再单独取需要的那几个值（能落盘或直接注入下游命令的就不回显进对话）。落盘副本可以事后清除，已进入对话的凭据不能撤回，只能轮换。
- 自己写的机制不要让失败与成功同形。读不到输入就放行、取不到值就返回空串、探测不到就当通过——这类 fail-open 在事后看和"检查通过"完全一样，于是没人会去查。拿不到判断依据时，要么报错，要么把"未能判断"作为一个与通过不同的可观察状态输出。**当场敲的取证命令同样在此列**，它不因为是一次性的就免检：管道的退出码只来自最后一段，`cmd | tail && next` 在 `cmd` 失败时与成功逐字同形，于是 `next` 照跑、其输出被读成对 `cmd` 的确认。要凭退出码判定就用 `set -o pipefail` / `PIPESTATUS`，或把截断与判定拆成两步。**输入为空、循环零次迭代，也会让"没查"打印出与"查过且干净"逐字相同的结果**：变量名写错取到空串后被跳过、列表拆分在当前 shell 下语法不成立于是一次都没进循环——这两种情形下末尾那句 `0 hits` / `全部通过` 与真跑过一遍完全一样。凡是要靠"零命中"下结论的，先断言被检对象的**数量非零**（取到几个键、迭代了几次、实际执行到几条断言），再报结果；这个计数本身也要打印出来，否则下一个读的人同样分不出两种情形。**你自己搭的判定装置（变异对照、探针、桩）也在这条之内**：它中途被掀翻（`set -e` 撞上一条非零返回、被信号杀）时留下的读数与"跑完了、断言没响"逐字相同，于是结论会写成"这条断言没有区分度"或"这段代码是死的"——归咎被测对象，而坏的是装置；**装置自己的退出码**因此也要进输出。同理，工具自身报的「成功」只覆盖它负责的那一段——入队成功不等于被读到，写入成功不等于写对了地方；**它的成功回执在你关心的那件事成立与否两种情况下若取值相同，那就不是证据**。同形的还有取证现场本身：多棵工作树并存时，跑错树的读数与跑对树的逐字同形——取证前的 cwd 自证见 `concurrent-plan-isolation.md`「代码层的块内 cwd 自证」。**本地端口是这条同形律最常见的一种冒名**：`ssh -L <本地端口>:…` 若那个端口已被别的东西占着，转发会失败或被挤掉，而随后的 `curl` 照样 200、照样返回一份看着合理的内容——那是旧实例、另一个服务或另一个 session 的响应，传输层全绿。实测：本机 8848 上早有一个旧实例在听，据它读到的旧内容差一步就被写成「部署没生效」。三条 invariant（**只约束要保证什么，不规定用哪个实现**——`ControlMaster` 复用时正确的 listener 可能由既有 master 持有，把「pid 必须是刚起的那个」当必备条件会把对的隧道判错）：**转发创建失败必须可观察**（如 `-o ExitOnForwardFailure=yes`，别让它静默退化）；**listener 归属要与本次转发方式一致**（新建就核新进程持有，复用就核那个 master 是指向本次目标的）；**响应必须带能区分目标的身份读数**——版本号、commit、构建标记、内容 sha，任何在「旧的」与「新的」之间取值不同的字段，不能只看状态码。同族的冒名者还有代理、缓存与复用的 socket；网页交付路径另有更严的一份（`remote-web-delivery.md`），本条覆盖它不会加载的纯 operator 侧取证隧道。
- **完成断言的观察通道由交付物的消费者决定，不由哪个读数更好取决定。** 先答两问：这件事做完了给谁用？他通过什么看到它？答案就是取证通道。前两问答对之后还有第三问：**我手上这份，与消费者读的那一份，是不是同一个可寻址位置**（同一 URL、同一次部署、同一台机器上的同一条路径）？前两问定的是通道的层，这一问定的是它的身份——层对而身份错的读数与正确的完全同形：同 schema、同集合、同路径族的另一个快照，逐字执行前两问都会返回通过。问的是查得到的位置事实，不是"有没有第二份候选"那种主观穷举——后者把触发权交给了正在被检验的那个判断，而误置的人恰恰没产生过"还有另一份"这个念头；**判不准就按"不是同一个"处理**。不是同一个位置时：**消费者那端能直接给出你要断言的那个量，就直接读它**（那既短又强）；够不着结论量时才退到身份读数——从消费者那一端独立再取一次（build commit、track digest、内容 sha，即上面隧道那条 invariant 写过的那一类，射程不止于端口冒名），与手上这份平账。只报自己这一侧的 sha 不算，它在"比过"与"没比"两种情况下逐字相同——`evaluation-integrity.md`「身份读数怎么写」把这个形态叫「镜像写入：两槽填同一次读取的值」并机械拦下，评测语境按那份更严的走。确认是同一个位置**、且中间没有可能替换响应的一层**（端口转发、代理、缓存、复用的 socket）时，答一句即可，不必产出 digest；有那类中间层时"同一个位置"不算数——位置同一不蕴含内容同一，回到上面隧道那条 invariant（本机 8848 上蹲着旧实例那次，URL 完全没变）。实测代价：一次覆盖率比较三次读的是打分原始产物而不是线上池（同 clip 集合，只差事后合并的那几层，而那几层恰好是覆盖率的来源），三次各自自洽、全部错，当天主线工作未给页面增加任何此前没有的覆盖；翻案靠的正是从消费者那端又取了一次——直连页面自己的 API（读数见 `~/private-project-a` 仓内 `docs/issues.md`「再订正（第三次，也是最要紧的一次）」）。上游读数与下游属性之间每多一层变换，就多一处它们可以不一致的地方——实测：API 返回"每条 23 个指标键"与页面上"123 条一个数都没有"同时为真，因为**键在值为 null 时存在**。**与上一条的分工**：上一条怀疑的是**仪器**（这个检查报得出相反结局吗），本条怀疑的是通道的**层与身份**（我读的是不是消费者读的那一份）；两条都该过的场合，本条通常先拦住。替身是**分层**的——破掉一层（行数→值非空）会产生"我已经严谨过了"的满足感，而下一层（文件→渲染页面）照样漏，实测对照组 4/6 正是停在这里。**"渲染页面"也不是最后一层**：实测再往下还有一层——一轮交付里 28 个 `<video>` 全在 DOM 里（`.mcard`=28、`not_synced`=0、112 个数值读数全部正常），而它们被祖先的 `overflow:hidden` 整块裁掉、用户一个也看不见；页面自己的 `IntersectionObserver` 因同一原因永不触发，`src` 从未挂上。**DOM 查询是站在消费者通道上量的替身**，而且是最难自觉的一层：浏览器已经打开、查询的也确实是真实 DOM。判据要换成用户那一侧成立的量——经全部祖先裁剪后与视口的实际相交、媒体的 `readyState`（测法见 `web-ui-observation.md`「测量技术」）。

  **前两问的主语是交付物本身，不是本轮改动**（第三问的主语不同——是你手上那份读数的**来源**）——上面那次失守的清单正是这样跑偏的：那一轮的工作是修指标绑定，于是验收只验指标同步，而那个页面的用途是"浏览评测集＝看视频"，视频一条没验。改动是你带进来的视角，用途是消费者的视角；照前者列清单，漏掉的恰好是他打开后第一件要做的事。
  - **交付一个用户会打开的页面时，报告正文必须带该 URL 的验收读数行**——形如 `page-acceptance <url> --expect 'video=28@ready>=2' → ever_intersected 28/28, ready_ok 28/28, errored 0`（`~/.claude/bin/page-acceptance`，它把上面那层替身变成一条机械读数）。`--expect` 要写的是**这一页的主功能元素**，由用途决定，不由本轮改动决定。这条约束的强制力来自读者：**缺了这行、或行里的 URL 与你交出去的对不上，用户一眼可见**——这是把"我可能忘了查"从静默失败改成可见缺失，而不是又一条只能靠自觉的规矩（它确实**不是**机械闸：无人阻止你不写，正因如此才要让它的缺席显形）。跑不了探针的场景（生产 URL 不得被滚动扫描打扰、页面需登录态等）改为写一行降级声明，说明未核实与差在哪一层。
  - **交付的页面用途是"人读到结果"时**，探针打印的「不覆盖」按上面「你消费的任何报告里那句『未核实』」那条处置——这一页要落进待办的具体是哪些项：**"探针全绿而读者看不见"的那些**，遮挡、透明度、visibility 与关系层对齐同属此类（同行的可读性归下面「别把可读性归成"打磨"」那条，感知质量归「通道是感知性的」那条，两者都不按待办处置；「内容对读者有没有用」归下面「`内容对读者有没有用` 也要有一格」那条；`可操作性` 与「多状态真实使用」由探针自己的 `NOT_COVERED_OWNERS` 判给 `test-ux`，不进本条的待办；探针也会打印「响应（点下去到画面更新等了多久）」，它归下面那一格、同样不进本条的待办）。探针覆盖的是存在与就绪，而这些与功能同级：读者要的东西离他几屏、进入时的那一屏装得下几条完整的、要被并排比较的两个对象共不共基线、渲染内容与它的盒子是否一致、每个区域里有多少在承载内容、以及元素有没有被盖住或透明掉（本枚举里不适用于这一页的项写 `n/a(<这一页的主内容形态>)`，别硬填也别留空——裸一个 `n/a` 在"确实不适用"与"没量"两种情况下同形）——任一不成立页面就没做到它被建出来要做的事，而它们在探针读数上**全部与正常同形**。所以**与验收读数行（或它跑不了时的降级声明）同段**再写一句 `可见性与关系层：<各一句读数>` 或 `可见性与关系层：未核实（<差在哪一项>）`——缺了这半句与缺验收行一样一眼可见，理由同上一条。**探针跑不了不等于这一层跑不了**：「离几屏」与「一屏装得下几条」依赖进入时的视口（时点见 `web-ui-observation.md`「测量技术」表下那条脚注），其余几项不需要滚动。量法见 `web-ui-observation.md`「测量技术」。实测代价：CSS 写死的 `aspect-ratio` 与产品实际输出不符时逐条读数全绿、28 条片每条都带黑边，并排两个播放器顶边差 48px，第一个视频在 5.94 屏之外——三样都通过了验收行（数字见 `web-ui-observation.md`「测量技术」）。
  - **`内容对读者有没有用` 也要有一格**，紧接 `可见性与关系层` 写成 `内容对读者有没有用：<按该档第一条产出的，各一句>`——探针的 `NOT_COVERED_OWNERS` 已把它连同关系层一并判给 `web-ui-observation.md`（键作 `关系层对齐与内容`），缺的只是通用层交付行里的这个格子；而没有格子的那项就是这一步被跳过的那项：遮挡 / 透明 / 共基线 / 离几屏 / 盒子一致都有具体量法、读起来像"要测的东西"，这一项没有量法，于是被读成软要求。**要产出哪几样由该档「交付前的最低证据」的「一、以读者身份用一遍，并报出读到了什么、等了多久」定，本条不复述、也不限定条数**；它不因页面无参照而免除。这一格要在"页面对读者有用"与"没用"两种情况下取值不同。走不通时按上面「三个出口」的同一形状写 `内容对读者有没有用：未核实（试了什么 / 撞上了什么）`。**该档另有一个面在这一格的判据下取值不变，因而要单独一格**：响应（点下去到画面更新之间等了多久）——顺滑与卡一秒半两种情况下，"内容对读者有没有用"的答案完全相同。写成 `点下去等了多久：<各操作的秒数，冷热各一次并写明是第几次>`（与该档「测量技术」同措辞——冷热差本身就是决定性读数，实测同一路径 2.5×），无可点元素的页面写 `n/a(静态页)` 并补一个首屏可读时刻的读数；判据是它在"顺滑"与"卡一秒半"两种情况下取值不同。**实测代价**：一次交付里 curl 验到了 HTML 正文与 `app.js`，而 `chart.umd.min.js` 是 404、三个图表面板整片空白——空 `<canvas>` 存在、可见、不被遮挡、盒子也对，上面那份枚举**逐项通过**；作者的浏览器观察只截了首屏，于是自己也没看见。
  - **用途是"给人看"的页面，别把可读性归成"打磨"**——归错了它就不进验收项，这正是那次 `aspect-ratio` 黑边 / 顶边差 48px / 第一个视频在 5.94 屏之外的成因。判据用 `CLAUDE.md`「非功能属性不自行加码」那条：能否语义追溯到用户表达的目标**或约束、或本任务开始前已生效且适用于该环境的契约**（三者取一，缺了后两项会把本该算功能的重新判成非功能）。据此：可读性、答案可达性、并排对象的可比性属**功能**，不合格即交付物没做到它要做的事，不需要问用户；而可读之上的精致程度（字阶档数、圆角族、过渡时长）属非功能，按同一条规则测出来 surface 成 choice，不默默做也不默默跳过。
  - **够不着才退，而「够不着」要具体**：不是「需要账号」就算够不着——已有登录态的浏览器往往完全可达；判据是**此刻这条通道 executor 能不能实际走一遍**。确实走不了（无凭据、需真实设备、消费者尚不存在）时退回上游读数，结论降级为「未核实 + 差在哪一层」。**断言同时指向多个消费者时，要么各自覆盖，要么把断言收窄到已覆盖的那一个**——只验其一却按全体断言，与上游替身是同一个错。 `plan-execution-principles.md` §verify 拆分 允许在下层验证（它同时服务「完整链路必须用户介入」与执行中的分段诊断，本条不与它冲突）：它管怎么拆，本条管**最终那个完成断言**用哪个观察面收口——链路不需用户介入、executor 自己能走完时，不走就是选了更好取的替身。
  - **通道是感知性的（要人耳/人眼判定）时**：口型对不对、声音自不自然、画面好不好看，这类属性没有等价的数值读数，executor 也走不了这条通道。此时**不得用数值代理冒充**——把能机械查的结构事实照常摆出来（媒体侧如容器声明时长与解码内容之差、PTS 断口的位置与累计秒数：实测一次交付里 6 处共 32.24 s 的断口本该是一等事实，却被当成工具口径问题解释掉了），再明说"感知轴未核实"，并把**待看的样本做成可直接播放对比的页面**交用户抽查（呈现形态按 `CLAUDE.md`「Present Multimodal Content for User Review」）。要不要为此做全量端到端，成本归用户——经 `AskUserQuestion` 让他定，别自己默默跳过、也别自己默默全做。自建的数值代理同样要按上面「据一次检查下结论前」那条的「施扰的轴要选对」做对照，音画同步探针那个反例就记在那里。
  - **owner 分工**：通用触发与 invariant 在 `CLAUDE.md`「取证的充分性」，方法在本文件；`web-ui-observation.md`（呈现形式与读者意义两面）与 `test-ux.md` §端到端真实使用（该 command 工作流）是**领域特化**、要求更严，不重复通用层判据。
