# Evidence Sufficiency

`CLAUDE.md`「取证的充分性」落到操作层的做法。

**什么时候读**：准备跑一条命令去确认某件事、或准备把某次检查的输出当成结论写给用户之前——诊断、排障、验证、review、核实一条事实主张都算，不限于写代码。判不准算不算时按适用处理。

这些条目此前住在 `coding-guidelines.md`；那个文件名让人在非编码相位直接判定它不适用，而这几条恰恰在那个相位最常失守。

- 证据要在结论宣称成立的环境里取得：当前 shell、venv 等既存状态是结论的隐藏前提，不是"干净环境 / 全新安装 / 换台机器"的证据。同理，**已在运行的进程**带的是它启动那一刻的环境与代码，而修复常靠"下次启动时加载"生效——"修复已提交"因此不等于"修复已生效"。要断言某个跑着的东西已被修好，证据得取自那个进程（启动时间晚于修复，或直接观察它的当前行为），不是取自仓库；长寿的 tmux pane、daemon、worker 能带着过期环境跑上数天而毫无征兆。
- 据一次检查下结论前，先证明这个仪器报得出**相反**的结局：它报失败 / 空 / null 时，跑一次阳性对照（已知良好条件下它确实报成功）；它报通过时，跑一次阴性对照（预期失败时它确实报失败）。两个方向都有各自的骗法：探针有 bug、读取窗口太小、请求被代理拦截会让健康的对象呈现为坏的；而两种结局下都相同的恒定读数（典型是观测手段自己进了被观测集合）会让坏的呈现为好的。多个本应独立的字段同时为空时，先把"仪器或 scope 取错"当作待证伪的假设，再读成缺陷加剧——但它只是假设：确实存在整片同时为空的真故障。
- 取证命令的输出会原样进入 transcript、日志和工件，因此凡回显配置、环境或远端状态的读取都先假定它带值输出——`tcb fn detail`、`vercel env`、`env | grep`、`ps eww`，以及 `${VAR:-…}` 这类在变量已设置时展开成值的 shell 构造。只需要存在性时用只产出布尔或计数的写法（`[ -n "$V" ] && echo set`、`grep -c`）。落盘副本可以事后清除，已进入对话的凭据不能撤回，只能轮换。
- 自己写的机制不要让失败与成功同形。读不到输入就放行、取不到值就返回空串、探测不到就当通过——这类 fail-open 在事后看和"检查通过"完全一样，于是没人会去查。拿不到判断依据时，要么报错，要么把"未能判断"作为一个与通过不同的可观察状态输出。**当场敲的取证命令同样在此列**，它不因为是一次性的就免检：管道的退出码只来自最后一段，`cmd | tail && next` 在 `cmd` 失败时与成功逐字同形，于是 `next` 照跑、其输出被读成对 `cmd` 的确认。要凭退出码判定就用 `set -o pipefail` / `PIPESTATUS`，或把截断与判定拆成两步。**输入为空、循环零次迭代，也会让"没查"打印出与"查过且干净"逐字相同的结果**：变量名写错取到空串后被跳过、列表拆分在当前 shell 下语法不成立于是一次都没进循环——这两种情形下末尾那句 `0 hits` / `全部通过` 与真跑过一遍完全一样。凡是要靠"零命中"下结论的循环或扫描，先断言被检对象的**数量非零**（取到几个键、迭代了几次），再报结果；这个计数本身也要打印出来，否则下一个读的人同样分不出两种情形。同理，工具自身报的「成功」只覆盖它负责的那一段——入队成功不等于被读到，写入成功不等于写对了地方；**它的成功回执在你关心的那件事成立与否两种情况下若取值相同，那就不是证据**。
