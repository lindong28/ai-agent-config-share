# Concurrent Plan Isolation

多个决策者可能并发写同一个 repo 时，避免彼此的改动、测试、运行时状态互相污染。最常见的入口是多个 agent session 并发执行 plan（create-plan / execute-plan），开工前就位三层隔离；判过"独占"因而没上隔离的 session，出现反证时按「执行中提升」重判——"独占"是开工时的判断，不是此后不再复核的前提。

## 核心：结构性隔离 ≫ 冲突检测

"互相检测再避让"是弱机制——要持续互看、临场协调，谁忘了看就撞。**结构上不共享可变状态**，撞车就不可能发生；检测只用于 merge 前发现文件面重叠（未隔离时另见「执行中提升」）。

流程骨架：**开工前**就位（三层隔离默认全上 · 登记占用 · 检测文件面重叠）→ 执行（出现另一决策者的反证 → 按「执行中提升」重判）→ **完工清理**。

## 三层结构隔离（默认全上，不靠检测触发）

隔离恒常施加——不因"没检测到别的 session"就跳过；那正是要消灭的弱机制，且会踩穿下面的铁律。

| 层 | 隔离手段 | 铁律 |
|---|---|---|
| 代码 | 各自独立 git worktree | execute-plan 默认在独立 worktree 落地；plan 显式声明"单 session 独占"**且未被「执行中提升」的反证证伪**时才免；任务含必须在已部署主 checkout 上跑的验证步骤时，仅该步骤在主 checkout 执行（见下） |
| 可变运行时状态（生产 DB、数据文件、缓存、状态文件） | 开发/测试指向独立副本（`.backup`/`cp`，环境变量如 `*_DB` 指向副本） | 绝不在开发/测试中读写共享的生产实例 |
| 服务 / 端口 / 进程 | 起隔离实例 + 独立寻址（端口 / socket / 队列名 / 资源命名空间），不复用共享服务的寻址 | 绝不碰线上 / 共享服务 / 默认端口 / 生产部署目标 |

代码层的部署耦合豁免：经 symlink 从主 checkout 部署的仓库（`~/.zshrc -> <repo>/zshrc`、`~/.claude -> <repo>/claude` 一类）里，**验证步骤**读到的是主 checkout 那一份，在 worktree 中跑会静默地测到另一个文件、结论无效。豁免只覆盖这类验证步骤，不覆盖开发本身——开发照常可在独立 worktree 进行，只把 live 验证留在主 checkout。

副本不回 merge：数据 / schema 的最终变更通过代码 + migration merge 回 main、由部署对生产实例应用一次；副本只服务本地开发测试，用完即弃。

## 外部不可复制资源（协调型，非结构隔离）

共享 LLM API 配额、限流、单点账号等**无法各自复制**的资源，不能结构隔离，只能**协调**——登记占用 + 串行化，或分账号 / 分配额；绝不让并发测试耗尽对方所需的配额。这是上面三层"复制型默认全上"覆盖不到的一类，需显式协调。

## 轻量登记（只补最后一环：文件面重叠）

结构隔离挡住运行时冲突后，剩下唯一冲突是"两条线改了同一源文件、merge 回 main 撞"。用一个 repo 内 git-tracked 的共享登记（约定位置，如 `.claude/active-work.md`）补上：

- 开工前：追加一条——worktree 名、占用的运行时资源、大致改动的文件 / 目录面。
- 开工前先读它：与既有条目的文件面重叠 → 协调（分工、排序，或约定谁先 merge）。
- 完工：删除自己的条目。

强度=约定（agent 开工读、完工清）；hook 强制留二期——结构隔离已挡住绝大部分，登记只补文件面重叠这一小片。

## 开工前检测（plan 流程起步时）

1. `git worktree list` —— 有无其它活跃 worktree。
2. 读共享登记 —— 其它 session 声明的资源 / 文件面。
3. 三层隔离照常全上（与检测结果无关）。检测的唯一用途是发现**文件面重叠** → 按「轻量登记」节协调 merge。

## 执行中提升（开工时未隔离的 session）

上一节的检测挂在 plan 流程起步时。但"有第二个决策者在改这棵工作树"是**当前状态**，与 session 由什么流程启动、开工时上没上隔离都无关——任何判过"独占"的 session，出现反证时按本节重判。

**反证 lens：** 有没有不受本 session 控制的第二个决策者在改这棵工作树？判据是决策者而非写入者：hook / formatter 会写，但它们没有独立意图，不算。

| 反证 | 它证伪的是 | 后续按 |
|---|---|---|
| "文件被外部修改"的提示 | 同一棵工作树被共享 | 下方 1–3 条 |
| `git status` 出现本 session 开始后新出现、且非本轮编辑的改动 | 同一棵工作树被共享 | 下方 1–3 条 |
| 本工作树 `HEAD` reflog 出现本 session 未发起的 rebase / amend / reset | 同一棵工作树被共享 | 下方 1–3 条 |
| `git worktree list` 新增条目、共享登记新增条目、或分支 reflog（全 repo 共享）出现外来写入 | 只是同一 repo 被共享，代码层仍隔离 | 「开工前检测」与「轻量登记」的既有 merge 路径 |

`git status` 那条要的是 delta：开工前就存在的无关脏改动不算反证——保留它们是既有纪律。

判定成立后：

1. **文件内部重叠。** 共享一棵工作树时，"两条线改了同一源文件"当场就是现实，而不是留到 merge 才兑现（上面几节的 merge 时框架以**已上代码层隔离**为前提）。最隐蔽的形态是对方改的正是本轮也在改的文件：工作树里没有任何陌生文件可看，重叠只存在于文件内部——于是"我 stage 了哪些**文件**"这个粒度无法表达归属，该文件交用户。同理，作用面覆盖整棵树或整段历史的操作（`stash` / `reset` / `checkout --` / `commit -a` / `rebase` / `amend`）在此状态下不再只影响自己。
2. **对方的产物不由本 session 处置。** 对方尚未提交的改动、以及本 session 之外产生的 commit 与历史改写，交用户。例外是本 session 自己派生的写入者（subagent、后台 agent）——那是本 session 有权也有责任收回的，不推给用户。
3. **协调对手方必须也在协议内。** 「轻量登记」的协调力全部来自对方也读那份登记——对方也是按本协议工作的 agent session 时，补一条登记并按「轻量登记」协调；对方是人、外部工具或另一 harness 时该路径落空，此时按上一条交用户，而不是追加一条无人阅读的条目。
4. **代码层隔离是否可行按三层表判，不在此另立豁免。** 该层的部署耦合豁免见三层结构隔离节；不可行时留在原地并按上述三条约束写入。另两层（可变运行时状态、服务 / 端口）的铁律不因未隔离或中途提升而放松。

提升只是承认工作树已被共享，不追溯重做已完成的工作，也不扩大任务目标——但反证是历史改写时，先确认本 session 已完成的改动仍在。

## 与产品侧 singleton 规则的边界

本 protocol 管 agent session 的工作流隔离。产品代码里 singleton / 服务在多 checkout 下的 ownership 自保护（per-machine/fleet 声明、detect another clone、拒绝 unsafe overwrite）是产品运行时规则，由项目侧的 CLAUDE.md / 代码承载、本 protocol 不复刻。

## 完工清理

merge / 交付后按三层隔离与登记各自的完工步骤统一清理（worktree、副本、隔离实例、登记条目），避免 orphan。
