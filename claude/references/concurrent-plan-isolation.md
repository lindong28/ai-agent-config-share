# Concurrent Plan Isolation

多个决策者可能并发写同一个 repo 时，避免彼此的改动、测试、运行时状态互相污染。最常见的入口是多个 agent session 并发执行 plan（create-plan / execute-plan），开工前就位三层隔离；判过"独占"因而没上隔离的 session，出现反证时按「执行中提升」重判——"独占"是开工时的判断，不是此后不再复核的前提。

## 核心：结构性隔离 ≫ 冲突检测

"互相检测再避让"是弱机制——要持续互看、临场协调，谁忘了看就撞。**结构上不共享可变状态**，撞车就不可能发生；检测只用于 merge 前发现文件面重叠（未隔离时另见「执行中提升」）。

流程骨架：**开工前**就位（三层隔离默认全上 · 检测文件面重叠）→ 执行（写入者登记随实际写入累积；出现另一决策者的反证 → 按「执行中提升」重判）→ **完工清理**。

## 三层结构隔离（默认全上，不靠检测触发）

隔离恒常施加——不因"没检测到别的 session"就跳过；那正是要消灭的弱机制，且会踩穿下面的铁律。

| 层 | 隔离手段 | 铁律 |
|---|---|---|
| 代码 | 各自独立 git worktree | execute-plan 默认在独立 worktree 落地，**且 session 本身要进到那棵树里**——只落不进时，相对路径、`pwd` 派生的参数与编辑的默认落点仍指向主 checkout；plan 显式声明"单 session 独占"**且未被「执行中提升」的反证证伪**时才免；任务含必须在已部署主 checkout 上跑的验证步骤时，仅该步骤在主 checkout 执行（见下） |
| 可变运行时状态（生产 DB、数据文件、缓存、状态文件） | 开发/测试指向独立副本（`.backup`/`cp`，环境变量如 `*_DB` 指向副本） | 绝不在开发/测试中读写共享的生产实例 |
| 服务 / 端口 / 进程 | 起隔离实例 + 独立寻址（端口 / socket / 队列名 / 资源命名空间），不复用共享服务的寻址 | 绝不碰线上 / 共享服务 / 默认端口 / 生产部署目标 |

代码层的部署耦合豁免：经 symlink 从主 checkout 部署的仓库（`~/.zshrc -> <repo>/zshrc`、`~/.claude -> <repo>/claude` 一类）里，**验证步骤**读到的是主 checkout 那一份，在 worktree 中跑会静默地测到另一个文件、结论无效。豁免只覆盖这类验证步骤，不覆盖开发本身——开发照常可在独立 worktree 进行，只把 live 验证留在主 checkout。

副本不回 merge：数据 / schema 的最终变更通过代码 + migration merge 回 main、由部署对生产实例应用一次；副本只服务本地开发测试，用完即弃。

## 外部不可复制资源（协调型，非结构隔离）

共享 LLM API 配额、限流、单点账号、开发实例端口、共享 DB 文件等**无法各自复制**的资源，不能结构隔离，只能**协调**——登记占用 + 串行化，或分账号 / 分配额；绝不让并发测试耗尽对方所需的配额。这是上面三层"复制型默认全上"覆盖不到的一类，需显式协调。

登记落在与文件面同一个条目里（`node ~/.claude/hooks/writer-registry-gate.js claim "<资源>"`，Codex 侧手工写同一个 JSON 的 `resources` 字段）。**这一类必须显式声明**：文件面能从实际写入自动累积，占用进程外资源的行为从写入里推不出来。两者同条目而不是各起一份登记——两份登记就有两份生命周期，其中一份必然先被忘掉。

## 写入者登记（只补最后一环：文件面重叠）

结构隔离挡住运行时冲突后，剩下唯一冲突是"两条线改了同一源文件"。登记补上这一片。

**载体：`$(git rev-parse --path-format=absolute --git-common-dir)/agent-writers/<session-id>.json`，一个写入者一个文件。**（`--path-format=absolute` 不可省：不带它时 linked worktree 里返回的是 `../..` 这类相对 `$GIT_DIR` 的路径，按 cwd 拼接就会落到错误位置，跨 worktree 可见性当场失效——而那正是换这个载体的全部理由。） 三条属性都是被反例逼出来的，换任何一条都会退回它要解决的问题：

| 属性 | 为什么 | 换成别的会怎样 |
|---|---|---|
| 放 common-dir，不放工作树 | linked worktree 的 `$GIT_DIR` 各不相同，但 `commondir` 都指回主 `.git`，所以同一 repo 的所有 worktree 天然共享它 | 工作树内的文件每棵树各有一份，A 写的条目不 commit 就在 B 里看不见——而跨 worktree 协调正是登记的主要目标场景 |
| 一个写入者一个文件 | 并发追加互不相干 | 单文件共享登记表自己就成了下一个"两条线改同一文件" |
| 不进版本控制 | 它是运行期状态，不是代码 | commit 噪声，且会被误提交进别人的改动 |

**登记的内容按实际写入累积，不靠开工前声明。** 每次编辑一个仓内文件时把它的 repo 相对路径记进自己的条目（连同 session id、所属 agent 进程的 pid、所在 worktree）。开工前预测"大致会改哪些文件"产出的清单必然既不全又过时，而重叠判据建在不准的清单上就是既漏拦又误拦。

**重叠判据两条同时成立**：目标文件的 **repo 相对路径**与某个活写入者的条目相同（相对路径而非绝对路径，跨 worktree 的同一文件才对得上），**且**该写入者的工作树里那个文件确有未提交改动。第二条不可省：登记的语义是"我在这个文件上有会丢的 WIP"，已经提交的文件上没有可丢的东西，再拦就是纯误拦——长跑 session 提交完继续待命是常态，少了它会无限期占住别人要改的文件。

**判定重叠时停下，把冲突交用户，取得授权才写。** 依据是「执行中提升」条 1：共享工作树下"我改了哪些**文件**"这个粒度无法表达归属，该文件交用户。不得自行判定"应该不冲突"就继续——agent 自评正是这条防线要挡的那一环。

**授权按文件计，不按处境计。** 提问粒度是文件，答案的效力也是文件：同一批冲突涉及多个文件时在提问里逐一列出，之后每出现一个新文件就是一次新授权，不得由既有授权外推。理由与上一句同源——外推所依据的"这两个文件情况一样"正是 agent 自评，而这道防线要挡的就是它。外推前若去核实了对方工作树、恰好没冲突，那份安全来自那次核实，不来自那次授权；下一次对方 WIP 还在时，同样的外推直接覆盖掉别人未提交的改动。

**死条目靠 pid 活性回收，不靠谁记得清理。** 读登记时对每个条目验一次进程活性，死的就地删除。指望退出时清理是靠不住的：崩溃、被 kill、断网时那段代码根本不会跑，而那恰恰是唯一会留下死条目的场景。反过来说，**活着就一直占**是对的语义——session 还在、WIP 还在，占用就还成立，不因为"这一轮说完了"而释放。

条目形状（两侧同一份，Codex 侧手工维护时照此写）：

```json
{ "session_id": "<本 session id>", "pid": <本 agent 进程 pid>,
  "pid_fingerprint": "<`ps -o lstart=,comm= -p <pid>` 的输出>", "worktree": "<绝对路径>",
  "started_at": "<ISO>", "files": ["repo/相对/路径"], "claimed_at": {"repo/相对/路径": "<ISO>"},
  "resources": ["port 39011"] }
```

`pid_fingerprint` 不可省：本机 pid 已实测会回绕，死 session 的 pid 被无关进程接手后，只看 pid 会让它的占用**永远**显示为活的——条目不再回收，那些文件上的声明永远无法证伪。指纹与 `pid` 必须成对更新（只换一个，要么条目立刻自判死，要么防护形同虚设）。

`files` 用 **repo 相对路径**，且先经 realpath 归一（解掉 symlink 与大小写别名，否则同一文件会产生两个对不上的键）。目标落在嵌套仓 / submodule 内时，登记要落到**那个仓**的 common-dir——父仓的 `git status` 只报告 submodule 根目录变脏、不报告其内部文件，登在父仓则 dirty 判据永远落空。`pid` 取 agent 进程自己的（不是某次工具调用的短命子进程，否则条目一写下就是死的）。整份覆盖写回时必须带全既有字段，漏一个就等于悄悄撤销了一条仍生效的声明。

强度分 harness：**Claude Code 侧由 `claude/hooks/writer-registry-gate.js` 在每次 Edit / Write 前强制**（拦截 + 自动登记 + 回收死条目 + 读-改-写加锁），用户授权后经该脚本的 `grant` 子命令放行单个文件。**Codex 侧没有 hook 机制，以上全部按本节声明式规则手工执行**——这也是本节把判据与条目形状写全、而不是指向实现的原因：两侧必须遵守的 invariant 不能只活在 hook 实现里。

条目里的 `worktree` 是登记那一刻的**路径快照**，session 存活期间 repo 被改名 / 移动后它就失效。此时不要据此下任何结论——向那个活进程问它当前的 cwd（`lsof -a -p <pid> -d cwd -Fn`），那是改名后仍然正确的唯一来源。三种偷懒做法各有真代价：当冲突 → 永久误拦（声明永远无法证伪）；删条目 → 漏拦（对方还活着、WIP 还在）；直接跳过 → 本次仍漏拦。

已知残余（都是**协调机制而非互斥锁**的体现——它把并发写同一文件的概率压到很低，不提供"绝不可能"）：

| 残余 | 何时出现 | 后果 |
|---|---|---|
| 登记-写入窗口 | 登记已落、真实写入未落的毫秒级间隙里，对方看到的文件仍是干净的 | `claimed_at` 的新鲜期盖住它（新登记的声明即使文件还干净也算数）；代价是失败的、或内容无变化的编辑会在该窗口内造成一次假冲突 |
| 路径快照失效且活进程 cwd 也问不出来 | lsof 不可用、进程刚退出、cwd 已不在任何仓内 | 放行（不拦也不删条目）——这一格是明知的漏拦面，因为拦会造成无法解开的死结 |
| 对手方查询预算耗尽 | 对手方分属很多棵树、其中若干在慢盘或失联挂载点上 | 未核实的声明按**冲突**处理：超时状态下宁可误拦（用户授权那条出路可用），不可漏拦 |
| 拿不到锁 | 等待超过锁等待上限（该上限已设得高于对手方查询预算，所以合法的慢查询不会触发它——需要持锁进程被挂起一类异常） | 退回无锁写，判定-登记竞态重现；不因锁本身把编辑卡死 |
| 跨 registry 的一次调用部分登记 | 单次 MultiEdit 同时改父仓与 submodule 内的文件，且后处理的那个仓有冲突 | 前一个仓已登记的占用留了下来（那些文件其实没写）。判定与登记的原子性只在**单个 registry 内**成立——跨仓要嵌套持有多把锁，引入的死锁风险大于它挡住的这个罕见场景 |

## 开工前检测（plan 流程起步时）

1. `git worktree list` —— 有无其它活跃 worktree。
2. 读写入者登记 —— 其它活写入者已占用的文件面（含外部不可复制资源的占用声明，那部分仍靠显式登记，不由写入自动产生）。
3. 三层隔离照常全上（与检测结果无关）。检测的唯一用途是发现**文件面重叠** → 按「写入者登记」节处置。

## 执行中提升（开工时未隔离的 session）

上一节的检测挂在 plan 流程起步时。但"有第二个决策者在改这棵工作树"是**当前状态**，与 session 由什么流程启动、开工时上没上隔离都无关——任何判过"独占"的 session，出现反证时按本节重判。

**反证 lens：** 有没有不受本 session 控制的第二个决策者在改这棵工作树？判据是决策者而非写入者：hook / formatter 会写，但它们没有独立意图，不算。

| 反证 | 它证伪的是 | 后续按 |
|---|---|---|
| "文件被外部修改"的提示 | 同一棵工作树被共享 | 下方各条 |
| `git status` 出现本 session 开始后新出现、且非本轮编辑的改动 | 同一棵工作树被共享 | 下方各条 |
| 本工作树 `HEAD` reflog 出现本 session 未发起的 rebase / amend / reset | 同一棵工作树被共享 | 下方各条 |
| `git worktree list` 新增条目、写入者登记新增条目、或分支 reflog（全 repo 共享）出现外来写入 | 只是同一 repo 被共享，代码层仍隔离 | 「开工前检测」与「写入者登记」的既有 merge 路径；另按下方第 5 条（该条只需 repo 共享即成立） |

`git status` 那条要的是 delta：开工前就存在的无关脏改动不算反证——保留它们是既有纪律。

判定成立后：

1. **文件内部重叠。** 共享一棵工作树时，"两条线改了同一源文件"当场就是现实，而不是留到 merge 才兑现（上面几节的 merge 时框架以**已上代码层隔离**为前提）。最隐蔽的形态是对方改的正是本轮也在改的文件：工作树里没有任何陌生文件可看，重叠只存在于文件内部——于是"我 stage 了哪些**文件**"这个粒度无法表达归属，该文件交用户。用户选择按行归属时，注意 index 存的是整份文件内容而非 delta：写进去的那份会回退掉对方在该文件上尚未提交的改动，故须以 HEAD 加本 session 的改动重建。同理，作用面覆盖整棵树或整段历史的操作（`stash` / `reset` / `checkout --` / `commit -a` / `rebase` / `amend`）在此状态下不再只影响自己。**不带路径的 `git commit` 也在此列**，而且是其中最容易漏掉的一个：它前面通常紧跟着一次 `git add <具体文件>`，看起来已经被限定过，实际落的是整个索引——对方 stage 了什么就一并带走什么。补救措施归 `create-commit` skill（CLAUDE.md 指定它单一维护 staging 纪律），但**注意它与本条上面的按行归属流程不兼容**：那个流程要求重建索引，而按路径限定 commit 的写法取的是工作树内容、会把重建的那份丢掉。两者同时需要时，先把重建后的内容写回工作树再提交。
2. **对方的产物不由本 session 处置。** 对方尚未提交的改动、以及本 session 之外产生的 commit 与历史改写，交用户。例外是本 session 自己派生的写入者（subagent、后台 agent）——那是本 session 有权也有责任收回的，不推给用户。
3. **登记只看得见在协议内的对手方。** 登记与拦截保护的是"我不覆盖已登记的写入者"，而对方**出现在登记里**的前提是它也按本协议工作（Claude Code 侧由 hook 自动登记，Codex 侧手工登记）。对方是人、外部工具或另一 harness 时它根本不会登记，于是拦截静默失效——**登记不响不等于没有并发写入者**，本节的反证 lens 才是那种情形下唯一的信号，按上一条交用户。
4. **代码层隔离是否可行按三层表判，不在此另立豁免。** 该层的部署耦合豁免见三层结构隔离节；不可行时留在原地并按上述三条写入约束落地。另两层（可变运行时状态、服务 / 端口）的铁律不因未隔离或中途提升而放松。
5. **共享分支 tip 是对方的发布面。** 本 session 不 push 只保证自己没发布，不保证内容没被发布——commit 落在共享的本地 `main` / `master` 后，对方随时会连同它一并推走，而 `~/.claude/CLAUDE.md`「Git Push 需显式许可」是第一人称禁令、约束不到对方。本条只需 repo 被共享即成立（含反证表第 4 行那类代码层仍隔离、只是同一 repo 的情形），不以共享同一棵工作树为前提。故 commit 到共享分支前，先把这一后果告知用户并由其定落点（共享 tip / 只有本 session 会推的侧分支 / 暂不 commit）；仓库未公开或含凭据时，共享 tip 不得作为推荐项呈现。侧分支最终经同文件「分支改动整合回本地 main/master 需显式许可」回到 main，那一步的整合许可同样要带上这层后果。

提升只是承认工作树已被共享，不追溯重做已完成的工作，也不扩大任务目标——但本 session 已完成的改动是否仍在，不止在发现历史改写反证时确认——交付报告前还要再确认一次，且确认的是改动的**内容**仍在当前 HEAD 上，不是原 commit 对象还在祖先链上（对方 squash / rebase 会换掉 commit 身份却完整保留内容，按身份判会误报丢失）。对方的 reset / rebase 可能就发生在你最后一次观察之后，只在察觉反证时确认，会让交付报告在写下之后才变成假的。

## 与产品侧 singleton 规则的边界

本 protocol 管 agent session 的工作流隔离。产品代码里 singleton / 服务在多 checkout 下的 ownership 自保护（per-machine/fleet 声明、detect another clone、拒绝 unsafe overwrite）是产品运行时规则，由项目侧的 CLAUDE.md / 代码承载、本 protocol 不复刻。

## 完工清理

merge / 交付后按三层隔离各自的完工步骤统一清理（worktree、副本、隔离实例），避免 orphan。写入者登记条目不在此列——它按 pid 活性回收，session 还活着就该继续占用（理由见「写入者登记」末条）；手工删自己的条目只会让还没提交的 WIP 对别人隐身。曾进入「执行中提升」的 session，交付报告前还欠该节末尾那次改动存活性确认。
