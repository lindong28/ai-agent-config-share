# CLI Output Review Principles

面向人的终端输出——CLI 命令、安装器、部署 / 迁移脚本、CI job——的质量判据。

**核心立场**：把终端输出当作**用户状态界面**审，而不是把"日志里存在相关文字"当成可读。读者应能直接判断发生了什么，不必从原始 JSON、子进程噪声或实现知识中推理。

**这套判据的消费方式**：写或改这类输出前读（别等事后审）；审查时逐条对照 P1–P7，循环到无违反为止。审核并修复既有输出用 `/custom:review-cli-output`。

**配套档**：消息内容的通道无关判据在 `human-facing-message-principles.md`（自解释 / 结论作用域 / 主视图按决策相关性组织 / 值的呈现服从决策用途）——**本档与该档一起读**，本档只承载终端输出特有的部分：读者归属、骨架分流、状态词与退出码契约、以及 capture 取自哪一份。

## P0. 读者情境与视图分段（先于骨架，对所有输出类型成立）

该档「先定读者情境」对本类输出的归档，沿用它的结构性谓词、不放宽：**只有阻塞等待用户应答的提示、必须当场处置的确认算"在手"；其余终端输出一律按"不在手"**，须完全自解释——手敲命令的即时输出也在内（打完就返回，输出留在 scrollback，半小时后翻回来或被粘进 issue 时读者手里已无上下文），CI job、无人值守的部署 / 迁移脚本、被转发的失败日志同理。用途这一轴**键在该视图自身要支持什么判断上**——不在命令名、flag 名，也不在"是不是默认视图"上：`status --verbose` 会同时命中"`status` → triage"与"verbose → 诊断"，而 `bench` / `debug` 子命令的**默认视图本身就是**测量输出，按"默认 → triage"又会归错。判法：该视图承载**状态结论**（还能不能用、要不要动手）→ **triage**，只在实现内部有意义的量该下沉；该视图本身是**测量 / 排障产物**（`--verbose`、`debug` 子命令、benchmark、`--format=kv` / `--json`，不论它是否为该命令的默认视图）→ **诊断 / 测量**，内部量不被剔除、分辨力按该产物要支持的判断定，但共享档 §1–§4 的其余要求与本档 P5、P6 照旧。

同一命令的不同视图分别定标尺。**未分段的混合体**（triage 结论与诊断 dump 交织、或结论被 dump 顶到后面）即**本段的一项 finding，不论输出类型**——它使两个标尺无法分别施加，因此不依赖 P3 / P4 任一骨架成立。

**不适用**：无人类读者的纯机器输出（被 hook / 脚本 / 日志管道独占消费）→ 按契约审，别强加可读性；GUI；一般文档与代码风格。

## 优先级

P0 先于一切：用途轴未判定、或输出是未分段混合体时，其余判据无法分别施加。其后 P1（读者归属没定，修复都可能因契约冲突落不了地）、P2（决定用哪套骨架），P3–P7 是具体判据。P7 管取证面，但它**不统辖其余各条**：判读者读到什么的（P3、P4、P6、共享档四条）以它选定的那一份为准；判生产端契约的（P5 的退出码与 stdout/stderr 分流）要直接运行那一份——实测一份被转发的 capture 上，P5 这两条的证据已经不在（退出码不随行，两路流交错后无归属）。两份都要时两份都取，各判各的。

共享档判据之间的裁决序由 `human-facing-message-principles.md`「裁决顺序」承载，本档不另立——否则同一冲突在 CLI 与 push 两个通道会得出不同结论。本档判据与共享档判据正面冲突时共享档胜；本档只收窄它，不反向放宽。

**逃生阀**：承接共享档「裁决顺序」的逃生阀（含纯审查场景的分支），本档不另述——否则同一机制会有两处需同步的裁决文本。

## P1. 先定读者：面向人的输出不得被机器格式占据主视野

**一条命令必须有显式选定的主读者。人是主读者时：默认输出是人类视图，机器格式退居显式 opt-in（`--format=kv` / `--json` / 环境变量）。**

**判定单位是命令的默认视图。**本条的 headline 与全部 flag 只施于默认视图——`--format=kv` / `--json` 这类 opt-in 视图正是本条要求达成的终态，对它套"主视图是 key=value"只会 flag 掉合规结果。

**已存在 machine consumer 不是保留现状的豁免理由，而是要 surface 的迁移成本**——列出消费者、给出迁移路径（机器格式移到 flag 后 + 同步更新消费者），交用户决策。让机器格式常驻默认 stdout，等于让每个人类读者替机器付账。

**唯一例外（本条整体不适用）**：契约**显式声明** stdout 归机器、stderr 归人，且 stderr 里的人类视图自身完整自解释——此时 stderr 就是主视图，人类读者没有替机器付账（详见 P5）。该例外优先于本条的 headline 与全部 flag，不只是下面的第二条；stderr 只有碎片时不成立，照本条 flag。

flag：
- 主视图是 `key=value` / JSON，人只能靠逐行扫它判断状态。
- 人话结论只在 stderr 或末行，机器格式抢占了主视野（例外见 P5 的 stdout/stderr 契约条：契约显式声明且 stderr 人类视图自身完整时不算）。
- 同一份 stdout 同时被要求"稳定 token 供解析"和"好读给人"——两个要求互相拖累，改一个必然伤另一个。
- "有脚本在解析它"被直接当成不改的结论，却没核实消费者是谁、是否真存在。

自检：这份输出的主读者是谁？若是人，他拿到结论要读几行、跳过多少不供他决策的字段？

## P2. 骨架分流：先判输出类型，再选审查骨架

| 输出类型 | 特征 | 骨架 |
|---|---|---|
| **action 型** | 改变系统状态：安装、部署、迁移、构建、CI job | P3 |
| **status 型** | 只读报告状态：health check、doctor、status、诊断 | P4 |

一条命令可同时具备两面（如 `status --repair`）→ **两套骨架都过**：修复动作按 P3 审，状态报告按 P4 审。别用一套骨架硬套另一半——把 status 输出套进 action 骨架会得到一堆退化的空问题（没有"未执行范围"、没有"部分成功"边界），真正的缺陷反而漏掉。

**两型都不落入时不套骨架**：查询 / 报告型输出（`list`、`show`、`search`、`diff`）既不改系统状态、也不报被检查维度的健康度，硬选一套只会得到退化的空答案——直接按共享档 §1–§4 与本档 P1、P5、P6 审。骨架是对这两类输出的补充入口，不是唯一入口。

## P3. action 型骨架：执行了什么、各自结果、整体收束、未执行范围

**"执行单元"**指用户认为可以独立成功、跳过或失败的功能动作（安装一个服务、更新一个组件）。单个 symlink、内部子进程或依赖命令只有在用户需要单独处置时才升为执行单元。

从输出本身还原执行单元与控制结果，回答：

1. 本次执行了什么、采用什么模式？
2. 哪些执行单元被尝试，各自最终结果是否明确？
3. 整体是成功、部分成功、失败还是被阻塞？
4. 若提前停止或部分成功，哪些既有结果保留、哪些单元未执行？
5. 对非成功结果，用户下一步该做什么？

对每个执行单元区分：**明确**（输出直接给出最终结果与必要上下文）/ **推断**（只能从过程日志、图标、JSON 或相邻文本猜测）/ **未知**（输出不足以判断）。

过程日志和诊断详情可以证明结果，但不能代替结果。检查信息层级、单元边界、整体收束和失败后的行动指引。

## P4. status 型骨架：结论在哪、四态可分、异常项可定位

读者跑一个 status 命令是为了回答"现在能不能用 / 要不要动手"。从输出本身回答：

1. 总体结论是什么、读者第一眼拿得到吗——还是要读完全部明细才在末行看到？
2. 每个被检查维度，**健康 / 降级 / 不可用 / 未测**四态是否可区分？（"未测"最常被塌缩进"健康"）
3. 非健康维度报的是**对用户的影响**还是内部状态名？下一步动作是否明确？
4. 结论的作用域是否与证据一致——本轮未取得阳性观测的维度，有没有被总体结论（**任何档位，不只是 OK**）覆盖而未声明不在覆盖内（共享档 §2）？
5. 正常项与异常项是否等权铺屏——读者能否不逐行扫就定位到需要注意的地方？

flag：
- 总体结论在最后一行，前面全是等权明细。
- 只有二态（ok / 不 ok），把"探测失败"和"探测到正常"合并。
- **人类视图**里的维度名是实现术语（`resource_health`、`route_health`），读者需要知道实现才懂它说的是哪一层。机器格式视图的 key 不按本条判——它们是 P5 的稳定 token，改名会破坏解析；命名问题只在其对应的人类视图上判。
- 同时暴露内部值与生效值（`stored_mode` + `effective_mode`）却不说明哪个现在生效、为何不同。
- 明细字段是给排障者的，却和结论字段同权同位、无主次。

## P5. 状态词、退出码与 stdout/stderr 分流自洽

修改前读取该输出的 controlling CLI contract；识别是否有 machine consumer，有则读其 contract。逐项对齐：

- **状态词语义一致**：同一结果不要在不同位置叫不同名字。
- **退出码与输出宣告的结论一致**：输出说 degraded 而退出 0 → 要么退出码错，要么"degraded 不算失败"这个语义必须写明。
- **stdout / stderr 分流有理由**：机器消费走 stdout、人类诊断走 stderr 是一种合法契约。此时 **stderr 就是人类读者的主视图**——共享档 §2「作用域声明不得低于结论的可见度」在此按 stderr 判，写在那里不算降权；这也是 P1「人话结论只在 stderr」那条 flag 的**例外**，成立条件是该契约被显式声明、且 stderr 里的人类视图自身完整自解释。碎片化的 stderr 仍按 P1 flag。
- **稳定 token 与展示措辞分离**：改措辞不应破坏解析。

契约 authority 缺失或歧义时，**停止**涉及这些语义的修复，交付审查结果与未核实项。存在兼容取舍时让用户决策；没有真实取舍的措辞、换行、分组和结果汇总直接改。

## P6. 区分「执行失败」与「输出没有诚实表达执行结果」，并保护已达标表达

- 产品真的失败了、输出如实报告 → 别把它改成看起来成功。但**诚实不豁免任何一条判据**——它诚实的只是"我这一步失败了"这件事，共享档与本档的其余义务照旧逐条过，下面两例是常撞的两条、不是全集：`ERROR: step 'migrate' exited with status 1` 如实，仍违反 P3 第 5 问与共享档 §1（没说影响、没有可执行的第一步）；一条 `usage: <用法>` 如实，仍违反共享档 §2（从未说读者要查的那个对象一次都没被查过，读者据此对它下了结论）。**注意这一类不会被"含不含结论"筛出来**——它们通常一个结论都没写。
- 产品成功 / 部分成功，但输出让人读不出来 → 这也是本档要修的。

同时保护做对了的地方——受保护对象与被禁动作的边界由共享档「保护已达标的表达」定义（受保护的是满足**全部**判据的表达，被禁的是仅为格式统一或判据字面对齐而重排）。终端输出侧另加两条：不要为统一外观引入日志框架；不要用最终 summary 掩盖过程中仍然含糊或相互矛盾的状态。形式服从内容，不强制所有程序使用同一组标签或模板。

## P7. Capture 取自读者实际读到的那条链路

自己跑一遍命令看到的输出，与读者拿到的那一份未必是同一份——中间常有转发方、日志采集、CI 面板、通知体。直接运行的读数在"读者收到了完整的话"与"他只收到其中一截"两种情形下相同，因此它证不了后者。

**Capture 取自读者实际读到的那个面**：组件输出经父进程转发时取转发后的那一份，进 CI 面板的取面板上那一份，被推送摘要的取推送里那一份。一条输出走几条链路就各取一份，它们常常不同。

实拍：根安装器只把子组件日志里匹配告警字样的行转发出去，于是一条两行 WARN 的第二行、也是唯一那句行动指引，在多数人走的那条路径上消失；直接跑子安装器则两行俱在，看不出问题。

丢失先判归属再修：转发方在本轮改动范围内就修它——把可修的转发缺陷固化成输出侧的迁就（给每行硬塞告警字样、把多行压成一行），会在不经它的那条路径上反过来伤 P3 / P4。

**链路不可达、或目标尚未部署时**，显式把这个缺口交决策者裁决（阻塞还是接受），不得静默跳过；接受时按直接运行的那一份审，并在结论里标注该判定未覆盖投递链路。这是证据取不到时的处置，与上面「逃生阀」承接的判据冲突裁决不是同一个机制，故各自成立——`schema-design-principles.md` §8 在数据契约通道上是同一形状。

flag：
- capture 由审查者自己运行目标取得，而读者的主路径经过转发或采集，两者未比对。
- 行动指引写在续行或次级面上，而该链路只取首行、只取匹配行、或按长度截断。
- 同一输出有多条链路，只审了一条。

自检：这份 capture 是从读者实际读到的那个面上取的吗？他那条链路会不会只给他其中一截？
