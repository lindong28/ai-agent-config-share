# LLM Cost Observability Review Principles

审核与构建 LLM 成本观测的行为准则。目标不是得到一个看似精确的金额，而是让每次付费尝试、价格证据、消费端与成本归因在不完整事实下仍然可见、可审计、可行动。

**适用范围**：LLM/多模型调用的计量、定价派生、成本报表与告警、prompt/route/cache 成本归因。普通服务故障告警的设计质量仍归 `alerting-review-principles.md` 与 `service-operations-protocol.md` §6。

**成功状态**：未知成本不会显示为零；失败调用不会从支出统计中无声消失；纯 pull 页面不是唯一消费端；价格与调用量变化可被区分；优化结论能归因到同一调用、同一 tariff 与同一比较口径；所有 PASS 检查都证明过自己能输出相反结局。

**校准锚点，不是通用阈值**：真实充值 ¥50 对应 222 次 interpret 调用；vendored catalog 与官方价格系统性相差 4.40%；约 87.6% 的报告成本来自尚未验证权威性的 nominal list price；prompt 前缀缓存从无可用命中提升到 97.755845%，同一受控调用派生为 ¥0.019954/篇。这些数字用于检验原则能否暴露口径与证据差异，不可复制成其他项目的阈值。

告警与阈值侧的 flag 同样出自实测而非推演：一条成本突变规则因可比性 guard 排除全部基线而从未上膛；一条判据带套在 4 个样本上，而其 before 侧自身的重复运行就跨了两档。

## 1. 计量发生在付费事实形成处

**一次 attempt 的存在性不得取决于请求发出之后的任何后续事件：记录在派发时即已不可撤回地建立，usage、outcome、cost 都只是事后回填的字段，未回填即 unknown。**

自问：这次 attempt 的存在性，取决于请求发出之后的哪一步？任何"取决于某一步"的答案都是缺陷。把义务挂在「provider 返回 usage 之后」是最常见的一种——它覆盖了响应回来后 parse/save 失败的路径，却漏掉 usage **从不返回**的那一整类：超时、断流、网关 5xx、客户端取消、SDK 在读 body 前抛异常。这些场景照样可能计费（额度已扣、任务在后端跑完），而按 usage-return 触发的规则对它们无话可说。

最小事实包括 provider/model、调用点或 stage、item 与 attempt 关联身份、input/output/cache token、发生时间、route/fallback 与可用的业务归因。cache 字段允许未知，但未知必须保留为 `NULL`/unknown 并单列覆盖率，不能转成零命中。

这条禁令约束**事实层**——存储、以及任何自称报告原始事实的聚合与显示。派生层可以为了让两侧可比而把 unknown 折算到某个保守基准（P6），前提是折算被标为 normalized、且被折算的 unknown cohort 在结果中仍可数出来。事实层与派生层同形才是缺陷，派生层做了标注的折算不是。

如果计量只能在 parse/validation/save 成功后运行，则所有金额、每调用成本与 cache 指标都只是 surviving calls 的统计量。修复前，权威成本契约必须把指标定义为 recorded/successful-call 口径并持久记录该限制；任何消费端若称其为 provider 账单、attempt 总支出或预期调用成本，仍是 blocker。无需在每一行重复完整免责声明，但限制必须从主视图或其直接口径指针可发现，不能只活在实现者记忆里。

这条降级有边界，它买的是时间而不是豁免。注意别把闸门设在一个此处必然测不出的量上：「失败 attempt 占比小」不能作为放行条件——在计量位置错误的系统里，那个占比恰恰是算不出来的，于是缺数据会默认成"看着不多"。默认是 blocker，除非用**带外**证据把占比测出来并证明它可忽略——证据得落在**扣费面**（provider 侧的扣费额或计费条目对上已记录行数）。调用计数不行：它很可能与被审系统共用同一个"成功才计"的过滤器，也未必覆盖网关侧短路的请求，于是两边对得上、而付了钱的那部分同时不在两边。用途本就是控制支出的视图，即便占比小也仍是 blocker——缺的正是要管的那部分。降级还要带修复期限：一个「已知限制」挂到没人记得它是临时的，就变成了默认设计。

flag（例，非全集——先用上面的自问扫一遍，再看这里）：

- 请求已发出但 usage 从未返回（超时、断流、5xx、取消），没有留下任何 attempt 记录。
- 同一失败 attempt 被 retry 后，只看得到最终成功行。
- per-call metering 存在，却位于任何可能失败的下游步骤之后——parse、validation、业务保存是常见的三个，去重、入队、流式读完、审核通过同理。
- cache 未采集与 cache 命中为零在 schema、聚合或显示上同形。

## 2. 不确定性必须可见且可行动

**代码不能确认一个事实时，不得用 `0`、健康、恢复或停止评估来替代未知；应把两侧归一到共同口径，或计算能支持单向决策的界限，并显式保留未知部分。**

自问：这个视图里每一个看起来确定的值，背后有没有一个"其实不知道"被折成了它？零、健康、已恢复、暂不评估都是未知最常穿的外衣。反向也问一遍：有没有哪个未知本可以归一或取界，却被用来拒绝报告？

这个判据同时约束单次调用、窗口比较、告警生命周期与中途测量：未定价调用为 `unpriced` 而非零成本；不可比窗口先统一 tariff/cache 基准；在途金额可作为下界触发阈值，但不能证明恢复；无法评估的规则必须可见为 unarmed/degraded，不能读成 healthy。

flag（例，非全集——先用上面的自问扫一遍，再看这里）：

- pricing 配置缺失后成本字段仍为 `0`，且没有 unpriced 计数。
- comparability guard 因口径不同永久拒绝比较，却持续显示正常。
- 报表有 comparison gate，但实际没有形成 before/after 两侧读数。
- mid-run 数据不完整时，系统停止所有正向判断，而不是使用可证明的下界；或反过来用下界宣布恢复。
- 部分 cohort 缺事实导致已知 cohort 也被全部丢弃，而不是分别报告 known 与 unknown。

## 3. 定价是带时间与权威性的证据

**每笔成本按调用时间从 provider-scoped 精确型号解析价格；价格记录同时携带有效区间、source tariff、来源币种、换算汇率、权威性与新鲜度。**

按量单价不是唯一计费模式。预付余额、包量、订阅额度、自建或免费额度下，per-call 的 list 派生值是**挂牌估算而非实付**：它自洽、精确、且与用户真实支出无关，正是 P2 所禁的「用看似确定的值替代未知」。这类计费下，成本视图必须标出派生值的这一性质，说明真实边际支出取决于额度是否耗尽，并且**不得据该派生值做渠道路由或用量取舍决策**，直到计费语义被权威核实。核实前把它当已验证实付价，比不报更糟——它会驱动错误的省钱动作。

自问：这个数字的权威性来自哪里，距离最后一次核实过了多久？两条轴要各自答得出来。

**调价与修正是两件事，处置相反。** 调价：旧区间在当时是对的，封口追加新条目，历史不动。修正：旧区间本身就错（catalog 抄错、型号映射错、汇率用错），此时"不重写历史"保护的不是审计而是错误——历史必须按修正后的费率重算，并走 P8 的消费端闭环。区分二者看的是**旧值当时是否正确**，不是改动发生在什么时候。两种都不能悄悄做：修正要留下修正前的值、修正原因与修正时刻，让"当时报了什么"与"现在认为当时是多少"都还查得到。

自动跟价的来源要能说清自己失效时会怎样——fallback 是显式的还是静默的。解析不到精确型号时保持 `unpriced`，不得让未知后缀吸附到相似 bare model。

状态至少区分 `priced`、`nominal`、`unpriced` 与 `fresh`、`stale`、`due-review`。计算一致性只证明同一 catalog 下算术一致，不证明 catalog 权威正确。已知的系统性价格偏差、以及金额中来自未核实挂牌价的占比，都必须在主视图中保留——它们是读者判断这个数字能信到什么程度的依据，被容差或总金额吞掉之后，一个估算读起来就和一份账单一样。

flag（例，非全集——先用上面的自问扫一遍，再看这里）：

- 一次调价被当成修正，历史被就地重写；或一次修正被当成调价，错价在历史里永久留存。
- bundled/community/list price 被显示为已验证实付价。
- FX 变化与来源单价变化无法区分。
- 对账工具与生产 resolver 共用同一解析实现，因此同一个错会共同 PASS。

## 4. 检查的读数必须携带关于被检对象的信息

**每个成本检查都要有独立输入或独立实现边界，并用阳性/阴性对照证明健康与故障会产生不同输出；检查对象数量为零时不得报告 clean。**

自问：这个读数在被检对象健康与故障时会不同吗？我能各造一例证明吗？造不出来的那一侧，就是这个检查看不见的那一侧。

两个方向都要证明。只会通过的检查（读数在成立与不成立时相同）与只会报警的检查（噪声宽于判据带，无故障也响）是同一个缺陷的两面：读数都不携带关于被检对象的信息。判据带必须由被测量的噪声定出，而不是从别处借一个看着合理的区间套上去。独立性要落在**这个检查声称在测的那条轴**上：另写一份实现、却读同一份 catalog 的对账，在 catalog 权威与不权威时给出同样的读数。

轴选错了，独立性就是假的：从 raw catalog 独立解析费率的对账只在**映射**轴上独立，能抓解析错配，抓不到 catalog 本身错价；要测权威性，得换一个不共享 catalog 的输入（官方账单、控制台读数）。

flag（例，非全集——先用上面的自问扫一遍，再看这里）：

- reconciliation 克隆被审 resolver，双方会复制同一缺陷。
- 告警长期停在 firing，被当作“告警在工作”；卡在该状态时真实 outage 产生不了新 transition。
- 判据带借自别处（生产分布、经验区间），窄于该样本量下自身重复运行的波动。
- 测试只断言 exception，且 unrelated exception 也能通过。
- scan 循环零次或目标集合为空，末尾仍打印 PASS。

## 5. 成本需要主动消费端

**成本事实至少同时进入趋势消费与异常消费：报表解释长期结构，告警检测调用量/token/模型组合突变，价格变化走独立通知链；纯 pull 页面或数据库列不构成观测闭环。**

自问：读者拿这份报表要做什么决定，缺哪一项他就做不成。以此定内容——窗口、前窗共同口径、per-stage/provider/model 驱动、单调用成本、cache 命中与覆盖、nominal/unpriced/stale 作用域通常都在其中，但它们是常见答案不是完整答案。告警必须证明真实部署能产出基线并上膛，生命周期可从 clean 进入 firing、升级并在完整证据下恢复；价格新鲜度、未定价与 tariff 变化不应混入量结构告警。

调用量在结构上形不成基线的项目（低频批处理、一次性实验），出路不是装一条永远 unarmed 的规则——那既满足不了本条，又正好落进 P6 flag 的「永不上膛」。改用不需要基线的消费形态：绝对额度阈值、每次运行结束时的成本回执、或按运行而非按窗口的对比。本条要的是成本事实被主动推到人面前，不是某一种告警实现。

flag（例，非全集——先用上面的自问扫一遍，再看这里）：

- 成本只存在于 admin 页或查询命令，没有定期 push。
- 报表打印金额但不比较任何等长窗口或共同基准。
- 告警规则加载成功，却没有可观察的 armed/unarmed 与 transition 证据。
- tariff-only 变化触发量结构 page，或价格变化没有独立通知。

## 6. 比较先统一口径，再解释变化

**跨窗口比较只在同一 tariff 与 cache 基准下进行；绝对成本保留调用时真实派生值，比较值与绝对值必须分名。**

自问：这两侧之间，除了我想解释的那个变量，还有什么变了？tariff 与 cache 基准是最常见的两个，model 组合、prompt 版本、batch 折扣口径、retry 策略同样会让两侧不可比。

「保守」是相对问题方向而言的：cache-all-miss 对"会不会超支"是保守的，对"至少省了多少"则是反向的乐观。缺 cache 事实时，可把两侧统一到 cache-all-miss 等保守基准，而不是要求原始 coverage 完全相同后永久拒绝比较。下界语义见 P2，但它只对**窗口内单调不减的累计量**（金额、token、调用数）成立；命中率、覆盖率、nominal share 这类比率在未封口窗口里双向偏移，既非下界也非上界，不能拿一个偏高的部分读数去 fire。任何 normalization 都要标为 normalized，并保留被排除或被折算的 cohort——unpriced、unknown-cache 与 survivor-only scope 都要仍可数出来。

flag（例，非全集——先用上面的自问扫一遍，再看这里）：

- cache coverage 或 tariff 版本不同，直接把金额变化归因于调用量。
- normalized comparison 被展示成账单绝对值。
- comparability 要求在生产分布下不可满足，规则因此永不上膛。
- lower bound 未越线被解释为 healthy。

## 7. 归因的分辨率要够到泄漏所在的粒度

**诊断必须能指出是哪个可被操作者改动的成本单元在增长，而不只是总量变大了；token、cache、route、质量结果与派生成本要关联到同一次调用。**

自问：如果成本涨了一倍，这套仪表能把它定位到哪一级？停在"总量"就不够。成本单元随调用形态而不同——prompt 的固定脚手架 / 跨调用动态注入 / 单篇正文是一种切法，agent loop 的轮次、工具返回值撑大的上下文、多模态的 image tile、reasoning token、batch 与 async 的折扣口径是另一些。按某一种切法逐项对照，不长那个样子的泄漏会全部报 N/A。

优先处理会随运行单调增长、又位于共享前缀之外的复利型泄漏；再按稳定内容是否进入 cacheable prefix 排序。优化前后使用同一 tariff 与同一调用口径，cache saving 只按同一调用的 actual-vs-all-miss 差额归因，其余差额保留给 prompt/output shape、provider/model mix 与生产分布。

「无 cache 事实」「测得 0% 命中」「测得某个命中率」是三种状态，任何一步都不能把前两者混为一谈。受控单次调用测得的单篇成本只能证明那一类成功调用；若计量位置使失败 attempt 不入账（P1），该数字更不能被当作每次尝试的预期支出。

flag（例，非全集——先用上面的自问扫一遍，再看这里）：

- 只看总 token，不知道哪个调用点或 prompt 区块增长。
- 把跨项目/跨模型/跨窗口总差额全部归因于 cache 或 prompt reorder。
- 降本验证没有 route/fallback、tariff、cache coverage 或质量结果。
- 优化结论建立在未核实权威性的挂牌价上（P3），却按实付口径陈述省了多少。

## 8. 共享事实源被修正后，必须闭环到全部消费者

**一个被多处消费的共享事实源（tariff、口径定义、归一基准、型号映射）被修正后，更新不是改一处，而是一次完整的历史与消费端闭环；各来源的复核周期分开管理。**

触发闭环的是偏差的**性质**而不是幅度：同向、跨调用可复现、可归因到 tariff 源，就是系统性偏差，哪怕只有几个百分点——它会随调用量线性放大，且不会自行回归。用一个幅度门限来筛它，恰好会让稳定的小偏差长期免检，那正是下面 flag 里「容差 band 吞掉系统性偏差」的成因。随机、双向、幅度随样本收敛的差异才是噪声。

闭环的判据是：识别出该事实源的**全部**下游消费者并逐一重放到与修正后一致，同时证明未受影响的窗口确实未被改动。自问：这个事实源的读者都有谁，包括不在代码里的那些（已导出的文件、缓存的聚合、下游的预算与配额）。其中有一类不能重放——已对外结算的账单、已入账的分摊、已冻结的预算周期：改它们不是修正而是伪造已发生的事实。对这类保留 as-reported 值，另发一笔标注过的前向调整。社区缓存 TTL 与 supplement 复核期分别管理；source `fetched_at`（何时取到）不能冒充 tariff `verified_at`（何时经权威核实）。

flag（例，非全集——先用上面的自问扫一遍，再看这里）：

- 只改当前价格，历史窗口被静默重写。
- supplement 超复核期仍显示 fresh。
- 更新后只测 resolver，没有重跑报表与告警消费端。
- 容差 band 吞掉系统性偏差，没人启动价格维护。

## 裁决顺序

发生冲突时依次守住：付费 attempt 不丢失（P1）→ 未知不伪装成确定（P2）→ 价格证据与检查可证伪（P3/P4）→ 消费闭环与共同口径（P5/P6）→ 优化归因与维护（P7/P8）。较低优先级不得用“更完整”或“更精确”为理由**推翻**较高优先级的结论。但**收窄适用域**不受此限：一条低位原则指出高位原则的某个做法在某类对象上不成立（如下界只对累计量成立、对比率不成立），那是在说明高位原则本来就管不到那里，不是破坏它。分清这两者：改变同一情形下的答案是推翻，划出这条规则本就不适用的情形是收窄。

这个排序回答的是「谁让步」，不是「artifact 该长什么样」。两条冲突各自都能写成具体要求、且满足其一必然违反另一条时，宣布赢家往往只是把洞挪到另一边——先找**能同时满足两条的第三种形态**（多数是把它们分派到不同层：事实层保留未知、派生层折算并标注；或产出一个显式标为 non-authoritative 的界限而不是沉默）。找不到才按排序让步，并把让步与理由记在该项目的成本契约里。

同档并列的两条（P3/P4、P5/P6、P7/P8）相撞时没有排序可退，第三种形态也找不到——此时不要自己选一边然后不说：把两条要求、各自的证据、以及你倾向哪一边写出来交人裁决，并把裁决记进成本契约。悄悄挑一边正是这套原则要防的那类沉默。
