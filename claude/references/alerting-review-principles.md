# Alerting Review Principles

审核与构建「服务故障告警」质量的行为准则——覆盖**值不值得 page、多严重、说什么、要不要合并**。

**目标**：让对的人、在对的时间、采取对的行动，且不"狼来了"。设计上要同时对抗两个失败模式——**漏报**真实事故（silence 看着和健康一样），和**告警疲劳**被用户静音（被静音的告警 = 没有告警）。

**取舍**：本准则偏向**更少、更高信噪比**的告警，而非为覆盖而多报。信息性/诊断性内容降级到低通道或落状态不推送，而不是都用 page 级轰炸。

**这套原则奏效的标志**：运维读消息本身即知影响与该做什么；page 级（🔴）只在需要立即处置时响；一个根因只发一条通知；没有一条告警会被用户调成静音。

**Loop**：对每条告警规则和每条告警消息，逐条对照 P1–P8，循环到无原则被违反为止。

## 优先级与冲突裁决

P1–P8 按**裁决优先级**排列：两条给出冲突指导时，编号小者胜（值不值得 page > 严重度 > 说什么 > 怎么说 > 合不合并 > 证据 > 生命周期 > 留痕）。

**逃生阀**：当照此顺序会与你对"什么服务于告警目标"的判断相悖时，先用 `AskUserQuestion` 问用户再落地。

## 1. 症状优先，抑制已知良性

**告警条件应追踪用户可感知的影响（或迫近的影响），而非纯内部指标破线。代理/provisional 信号（同机 co-load、合成探针、已知瞬态生态）只有在有独立信号背书——该信号覆盖它所探测的同一用户可感知失败面（且对该面的真实退化至少同等敏感、不因阈值更钝而漏）、且当前干净——时才可降级或抑制；否则（唯一探测路径，或只有位置更贴近用户却不覆盖同一失败面的信号）保留 page 资格。"是 provisional"只 correlate、不 entail 良性；"位置更贴近用户"也不 entail 覆盖同一失败面。**

flag：
- 条件是内部阈值破线，但说不清哪个用户的什么体验会坏。
- 对代理/provisional 信号降级或抑制，却**没有**覆盖同一失败面的独立干净信号背书——此时它可能是唯一探测路径，降级会静默掉真实事故。
- 反过来：已有覆盖同一失败面的独立干净信号佐证良性，却仍对代理信号以最高级 page（这才是真的过度 page）。

自检：这条一响，能不能一句话说出哪个用户的体验坏了？说不出别急着判它良性——回到上面的规则走一遍。

---

## 2. 严重度 = 影响 × 紧迫

**严重度按影响与紧迫定，不按信号是否 provisional 定：page 级/最高级只保留给真实或迫近的用户伤害、且需要立即处置的情形；良性 / 信息性走低档通道或只落状态、不推送。**

flag：
- 同一严重度既给"服务挂/上游不可用"，又给"provisional 探针偏慢"这类不对等的事。
- 不需要立即行动的信息也用 page 级推送打断人。
- 完全无分级——所有告警一个通道、一个颜色。

自检："收到这条，我必须现在放下手里的事吗？"否 → 它不该是 page 级。

---

## 3. 消息自解释：影响 + 行动 + 是否需立即处置

**读消息本身就能知道：什么受影响、该做什么、是现在做还是仅知会。不让运维去重推系统已经算出来的结论。**

flag：
- 只报数值/类别，不报对用户的影响。
- 没有明确的下一步动作，或动作只是"自己去看"。
- 系统已知的关键判断（如"与 pipeline 并发、疑似同机争用"）没写进消息，要运维自己再推一遍。

自检：把消息给一个没有上下文的人，他能否说出"影响是 X、我该做 Y、是否现在"？不能 → 补齐缺的那一项。

---

## 4. 为压力下的人写

**消息面向一个可能被吵醒的人。不泄露状态机内部量，数值给有意义的精度并带对照，调试细节进 evidence/runbook、不进推送正文。**

flag：
- 无意义精度（如 `2367.249083ms` 的亚毫秒小数）。
- 内部机制量（`advanced_window_streak=3/3`、`samples=35`、warm count）出现在推送正文。
- 裸数值无对照——没有"实测 vs 预算 vs 倍数"，读者得自己找基准。
- 一条推送里塞进多屏调试信息。

自检：正文里每个片段，运维**决策**时用得上吗？用不上 → 移到 evidence/runbook。

---

## 5. 一次事故 = 一条通知

**同一根因引发的多条关联告警必须合并成一条带清单的通知。**

flag：
- 一轮检测里多条互不相同的告警几乎同时响，且指向同一根因（如主机争用让所有旅程一起超标）。
- 无关联/rollup 逻辑，每个规则各自独立推送。
- 运维要自己在脑子里把 N 条拼回 1 个事故。

自检：这些同时响的告警共享同一可观察的**因果**判据吗（同一上游标识 / dedup 维度；"同主机"仅在假设根因本身即主机级——如 CPU 争用——时才算，否则只是位置巧合、不 entail 同因）？是 → 合并成一条带明细清单的通知；无可核验的共因判据、仅时间巧合时倾向不合并，别把独立并发的第二事故并掉。

---

## 6. 每条告警指向证据/runbook

**每条告警带"去哪看"——evidence artifact、日志路径或 runbook 章节——让 triage 不从零开始。**

flag：
- 告警没有任何"下一步去哪看"的指针。
- 处置动作抽象、无具体落点（哪个文件、哪个页面、哪条命令）。

自检：收到告警的人能否不用翻找、直接知道该打开哪个文件/页面/命令？

---

## 7. 确认后再 fire，清除即 resolve

**抖动/易 flap 的信号先去抖（确认窗口 / 连续失败计数）再 fire，避免单点毛刺 page；只有**已超自愈能力的硬 down**（进程死亡且 supervisor 重启预算耗尽 / 破 crashloop 阈值 / 超重启窗口仍不起）才 entail 终态、应立即 page，强行去抖只会平添延迟。恢复后发显式 resolve，让运维知道事故结束。投递侧的去重与复位见 §6.4，本条是设计侧的"确认"与"闭环"。**

flag：
- 对**抖动-prone**信号、或对目标状态的**远端单次采样**（端口 / 健康端点）单次失败即 page、跳过去抖。
- 把**裸 PID 消失 / 单次 exit 事件**当终态即时 page——计划重启 / rolling deploy / crashloop 每周期都会瞬时 PID 消失或发 exit，据此即时 page 会把 P7 要防的 flapping-page 放回来；终态判据是死亡**且未自愈**（超重启预算 / 破 crashloop 阈值）。
- 反过来：对已超自愈能力的硬 down 强行要求确认窗口，给本该即时的 page 加延迟。
- fire 后无 resolve 通道，运维不知道好没好。

自检：这条会不会被一次偶发抖动 / 一次计划重启触发（是 → 去抖或过滤）？它是不是已超自愈能力的硬 down（超重启预算 / crashloop 阈值，是 → 即时 page）？恢复了运维怎么知道？

---

## 8. 告警留痕：持久、有界、可查

**fired 告警应留下持久、可查询的记录，且该记录必须有界——留痕缺失则事故后无据可查（无法复盘、调阈值），有界确保告警流不成为 retention 的遗漏项。retention/rotation 的通用机制见 `resource-cleanup-protocol.md`，本条只约束"告警流要留痕、且留痕要有界"。**

flag：
- fired 告警只落当前状态（覆盖写）或仅进程 stdout，无持久可查的历史——事故后无法回答"这条规则近来告警过几次、每次什么值"。
- 有留痕但无 retention/rotation，随时间无界增长。

自检：事故后能不能查到"什么告警、何时、多频、什么值"？这份记录会不会无限涨？

## 反例改写（AI Radar，2026-07-20）

**改写前**（实际推送，违反 P1/P2/P3/P4/P5）：

```
【AI Radar】🔴 PERF:wechat.pagination.settle:same_host_origin:busy 旅程性能退化 wechat.pagination.settle
故障类别：旅程性能退化 wechat.pagination.settle
具体故障对象/数值：wechat.pagination.settle same_host_origin busy: samples=35,
  p75=2367.249083ms/1000ms, p95=3521.997208ms/1500ms, advanced_window_streak=3/3;
  same-host provisional; not a regional SLO
处置方向：查看证据中的近期样本、CPU 与 pipeline 状态；该结果仅代表同机 provisional 观测。
```

违反 P1–P5：busy 良性仍 🔴 且无独立干净信号背书（P1）/ 与 A1 同级（P2）/ 埋掉"用户大概率无感"的结论（P3）/ 假精度 + streak/samples 内部量入正文（P4）/ 6 条同因（host busy）齐发未合并（P5）。

**改写后**（降级 + 合并，符合 P1–P5；下方字段布局仅为示范、非规定格式）：

```
【AI Radar】🟡 性能自测（同机 provisional，非用户侧）：pipeline 运行期间 6 条旅程探针超预算
影响：仅同机合成探针，与 pipeline 并发、疑似主机 CPU 争用；idle 视角与真实用户侧无异常，用户大概率无感。
需否立即处置：否——除非 idle 视角也开始超标（那才代表真实退化）。
去哪看：logs/performance/evidence/ 最新证据 + 主机 load。
明细：homepage.first_card、wechat.list、wechat.pagination 等 6 条在 busy 下超预算
  （最严重 homepage p95 ~20s，含探针超时）。
```

修复 P1–P5：🔴→🟡 降级（P1/P2，因 idle 与真实用户侧这两个独立信号在场且干净）/ 开篇即写影响与"需否处置"（P3）/ 去假精度与内部量、数值带对照（P4）/ 6 条合一（P5）。
