# 从用户角度观察与对比网页

网页的正确性有一部分只存在于**用户眼里**：对齐、留白对称、阅读顺序、缩放后的重排、**这些盒子里的字对他有没有用**，以及**他点下去之后等了多久**。这些既不在源码里、也不在单元素的属性值里，因此按值逐项核对可以全绿而页面看起来仍然不对、读起来仍然没用、用起来仍然卡。本文件规定观察与对比的方法，供 `test-ux` / ux-contract 系列 / `design-critique` 引用。

**动机案例**（真实、代价已付）：一次"1-1 复刻参照站"的任务里，我方逐值核对了 649 个 CSS 值、跑了 65 条 Playwright、拍了 100 帧对照截图、填了 700 格 rubric，全部通过；用户打开两个站一看就说日期与时间戳的水平位置不一致、缩放后观感差。实测证实：日期标签在参照站里**右对齐在时间列内**（与下方所有时间戳共一条右边界），我方把它缩进到了卡片左缘——错开 60px；≤960px 时我方内容列 564px 宽、左右留白 98/58 不对称，参照站 640px 宽、40/40 对称。**两处都在已通过的检查覆盖范围之外**。

## 观察的三个面——只查值层必漏

**呈现形式**分三层，是同一件事的三个粒度：这些盒子长什么样（值）、彼此什么关系（关系）、由什么机制产生（结构）。**读者意义**是另一个面：这些盒子里的字对读者有没有用。两者分开，是因为漏掉的方式不同——呈现形式三层可以全绿，而页面在读者眼里毫无用处。读者意义这一面还特别难自查：漏掉它时你**已经把页面渲染出来了、也确实在查真实 DOM**，只是从未把文字当文字读过一遍。

**响应**是第三个面：这一页对他的操作回应有多快。它与前两个面正交——排版完美、文字有用的一页，照样可以在他点下去之后让他等一秒半。它漏掉的方式又不一样：前两个面的每一项检查都在**某一个静止时刻**上取读数，而响应只存在于**两个时刻之间**，于是无论把静态检查加到多密、跑多少轮，它一次也不会被采样到。

| 面 · 层 | 例子 | 用户是否感知 | 常见检查是否覆盖 |
|---|---|---|---|
| 呈现形式 · **值** | 字号 12.5px、色值 `#96702e`、`border-radius: 3px` | 弱（亚像素差异不可辨） | 覆盖——按 spec 逐项断言即可 |
| 呈现形式 · **关系** | 日期与时间戳左/右边界是否对齐、左右留白是否对称、A 在 B 上方还是下方、间距是否等距、读者要的那一项在不在进入时的视口里 | **强，第一眼就看到** | **通常不覆盖**——关系不是任何单个元素的属性 |
| 呈现形式 · **结构** | grid 还是 flex、几列、轨道宽度、padding 由谁承担 | 间接但决定关系 | 通常不覆盖——值相同而结构不同，观感仍不同 |
| 读者意义 · **内容** | 读者要的答案根本不在页面上、或藏在猜不到的分组里；同一事实两处两种写法（`0.00055` 与 `5.55e-4`）；同一句话在一张表里重复 28 次；并排两列的解释文字逐字相同；内部状态码原样出现在正文（`provisional_heavy_scorer_not_integrated_before_first_production`）；浮点尾巴 `220.40539600000002` | **强，且决定这一页有没有用**——读者是来找答案的，不是来确认元素在位的 | 默认不覆盖：`innerText.length`、元素计数这类**聚合读数**在"写得清楚"与"同一句重复 28 次"两种情况下同样是五位数。但它**不是不可测**——重复行、同一事实两种写法、术语外泄都抓得住，写个确定性检查就行；只有"这些字回答了读者的问题没有"必须靠读 |
| 响应 · **时间** | 点侧栏切到另一个视图、翻页、筛选、搜索、展开、滚动追加下一批，各自从他的动作到画面更新之间等了多久；首次进入到能开始读之间等了多久 | **强，而且这是他唯一会主动开口抱怨的一面**——"有明显延迟感"、"不顺滑" | **通常不覆盖**——静态检查在一个时刻上取值，两个时刻之间的量它测不出。而站内切换若是纯客户端的，连一次导航都不产生，`curl` 的 `time_total` 与 LCP/FCP 那套**连观察对象都没有** |

**规则**：凡"看起来不对"的抱怨，先查关系层与结构层，不要再加一轮值断言。凡"看不懂 / 没用 / 太吵 / 找不到"的抱怨，查内容——**加多少轮呈现形式的检查都不会靠近它**。凡"卡 / 慢 / 不顺滑 / 有延迟感"的抱怨，查响应——它与前两面正交，**加多少轮静态检查也一样不会靠近它**。值全对而关系错是最常见的形态；呈现形式全绿而内容烂，是**自查最容易通过**的形态：你跑的每一项都真跑了、也都真通过了，它们只是都不指向内容。响应面有它自己的一种自查通过法：**你确实操作了页面**——展开过、切过、滚过——只是每次操作之后看的都是布局，一次时也没计过。

## 测量技术

| 要测的东西 | 正确做法 | 错误做法与后果 |
|---|---|---|
| 用户看到的文字位置 | 对文本节点建 `Range`，取 `getBoundingClientRect()` | 取元素盒——inline 元素收缩包裹、`text-align` 只移动文字不移动盒，两者可差数十 px |
| 某元素的几何 | 先断言它**可见且非退化**，再测。判据是**经全部祖先裁剪后仍与视口有非空交集**——`IntersectionObserver` 直接给这个读数；只查自身的 `display` 与宽高不够 | 直接测——隐藏子树里的同名元素返回 0×0 或错值，对比等于什么都没比。**只查自身属性同样漏**：实测一个 `display:block`、372×512、`getBoundingClientRect().top=266`（视口高 577）的 `<video>` 按自身属性判为"可见"，实际被祖先的 `overflow:hidden` 整块裁掉——同页 28 个播放器全部如此，且页面自己的 `IntersectionObserver` 因同一原因永不触发、`src` 从未挂上 |
| 某属性是否生效 | 读 `getComputedStyle` | grep 源码——插值生成的类名（`cls-{{ i }}`、`` `x-${n}` ``）与 `dataset.fooBar` 在源码里不以字面量存在 |
| 布局机制 | 读 `display` / `gridTemplateColumns` / 各方向 padding 的归属元素 | 只比值——同样的 64px 在"网格轨道"与"padding"里产生不同的对齐关系 |
| 留白对称性 | `left = box.left`、`right = clientWidth - box.right`，比较两者 | 只看宽度——宽度对而位置偏，用户看到的是内容没居中 |
| 一个区域里有多少在承载内容 | 量**实际绘制的那些东西**：区域内每个非空文本节点建 `Range`、每个图形元素（量条、图标、canvas）取其盒，取这些矩形的并集，再与该区域自己的盒比。高与宽分开报——前者答"下面空了多少"，后者答"一行里有多少在干活"。报数带视口，且要在**读者实际用的那个宽度**上取一次（要覆盖哪几档见本文件「必须覆盖的轴 · 缩放」）：容器有 `max-width`、或按栏分配剩余空间时，同一页在两个宽度上这个比值可以完全不同 | 拿子容器的 `getBoundingClientRect()` 当"内容尺寸"——grid / flex item 默认 `align-items: stretch`，容器被拉伸到轨道高度，于是"内容高"读成"轨道高"、空白恒算成 0。实测一页左栏 68% 是空的，按容器盒量出 **0%**；这个读数在"排得很满"与"大片空白"两种情况下取值相同，因而不是证据。反向的同形也要挡：并集里混进被拉伸的 wrapper、绝对定位的装饰、或区域外的节点时，比值趋近 1，与一个真正排满的区域读数一致——**比值 ≥0.99 时按未核实处理**，别读成"排得很满" |
| 渲染内容与它的盒子是否一致 | 比 `videoWidth/videoHeight`（图片用 `naturalWidth/naturalHeight`）与 `getBoundingClientRect()` 的宽高比；差出来的就是黑边或裁切 | 只断言盒子尺寸符合 CSS——CSS 写死的比例与产品实际输出不符时，逐元素读数**全部正常**。实测：CSS `aspect-ratio: 256/352`、产品实际交付 `256×288`，28 条片每条都带黑边（512px 高的盒子里只有 418px 是画面），而 `video=28@ready>=2` 与逐条 `videoWidth` 全绿 |
| 并排对比的两个**块级**对象共不共顶边 | 各自 `getBoundingClientRect().top` 相减 | 只比两者的尺寸——尺寸一致而起点不同，眼睛照样无法在同一水平线上比较（实测差 48px，而两个盒子都是 372×512）。**对象是文字时不能用元素盒**，改按本表第一行建 `Range`——本文件开头那个动机案例（日期标签与时间戳错开 60px）正是文字对象 |
| 一屏装得下几条 | 两道闸都过才算一条：① rect 落在**可见带**内；② 它真的看得见（没被裁掉 / 盖住 / 透明掉 / 退化成零高）。另报 `max(r.height) / band.height`，**这个 max 取未经筛选的全部条目**——高过一屏的那条必然筛不过闸 ①，而它正是要抓的。可运行配方、带的算法与仪器自检见本表下方「一屏装得下几条：用 `~/.claude/bin/first-screen-density`，别手写」；报数带视口、缩放档与内容量 | 只用 rect 判完整可见——它给的是未经祖先裁剪的布局位置；实测被 `overflow:hidden` 裁掉、被 sticky 头盖住、`opacity:0`、`visibility:hidden`、零高的卡片全部落在带内，其中后四种连 `IntersectionObserver` 的 `intersectionRatio` 也照给 1.0（它不做遮挡命中测试、不读 opacity/visibility，零面积元素规范上直接判满）。计数于是在"看得见 N 条"与"一条都看不见"两种情况下相同（同反模式表「「DOM 里数得出来」当作「用户看得见」」）；拿 threshold 默认 0 的相交读数冒充——一张占满整屏的卡片照样计 1，`>= 2` 这类下限断言在首屏实际只剩一张时仍然通过；`max` 只取筛过的那批——高过一屏的条目筛不过边界，比值于是永远报不出 > 1，而它存在的全部理由就是抓那条；用均值守最坏形态——实测一条 998px 混进九条约 210px，均值 289 轻松低于任何按常规卡片高定的上限；分子分母不同源（边界用 `intersect(...)` 的高、分母却用 `scroller.clientHeight`）——实测把真值 2.5 报成 0.495，五倍低估；把元素数组直接喂进筛选器，或同步去读异步的 IO 结果——前者 `r.top` 取到 `undefined`、比较恒 `false`，后者拿到空集合，结果都是 `0`，与这条检查真失败时的读数逐字相同 |
| 答案元素离读者多远 | 答案元素是读者为这次访问而来的那个东西——可以是容器里的某一行，不必是页级块。从进入时的视口顶算到它，按承载它的滚动容器的高度换算成屏数，报数带视口、缩放档与内容量 | 只量到承载它的组件——组件在首屏内而目标行在其下三屏，照样通过；整页截图目测——图里没有高度基准；按距页顶算——它在定高面板里读数不足一屏，面板内却要滚很久 |
| 一次**操作**让用户等了多久 | **用 `~/.claude/bin/interaction-latency`，别手写**（用法、退出码与它已知会报错的四类情形见本表下方同名小节）。它实现的就是右边这套：跨两个时刻各取一次时间戳，**起点是他动手那一刻**：指针操作取 `pointerdown`（不是 `click`，两者之间隔着一次抬手）；滚动追加这类没有指针事件的，取触发它的那一刻（首个 `wheel` / `scroll`，或加载阈值被跨过那一刻）——起点说不出来就没有这个读数。**终点必须锚在目标节点上**：先确认**他要的那个东西已经带着新内容出现**——判据是**内容真的变了**（MutationObserver 命中后仍要比内容，同内容重渲染与 class 切换都会触发它；轮询目标选择器同理），再取下一帧。**等待要有上限**（实测取 8 s），到点未变就报"N 秒内无变化"，别挂住。报数写明目标节点是什么，带视口、缩放档与内容量，**冷、热各报一次并写明是第几次**。**首次进入**是另一回事：那一次本身就是一次导航，同一条锚定纪律照用——锚在读者要读的那个节点上，三个标准指标里**取 LCP**（它最接近"能开始读"），`FCP` 与 `TTFB` 只作分段归因，别拿来回答"他等了多久"：首字节到了而后白屏三秒，TTFB 依然漂亮 | **终点不锚目标节点就等于没测。** `requestAnimationFrame` 在点击后的下一帧无条件触发，与页面有没有开始换内容无关，于是任何页面都给出约 16 ms；`PerformanceObserver` 的 `event` 条目止于**事件处理器之后的那次绘制**——handler 立刻返回、内容 1.5 s 后才回来时它照样只有几十毫秒，且 `durationThreshold` **默认 104 ms**，比它快的交互一条条目都不产生，而"零条目"与"这个 entryType 不被支持、`observe()` 静默无效"逐字同形；`long-animation-frame` 测的是 **>50 ms 的渲染帧**、不是输入到绘制的时延，不支持时同样静默为空。用 `curl` 的 `time_total`——纯客户端切换不发请求，这个读数不存在；发了请求它也只到字节收完，不含解析、执行与绘制。用 LCP / FCP 回答**站内切换**——它们按定义只在一次导航上产生，站内第二次切换永远不会有新的 LCP。只测一次就报——第二次点的是热缓存加已预热的连接，实测同一路径 MISS 0.216 s → HIT 0.086 s → HIT 0.075 s |
| 一次**等待**花在哪一段 | 拆段各取一次独立读数：网络路径（DNS / TLS / 往返）· 边缘命中与否 · origin 现算 · 传输 · 客户端解析执行与绘制。报数同上带视口、缩放档与内容量。见本表下方「一次等待要拆开才归得了因」 | 只报一个总数——它不指向任何一段，因而指导不了任何一次修改；且下一轮改完也无法归因 |

**一次操作让用户等了多久：用 `~/.claude/bin/interaction-latency`，别手写**

```
interaction-latency <url> --click '<被点的选择器>' --target '<他要的那个节点>'
    (--until-text '<看到这段文字才算到>' | --any-change)
    (--noop-click '<当前已选中的那一项>' | --no-negative-control)
    [--viewport 1440x900] [--timeout 8] [--max-ms N] [--json]
```

两组括号各是二选一、不能都省：不给到达判据时 loading 占位符本身就是一次"内容变了"、且能稳定很久；不给阴性对照时没有任何东西证明仪器分得清"变了"与"没变"——所以 `--no-negative-control` 把退出码**固定为 3**，不让未核实的读数以 0 的形态流到下游。

退出码：`0` 读数取到、阴性对照通过、冷热都未超 `--max-ms` / `1` cold 或 hot 任一超阈值 / `2` 仪器故障（含点击没落在预期控件上、viewport 没设成功、读数形状不对）/ `3` **unresolved——阴性对照自己报出了变化、没跑阴性对照、超时仍未到达、或目标是整页导航；不要读成 0，也不要读成通过**。夹具矩阵在同目录 `.test.py`，**31 条**，每条固化一次真实误判。

**它已知会给出错读数的四类情形**（外部评审报出、尚未闭合；完整场景见 `docs/issues/harness-issues.md` 的 HARNESS-429）：① `onScreen()` 判的是 `--target` 那个容器、不是 `--until-text` 实际所在位置，容器进了视口而文字还在折叠线下时会判"到了"；② `--until-text` 是子串匹配，判据在点击前已存在、或中间态偶然包含它都会提前收工；③ 阴性对照遇整页导航时**非 `--json` 模式抛 `KeyError` → 退出码 1**，即仪器故障冒充"页面慢"（用 `--json` 可避开）；④ viewport 读回失败、两组互斥参数、CLI 非有限数三条路径**零夹具覆盖**——守卫写了但没有用例证明它会开火。**这四条不是"覆盖不到"，是"会给出一个看着合理的数"**，所以拿它的读数下结论前先对照一遍。

**这一行为什么也必须是程序**：与「一屏装得下几条」同因——只有真实浏览器跑得出来，而散文没有回归测试。它以散文形态被推翻过**三次**（终点判据恒为真 / 终点不锚目标节点 / MutationObserver 命中即算数），成为程序后第一版又被外部评审推翻**八条 HIGH**，而那一版的 12 条夹具对其中两条最要命的**零覆盖**：把 `location.pathname` 拼进签名，于是"点击后立刻 `pushState`、内容 800 ms 后才到"约两帧就收工；只判 `innerText` 变了而不判目标可见，于是 `opacity:0` 的目标照样算"到了"。现在各有一条会红的用例：把路径拼回签名，读数从 **850 ms 掉到 53 ms**；去掉可见性检查，那条从 exit 3 变成 exit 0 报 **34 ms**。

**操作时延读数必须先过一次阴性对照，否则按未核实处理**（工具带 `--noop-click` 时自动跑；不是加强语气，理由与那三次实测见上一段）。阴性对照的形状是**做一个不该改变任何东西的操作**（点当前已经选中的那一项），看你的仪器报不报得出"无变化"。**首屏那一支没有操作可做，因而不适用这一条**；它的等价物是**加一次已知扰动**（网络或 CPU throttle、或临时挡住首屏必需的那个资源）后重量一次，读数必须显著变大——不变就说明你没在测这一页。**别拿"重载两次、读数落在同一量级"当自检**：仪器读到缓存里的旧条目、或干脆吐一个恒定值时，两次同样一致——那正是它坏掉的样子；而仪器好的时候第一次冷、第二次热，本来就该差开（本表下一行的冷热差实测 2.5 倍）。这个自检与它要查的故障反向相关。

（实测，代价已付。环境：Playwright headless Chromium、viewport 1440×900、`https://news.aiplanet.live`、已排除本机代理；被点的是侧栏「精选」`/` 与「全部 AI 动态」`/all`。一次量法把等待条件写成"当前文档存在 FCP 条目"——该条件在点击**之前就已为真**，于是六次切换报出 25 / 43 / 59 / 77 / 80 / 101 ms 一组看着完全合理的数，而 `location.pathname` 全程未变、那几次点击**根本没换过页**。把条件改成"路径或正文首 80 字真的变了"、并加一次阴性对照之后，同一页面同一浏览器的读数变成首次 1347 ms、其后 71–95 ms，阴性对照如实等满 8 s 上限报"无变化"。**两版读数都是三位数毫秒、都排得整整齐齐**，区别只在后一版的仪器报得出失败。）

**一次等待要拆开才归得了因**

无参照时，**归因**只能靠这一节：没有对照站，你拿不到"该是多少"，但每一段都答得出"这一段该花这么久吗"。（**测量**不因此免除——第一条无条件那项照旧要交秒数，见「交付前的最低证据」。）

- **总数在成因完全不同的两种情况下取值相同**。1.3 秒可以是 origin 每次现算，也可以是跨洋往返，而两者一个修在代码里、一个修在部署拓扑里。（实测两侧都撞过：一次 origin 侧 `/` 的 TTFB 是 1.300 s，profile 里最大的两项各为 `_batch_related_discussions` 1.008 s 与 `_latest_run` 0.349 s——**这两项互有重叠，不要相加**；另一次总延迟的主因是 origin 在上海却被路由到美西边缘再跨洋回源，按"服务端慢"去改 region 无效、已证伪并回滚。**只看总数时这两次长得一模一样**。）
- **要一条区分度读数把候选劈开**，别靠猜。形态是**改一个只影响其中一段的输入，看总数动不动**：`limit=1` 与 `limit=40` 耗时相同（0.571 s vs 0.574 s）→ 成本是固定开销、不随行数变化，于是"数据量大"这一支被排除。
- **每一段的结论都要有阳性对照**，尤其当结论是"这一段没问题"。判边缘缓存没生效，就去找一条**确实挂着缓存规则**的路径量一次，看仪器报不报得出命中（上面那条 MISS→HIT→HIT 就是它）；量不出命中，说明这次没在测缓存。
- **在部署机上量到的 origin 耗时不是用户的等待**，它少了整条网络路径与客户端渲染。它只能用来给"origin 现算"这一段定值，不能拿去回答"他等了多久"。

**「离读者多远」与「装得下几条」的读数时点**：两者都按定义从**进入时**的视口算起，所以要在你自己这次会话的**第一次滚动之前**取；已经滚过就重载再量。豁免只给「装得下几条」比值的**分子**——最高条目可在滚动加载全量后另量，**分母仍用进入时那次的 band**（实测同一页面只滚动一次，band 从 260 变成 400、比值从 3.46 变成 2.25，两个时点混用等于这个比值没有定义）。

**一屏装得下几条：用 `~/.claude/bin/first-screen-density`，别手写**

```
first-screen-density <url> --items '.card' [--scroller '.feed'] [--viewport 1440x900]
    [--min-visible 3] [--max-item-ratio 0.8] [--band-height <进入时那次的 band>] [--json]
```

退出码：`0` 读数取到且满足阈值 / `1` 未达标 / `2` 仪器故障 / `3` **unresolved——读数不可信，不要读成 0，也不要读成通过**。夹具矩阵在同目录的 `.test.py`，17 条用例，每条都是一次真实误判的固化。

**这一行为什么必须是程序**：同一段量法在本文件里被写错过**四次**，四次都只有真实浏览器跑得出来，而散文没有回归测试——这本身就是本文件「自己写的机制不要让失败与成功同形」的一个实例。四次分别是：只用 `getBoundingClientRect()`（不受祖先 `overflow:hidden` 影响，被裁掉 96% 的卡片照样"在带内"）→ 用 `IntersectionObserver` v1 并声称能判遮挡（实测它对遮挡 / `opacity:0` / `visibility:hidden` / 零高一律给 `ratio 1.0`）→ 四角 `elementFromPoint`（`r.right`/`r.bottom` 是排他边界，对**正常元素**也判 false，八个夹具一律返回 false）→ band 不扣 fixed / sticky 头（实测 800 视口 + 90px 头下，一条穷举所有滚动位置都读不完整的 730px 条目算出 0.912、判"装得下"）。

**判据本身（工具实现的就是这些，你要 review 它或换个环境重写时看这里）**：

- **band** 是进入时用户实际读得到的那条带 —— 文档滚动时 = `documentElement.clientHeight` 减去 fixed / sticky 覆盖层；有滚动容器时 = 对该容器做一次 IO 拿到的 `intersectionRect`（**不是** `getBoundingClientRect()`：容器被祖先裁剪时后者把 196 报成 400，比值低估 2.04×）。band 面积为 0 时密度与比值**无定义**，报"进入时列表不在屏内"，不是报 0。
- **闸①** 是两轴完整包含，且 `intersectionRect` 要盖住整个 rect（把祖先裁剪补进来）。轴向策略在这里显式定死——不要交给 IO 的 threshold 隐式承担：实测 `threshold:[1]` 会让宽度超出视口的元素 `isVisible=false`，横向溢出页因此整页报 0。
- **闸②** 两条路径**永远同时跑**、不一致就报 unresolved。`isVisible` 保守偏 false，已实测的假阴性成因有三：相邻元素的 `box-shadow` 溢出压边（8 条报成 5，同页加 `border-radius` 即翻转）、**退化的零高兄弟节点**（相邻的完整可见条目被判 false）、祖先合成属性（`filter` / `opacity<1` / `backdrop-filter` / `mix-blend-mode` / 非轴对齐 `transform`——实测 `mask` 与 `will-change` / `box-shadow` / `contain:paint` **不**触发）。这些产出的都是**看起来合理的偏低数**，比归零更难发现，所以不能只跑一条路径再自检。
- **`max(itemHeight) / band.height` 的 max 取未经筛选的全部条目**——高过一屏的那条必然过不了闸①，只在筛过的那批里取 max，这个比值就永远报不出 > 1，而抓那条正是它存在的全部理由。
- 分子可在滚动加载全量后另量，**分母仍用进入时那次的 band**（`--band-height`）；同一页只滚一次，band 就从 260 变成 400、比值从 3.46 变成 2.25。

## 先确定有没有参照

「有参照产品时的对比纪律」一节整节都写在**参照已经在场**的前提下——用户点名了某个站，或任务本身就是复刻。但参照常常没被点名却近在手边，而**没人会来告诉你它在**。判据是**它为同一个问题做过一遍决策、而那些决策已经过真实使用的检验**——按这条，同一产品的另一条轨、另一个租户、上一版页面、同一设计稿的移动端实现、同一组件在另一条产品线的落地，都算。同仓已交付的那种往往比外部站更强：它已经被人用过、问题已经被人提过，而且它的取值就是同一套代码在另一组输入下的正确答案。

所以在判定"本次没有参照"之前先找一次。这是个反向断言：说没有参照，会直接删掉「有参照产品时的对比纪律」的全部检查。**并且要报出读数**——按上段那条判据枚举出候选、逐个查过、各自结论（含下段那个最危险的形态），而不是只交一句"本次无参照"：那一句在"认真找过、确无"与"压根没找"两种情况下逐字相同，与本档反模式表里那条"『DOM 里数得出来』当作『用户看得见』"是同一个病。

**共用代码的第二个消费者是最危险的一种**，单独列出来：一段为第一个消费者写的逻辑，会把那个消费者的语义当默认值编码进去；换一组输入就静默变味，而两边跑的是同一份代码，diff 里什么都看不出来。判据不是"我改了什么"，是"同一段代码在两组输入下各产出什么"——只能在两侧各跑一次读数来比。

（实测：一处"哪几档默认展开"的判据按 scope 档名写死。第一条轨有两档命中，每张卡片 81 个可见读数；第二条轨的指标全落在另一档，同一段代码给出 **0** 个——页面上一个数字都没有，而那一页存在的理由就是核对这些数字。改动它的那几次提交里，没有一行 diff 指向这个后果。）

## 有参照产品时的对比纪律

参照产品在跑时，它**本身就是规格**，任何抄录出来的中间清单都只是它的有损投影。

| 纪律 | 内容 |
|---|---|
| **同条件成对测量** | 权威检查是"同一次运行里，把两边放在**同一 viewport / 缩放 / 主题 / 交互状态**下各测一遍再比差"。拿我方对着抄录清单核对，可以全绿而两边仍然不同——因为清单可能本身就漏 |
| **时间维度的同条件** | 上一行列的同条件（viewport / 缩放 / 主题 / 交互状态）只够静态面用。比响应还要另外控住三件事，**每件都要落成读数，不能只写"已控住"**——那句话在认真查过与压根没查两种情况下逐字相同（同本档「先确定有没有参照」那条）。**测量点**：两边都从用户那台机器量，不是各自的部署机；读数是**每次请求各报一次 TCP 连接耗时**——`curl` 里点名 `%{time_connect}`，**不是 `%{time_appconnect}`**：实测那次事故里两个字段朝相反方向读，`time_connect` 恒为 `0.000`（露馅）而 `time_appconnect` 恒约 1.0 s（看着完全正常），取后者的话这条检查在它自己的原始证据上就会通过。判据是它接近 0 而对端在另一个大洲——**但 `0.000` 另有成因**（`file://` 传输同样给 `0.000000`），所以它是一条提示而非判决：同一命令加 `--noproxy '*'` 重跑一次比对才算数（那次 TTFB 从 2.5 s 变成 0.12 s，整张表作废重来）。**缓存冷热**：两边各冷一次热一次，报数写明是哪一次。**网络路径**：报出两边各自解析到的 IP 与边缘节点标识（`eo-cache-status` 一类的响应头），两站 origin 不在同一地理位置、或一边过 CDN 一边不过时，你量到的差可能整个来自往返距离而与代码无关。控不住或读不出的那一项写"未核实（差在哪一项）"，别把差值当成我方的缺陷 |
| **反向完备性** | "我写的每个值都有出处" + "清单每行都忠于参照" 仍漏第三个方向：**参照里有、清单里没抄的规则**。范围内的每个参照组件，要从参照侧枚举其规则，逐条确认我方有对应决策（已实现 / 有理由的接受差异）。缺失的规则在前两个方向上完全不可见 |
| **独有元素交用户裁决** | 上一行只覆盖"参照里有、我方没抄"。反方向——**我方有、参照没有**——在从参照侧枚举规则时结构性不可见：参照侧没有这个东西，枚举不到它。所以范围内每个我方独有元素都要反过来记一条决策：参照在同一位置什么都不放，那是它做过的取舍，不是它的疏漏。默认动作是把「**移除 / 保留**」二选一按 `CLAUDE.md`「Surface Choices」交用户——"缩小、换个视觉语言重塑、移到次要位置"都属保留的子形态，选它仍要先回答留不留，agent 自行挑一个折中不算已处置（executor 是子代理时按 `CLAUDE.md`「非功能属性不自行加码」的两跳：子代理列出这些元素并标注待裁决，caller 履行 surface） |
| **结构先于值** | 先比布局机制（grid/flex、列数、轨道、padding 归属），再比值。机制不同则值再准也对不齐 |
| **叠加而非并排** | 两张图并排放，人眼与模型都测不出 60px 偏移。用差值叠加（difference blend），或算逐行/逐列的墨迹分布曲线再比峰位 |
| **别把参照当唯一真相之外的东西** | 参照站会漂移。要冻结快照并记录哈希；但**冻结的是像素与 CSS，不是"我抄对了"的结论** |

## 必须覆盖的轴

| 轴 | 要求 |
|---|---|
| **缩放** | 浏览器缩放（`⌘=` / `⌘-`）在窗口物理尺寸不变的前提下**缩小 CSS 视口**：Z% 缩放 ≈ 视口宽 `W/Z`。至少覆盖 100/125/150/200%，并在每个断点的 **B-1 / B / B+1** 各取一点——断点两侧归属不同布局 regime，只取整数缩放档会跳过中段 |
| **交互状态** | 只加载不操作会漏掉展开、筛选、搜索、滚动追加、折叠后的布局，**以及每一次操作让他等了多久**。触发之后要取**两样**读数：新的布局，和从动作到画面更新之间的时间。**只取前一样是这条轴最常见的漏法**——交互确实触发过了、状态也确实看过了，这一格于是被标成已覆盖，而响应面一次都没被采样。参照产品的对应状态要同步触发再比 |
| **主题** | light / dark / 跟随系统三态各比一次；有的差异只在一种主题下出现 |
| **内容量** | 空态、单条、满屏、超长标题。参照站与我方内容不同时，比的是骨架与关系，不是文本 |

## 交付前的最低证据

两条。第一条**无条件**，第二条只在有参照时另加。以前这一节只有第二条，于是**无参照的页面在这一节里没有对象**——而那正是最需要它的情形。

**一、以读者身份用一遍，并报出读到了什么、等了多久。** 宣称一个页面"没问题 / 已核验 / 可以交付"之前，不论有没有参照。

- **主干是两问**：① 这次的读者是来找什么的——读完回答他要的答案在不在页面上、在哪、找到它要付出什么（翻几屏、点开几层、先读懂哪个词）。② 他为此要做的那几个操作各让他等了多久——**页面上有可点的东西就至少点一次**，按「测量技术」表那两行取读数。下面那些只是常见的失败形状，**不是完备清单，也不是必填格子**。
- 常见失败形状：答案根本没给、或藏在猜不到的分组里；同一事实两处写法不一；同一句话重复多遍；内部术语原样示人；层级让人判断不出该先读什么。
- **报读数，不报"读过了"**：读到的问题（可以为零）连同上面那两问的答案一起写出来。"我读过了"这句在读过与没读过两种情况下逐字相同，而本节存在的理由就是不让两种结局同形。
- **第二问要报秒数，不报"挺快的"**：形容词在顺滑与卡一秒半两种情况下都写得出来，跟上一条是同一个病。这一问在**无参照**时最容易整段消失——没有对照站，就没有一个数逼着你去量，而"打开看了一下，很流畅"照样交得出去。
- **判为不处置的，逐条交代那条判定**——第一条只管"用一遍并报出读数"，读出来与量出来的东西该交代还是该把取舍交他选，按 CLAUDE.md「本轮取得的认识不得静默消失」与「Surface Choices」判，此处不复述触发词与处置。实测漏法：读者验收报回"未测的那一维在逐片卡片里整个消失"，作者判为"有道理，但本轮不改"，于是既没修、也没写出来，用户随后自己撞上同一处并报为矛盾。
- **重复那一项通读找不到，交给 `~/.claude/bin/page-repetition`**：上面列的失败形状里，只有「同一句话重复多遍」是这个方法的盲区——读者读一屏觉得没问题，问题恰恰是这一屏被复制了 14 遍；要在几十屏里察觉"这句我见过 391 次"，通读做不到。它同时是这串形状里**唯一能被精确测量**的一个，所以归仪器。跑它、把读数（最多重复几次 · 字面重复占已统计正文百分之几）连同上面那四样一起报出来。三条使用纪律：**① 带 `--expect-text`**，否则它分不出目标页与登录页/错误页（两者正文都非空），输出会如实写成未核实；**② 不给 `--max-repeat` 时它退出 0 但首行写「未判定」——那不是通过信号**，别拿它当 gate 过了；**③ 读数干净不豁免通读**——它只数字面重复，同义反复、黑话、层级混乱、答案藏得深一概不管。
- **范围**：读本次声明所覆盖、与读者任务相关且**有限**的内容。无限滚动、虚拟列表、大规模重复数据集上不存在"从头读到尾"——改为分层取样并**写明未覆盖的范围**，别拿抽查冒充通读。

**二、有参照时另做一次用户会做的那个对比**：把两边同时打开、在同一缩放档下逐屏看过、对点名关注的元素做关系测量，**并把用户会做的那几个操作在两边各做一遍、各计一次时**（按上面「时间维度的同条件」控住测量点、缓存冷热与网络路径）。

两条的证据要求不同，别混：

- **第一条**的证据形态可以灵活，但判据是**产出了上面那四样**——① 读者任务的答案；② **各操作的秒数，外加一次首屏读数（取 LCP）**；③ 问题清单**含逐条的不处置判定**；④ 覆盖范围——不是拿出了什么载体。②的两半各有出口：页面无可点元素时前一半写 `n/a(静态页)`、只报首屏那个数，别硬编一个秒数也别留空（同上面「报读数，不报"读过了"」那条里"可以为零"的写法）；而**有可点元素并不免除首屏那个数**——它是响应面定义里的两个量之一，最常见的页面反而最容易把它漏掉。截图与 rubric 只有**与这四样绑在一起**时才算执行证据——单独一沓截图分不出"读过并判断过"与"只是生成了截图"，rubric 里存在一条判据也不证明有人逐条判过。截图对第二样尤其无能：**静止图像里没有时间**。
- **第二条不可替代**：同条件成对观察、关系测量与成对计时必须**真的做过**。截图与 rubric 在这里只能**记录**那次对比，不能顶替它——rubric 里有一条"两边对齐了吗"并不证明有人把两边同时打开看过。

判定来自何种证据要在报告里如实写明——"依据运行时逐值证据"与"我逐屏读过"是两件不同的事，不可互相冒充。

（第一条的出处：一轮交付里元素计数、盒子测量、`innerText.length`、外链状态码、产物 sha256 全部通过，据此宣称已核验；而该页同一句免责在一张表里重复 28 次、内部状态码原样示人，一次都没被读到。该页**无参照**，所以当时这一节整段读起来不适用。）

（第二问的出处：一次"把我方与参照站的页面延迟做全面对比"的任务，用了 `agent-browser` 1036 次、`playwright` 837 次，**浏览器全程在用**——切过 tab、看过筛选后的布局；产出的验收契约是"真实冷连接下**首屏**等待不得显著慢于参照，median TTFB 与 FCP 不超过 110%"。三周后用户报告：交替点击侧栏的两个视图"有明显延迟感"，参照站同样操作顺滑。复盘那次 session 的全文（Claude Code 转录 `~/.claude/projects/-Users-USER-private-project-d/4764add5-916f-4f91-9f18-72ae8059be2c.jsonl`，14.8 MB，词频可当场重跑）：`time_total` 53 次、`LCP` 16 次、`FCP` 15 次，而 `performance.now` **0** 次、`INP`（词边界）**0** 次、"延迟感 / 顺滑 / 交互延迟 / 切换延迟" 各 **0** 次。（**这几个数第一次报出来时是错的**：`LCP` / `FCP` 报成了 176 / 152，因为统计忽略了大小写，而多出来的 160 次全是 base64 随机串里的 `PHDlCp9Nd`、`3puLcPCwg` 一类噪声。**三字母缩写做大小写不敏感匹配，在含 base64 的语料上必然虚高**；错误在把 locator 补进本段、使它变成可当场重跑的那一刻才暴露——这本身就是「取证的充分性」要的那一步。）**观察面整个绑在"打开一个 URL"上，而用户抱怨的动作是"在站内从 A 切到 B"**——后者从来不在被观察的动作集合里，于是每一项检查都真跑了、也都真通过了。）

（把重复交给仪器的出处：同一页全页 105,690 字里 74.2% 是重复的文字，最多一句出现 112 次。后来据本节第一条**逐屏读过并截图**、还按读者路径重写了整页之后再量，仍有 55.9% 是重复——通读两次都没读出它。而一条 `page-repetition` 命令在两个版本上分别报 74.2% 与 55.9%，读数分得很开。）

## 反模式

| 反模式 | 为什么错 |
|---|---|
| 用抄录清单代替参照产品做权威 | 清单是有损投影；它漏掉的规则在所有基于它的检查里都不可见 |
| 只做单元素值断言就宣称视觉对齐 | 值全对而关系错是最常见形态，且正是用户第一眼看到的 |
| 测元素盒当作测文字位置 | inline 收缩与 `text-align` 使两者相差数十 px |
| 不校验可见性就测量 | 隐藏子树里的同名元素给出 0×0 或另一套值，对比静默失效 |
| 「DOM 里数得出来」当作「用户看得见」 | 元素计数在"渲染正常"与"被祖先整块裁掉"两种情况下取值相同，因而不是证据。它骗过自己的方式很特别：人已经打开了页面、也确实在查询真实 DOM，于是产生"我已经站在消费者通道上了"的满足感——而通道之内还分着层 |
| 并排看图找偏移 | 人眼与模型都不可靠；要叠加或算分布 |
| 缩放只取整数档 | 断点中段（如 641–960 的中部）被整档跳过 |
| 一致性断言当合理性断言 | "A 与 B 一致"对"A、B 同错"完全免疫（如 VOL 日期与报头日期都是未来日期而一致） |
| 用 rubric 格子的绿色代替看过 | 判定若来自别处证据，就要写明来自别处；标成"看过"即虚报 |
| 拿"打开这一页"的读数当"用这一页"的读数 | `time_total` / TTFB / LCP / FCP 全绑在**一次导航**上，而用户抱怨的动作是站内切换、筛选、展开——它要么不产生导航（读数不存在），要么从不在被观察的动作集合里。两种情况下这些指标都全绿，与页面真的很快时逐字相同。（**首次进入那一次不在此列**：它本身就是一次导航，**其中 LCP** 正是回答它的对的工具——`FCP` 与 `time_total` / `TTFB` 仍只作分段归因，理由见「测量技术」那一行。被禁的是拿这四个去回答站内的后续操作。） |
| 报一个总延迟数就动手改 | 总数在成因完全不同的几种情况下取值相同（origin 现算 / 跨洋回源 / 边缘未命中 / 客户端渲染），它指导不了任何一次修改，改完也归不了因。先拆段，再对可疑的那段取一条区分度读数 |
| 只量一次就报延迟 | 第二次点的是热缓存加已预热的连接。实测同一路径 MISS 0.216 s → HIT 0.086 s，冷热差 2.5 倍；不写明是第几次，这个数就没有定义 |
