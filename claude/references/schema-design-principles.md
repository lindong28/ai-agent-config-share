# Schema Design Principles

设计与审查**有人类读者的数据契约**的判据——字段名与值会被人在某个界面上读到的 schema：artifact / 交付物元数据、API 响应、事件、配置、报表、导出格式。

**目标**：读者在他实际使用的那个界面上，读字段名与值即能做出他要做的决定，不必去查 schema 文档、不必猜单位、不必分辨哪个字段权威。

**取舍**：偏向**更少、语义更自足的字段**，而非为覆盖而多加；可派生的默认不存第二遍。两处的例外都在「优先级与冲突裁决」。

**这套原则奏效的标志**：消费者拿到一份实例就能用，不来问"这个数是什么单位""数据到底在哪"；schema 演化时旧字段的守护职责有人接手；一次交付的 review 不会发现"改了 description 但界面上什么都没变"。

## 范围与证据面

**适用**：契约被本进程之外的消费者读到，**且**其字段名与值会被人在某个界面上读到。两个条件都要成立。

**不适用**：无人读字段名与值的契约（内部 RPC、二进制协议）——下面多条判据的前提正是"有人读到"，硬套只会稀释判据。

**判不准时按适用处理**，并在结论里写明这是按适用判的。两个高频歧义带，判据如下：

- **同时有人读和机器读**（运维直接 curl 的 status 端点、既被程序解析又被人 grep 的 JSONL）→ **适用**。判据是"有没有人读"，不是"主要给谁读"。
- **部分字段有人读**（一份契约里少数列会被人看）→ 可读性类判据（§2 / §4 / §7 / §8）只对那些字段适用；**§1 / §3 / §5 / §6 / §9 管全字段集**，它们判的是字段该不该在、会不会漂移、引用是否为真、改动带走了什么，这些与谁读无关。不因多数字段无人读而整份豁免。

**证据面**：九条判据均自一族契约提炼——不可变注册记录 + 版化 schema URL + web UI 消费面（案例见文末）。其余类别（API 响应、事件、配置、导出格式）未贡献失败实例，按各条自身的前提是否成立取用；§6 的版本冻结与 §7 的恢复成本都已就地条件化。

**编号冻结**：§1–§9 的编号只增不改，可被外部按 `§N` 引用；每条另有短名，优先按名引用。以下**节标题同样冻结**（外部已按名引用）：「范围与证据面」「三个上游，逐条对应」「术语」「优先级与冲突裁决」。

## 三个上游，逐条对应

本档只写 schema 特有的增量。被引用的判据住在上游，不在此重述——重述会让两处漂移，而读者无法判断该信哪个（这正是 §3）。

箭头方向一律「本档 ← 上游某条」。**上游整档 binding，与本档一起读**；下表标的是每条的主要出处，不是分发边界。

| 上游 | 本档哪条是它在数据契约通道的投影 |
|---|---|
| `human-facing-message-principles.md` | §2 ← 自解释 + 值的呈现服从决策用途 · §9 ← 多个同类值里究竟哪个生效 · §7 ← 维度缺席时不辨来源。**「主视图按决策相关性组织」在本档没有投影**——一份 schema 的字段预算问题按上游那条直接判，本档不重述 |
| `~/.claude/CLAUDE.md`「取证的充分性」 | §4 · §8 |
| `coding-guidelines.md`「Goal-Driven Verification」 | §1 的正向推导 |
| `evidence-sufficiency.md` | §5 的"未能判断"分支 · §8 的取证形态 |

**读者情境的归档**（上游要求必须判定、不得用默认值）：数据契约通道一律按**上下文不在手**——字段名与值会在任意时刻被任意读者读到；"读者拿这段做什么判断"由 §1 的消费者角色 × 决定承担，不另设默认。

引用上游时**取其全部分支**。已知两处最易只抄一半：上游对"检查不成立"给的是"要么报错，**要么把'未能判断'作为可观察状态**"（§5、§7 都用得到后一半）；上游对"维度缺席"给的是"合法缺席只能由目标自身的显式声明确立，**判不出即按覆盖降级处理**"（§7 用得到后一半）。

## 术语

| 词 | 指 |
|---|---|
| **消费者** | 读这份契约的那一方——可以是人，也可以是解析它的程序 |
| **消费方** | 消费者那一侧的实现：渲染界面**与**代码。审查时作为一个"面"来定位 |
| **消费界面** | 消费方里**读者实际读到字段名与值的那个渲染面**——§8 的接地对象。读渲染代码不算（理由见 §8） |
| **原则 / §N** | 本档的一条编号小节。审查时的分派单位是"一条原则"，不是更宽的"维度" |

## 优先级与冲突裁决

**上游判据之间的裁决序由 `human-facing-message-principles.md`「裁决顺序」承载，本档不另立**——否则同一冲突在数据契约与 push 两个通道会得出不同结论。本档判据与上游正面冲突时上游胜；本档只收窄，不反向放宽。

**逃生阀**：承接上游「裁决顺序」的逃生阀（含纯审查场景交 owner、不自行裁定的分支），本档不另述。

本节只裁一件上游没有的事——**要不要为读者自足多加一个字段**。**本档另有几处裁决就地写在小节体内**（§3 的"判不出时按便利类处理"、§9 两支的先后与"§3 那条删侧 scope 同样适用"），它们不上提到这里；在这里找不到 tiebreaker 时先回那一节看，别默认没人裁过。

那一件：加，除非那份拷贝会漂移。§2 与 §3 多数时候不是对手（§9 的 `declared_*` 一支给的正是让两边同时成立的路径）；只有当拷贝既必要、写入路径上又没有能拒绝的点、**且 `declared_*` 那一支不成立**时才是真冲突——此时按 §9 的分支次序走到"回到单一 home"，它的两条路也不可行时走上面的逃生阀，别为了裁出一个结论而牺牲"读者会做错决定"这一档。

**§4 与 §6 是硬边界**，先满足再取舍；两者相撞（已发布版本上的可见层修正）在 §4 末段裁。

**发现的严重度另按此序**（与上面的判据裁决序不同轴）：不可恢复 / 已污染不可变记录 > 读者会做错决定 > 两处会漂移 > 字段冗余。

## 1. 消费者与界面先行

**每个字段都要能回答：谁、在哪个界面上、读到它之后做什么决定。反向同样要问：每个消费者要完成的事，有没有哪件在 schema 里没有任何字段支撑。**先列消费者角色与他们各自要完成的事（取数、复现、审计、排障），再从这些事反推需要哪些字段——而不是先罗列"关于这个对象我知道什么"再挑进 schema。

**消费者不限于人。**解析与身份所需的键（版本号、id、内容哈希）、以某字段为条件的校验 / 路由 / 分支（见 §6）、消费者此刻未知的审计溯源字段、以及**字段的存在或必填本身即某条不变量的唯一载体**（没有代码读它，但"缺它就不许发布"是流程要求），都是合法理由。对这类字段，问题换成"它缺失时哪段逻辑或哪条不变量失效"，而不是"哪个人读它做决定"。

**删的那一侧有 scope**：本条按消费者需要反推字段集，前提是**字段集由你决定**。以对源保真为价值的镜像 / 透传契约（CDC、webhook 转发、原样导出）不适用删的一侧——那里字段存在的理由就是源侧有它，按当前消费者筛一遍等于造一个有损投影，而下一个消费者要那列时源可能已过保留期。要删须先证明源侧该字段确已不可能被需要。

同一份 schema 常被多个界面渲染，同一个字段在不同界面上的可读性不同：一个在 JSON 文件里清楚的名字，在只显示键值对的表格里可能无法解读。**逐界面判**——你要为哪几个界面宣称可读性，就要在那几个界面上判。

flag：
- 字段的理由是"这个信息我们有"，而不是某个消费者的某个决定、或某段逻辑需要它。
- 消费方为这类信息预留的原生结构槽位空着——信息完全缺失、或挪进了自定义字段，都是用错槽位，读者不会在他预期的位置看到它。
- 两个生产者、两类交付在消费界面上分不开：缺一个区分它们的字段。
- 只在 schema 文件或 JSON dump 里判过可读性。

自检：删掉这个字段，哪个消费者的哪个决定做不了、或哪段逻辑失效？都说不出，**且删除不带走任何不变量（§6）**，才删。反向：消费者要完成的每件事，都有字段支撑吗？

## 2. 字段自足

**读者在界面上只看到字段名和值。任何理解该值所必需的那一位信息，要么在名字里、要么在同屏的伴生字段里**——不能只在 schema 的 `description` 关键字、外部文档或作者的脑子里。

同一缺陷有多种形态，共同点是**理解该值所需的信息落在读者视野外**。已反复出现的两种：

- **数量缺单位**——`total_bytes`（写进名字），或 `record_count` + 伴生字段承载口径。伴生字段的取值须收敛、不可自由文本漂移，故一般是 enum。
- **位置 / 引用缺 kind**——值合法但指向的地方没有读者要的东西。凡存在"值合法而语义为空或例外"的情形，就需要伴生字段说明属于哪种情形。

flag：
- 同一个字段在两类交付里语义不同，靠上下文区分。
- 理解该值所必需的那一位信息只写在 `description` 关键字或外部文档里。
- 读者要先知道"这是哪种交付"才能读懂某个值，而 schema 里没有字段告诉他是哪种。

**伴生字段的读者须有资格知道那一位信息。**跨信任边界时（同一事实的对外契约与内部契约受众不同），正确解法是按受众切分契约——对外那一份保持不自足，解释住在受控通道里——而不是在低权限那份里补全语义。

自检：把这个字段名和值单独抄给一个没读过 schema 的消费者，他会不会解读错？

## 3. 可派生的事实不存第二遍

**可以从别处推出的事实不存第二遍。**两个成本，第二个常被忽略：

1. **漂移**：两处会漂移，而读者无法判断该信任哪个——他会信错的那个。
2. **核对成本**：即使写入端杜绝了漂移，读者也**看不出**两个字段之间存在计算关系；他必须查描述或读实现，才能排除不一致。

本条只判**删不删**。判下来该留的，那份拷贝怎么活由 §9 接手——不论它是因为读者算不出而留，还是因为别处强制它存在而留。

**第二个成本只裁便利类冗余。**判据不是它长什么样，而是：除了"省读者或查询方一步"之外，**还有没有别的东西强制它存在**——本档任一条、上游判据、外部兼容或合规要求…任一成立即不按便利类裁，交 §9。接地要指向**存在理由**（schema required、写入端**以它为条件**的分支、文档化的解析键），不是"有人校验过它的值"——后者恰恰是 §9 给投影的强制形态，拿它当豁免会把最该判成投影的那一类反过来放掉。判不出时按便利类处理——**但先分清"查不到"是这个字段没接地，还是这类契约根本没有可查的地方**：无 schema 的 JSONL / 导出格式里，接地只能来自消费方代码或文档，那时按"有没有具名消费者以它为条件"判，不要拿契约形态当证据去删一个已交付的字段。便利类之内，**最小性优先**。

**删的那一侧有 scope，按字段判、不按契约判。**问的是：**这个字段在这里存在的理由，是不是"源侧有它"**——保真搬运（§1「删的那一侧有 scope」的镜像 / 透传契约是它的典型），或从更早的交付原样搬来的快照值。是，才在豁免里；本交付自己算出来的不在，哪怕整份契约自称原样导出。快照那一类还要求交付层说得出它凝固在哪一刻、来自哪份上游；说不出就交 §9。

出口：**读者在需要该事实的那一刻算不出它**——输入不在他那一刻实际拿到的那份 payload 里（列表投影、slim 缓存、分页会裁掉它），推导本身他在那个界面上做不了（哈希、跨对象聚合），或推导代价随契约规模增长而那个界面有固定预算（有界请求路径、交互式列表页）。凡以代价立论的**须给出规模与预算**，"查询会慢一点"不算。

**出口按承载层成立，不按事实成立。**多层架构（权威 store → slim 投影 → 交付文件 → 渲染面）里，投影只落在挣得出口的那一层；它上游的每一层仍各自按本条判，除非那一层自己也挣得出口。结论里写明成立在哪一层。

**界面在你的交付范围内时**（同一 repo / 同次交付的渲染面、SQL 投影），"该界面算不出"**不构成出口**——先问该不该在那个界面上补上输入。否则这个出口由被审方自己控制：想留一个冗余字段，只要留一个不投影其输入的窄界面。补输入本身有代价时，同样按上面那条给出规模与预算。

flag：
- 值由消费者在那一刻**已经掌握的任何东西**唯一确定，却仍独立存储——推导输入必须与值同行（`location_kind` 之于 `data_roots[].kind`；聚合字段之于它同屏的来源数组）。输入靠读者的**取回方式**才在手（请求地址、目录位置）时不算：payload 一落盘或被转发，那个输入就不在了。

自检：读者手里那一份 payload 的其余内容，**是否已经唯一确定这个值**——不论它有没有在别处被写下来（聚合与纯函数组合都算，一个 4 元素数组里没有任何地方写着 `4`）？确定了，再问它还有几处**可以被独立写入的承载**（字段、地址段、文件名、复合值子串、面向人的散文，任何形态）。多出来的那份读者自己算得出、契约内又查不到强制它存在的接地，就删；其余交 §9，别停在"算不出 → 保留"。

## 4. 修在缺陷所在的层

**缺陷在哪一层，就必须在那一层修。**最常见的走偏是只改 `description` 关键字：当消费界面渲染的是名和值时，那等于没改——作者觉得问题已解决，而读者看到的东西一个字节都没变。

字段名有歧义 → 改名或加伴生字段。约束不够 → 加约束。语义没人校验 → 加写入端校验（§5）。

**前提是该界面确实不渲染 description**——按 §1 逐界面确认过。Swagger / OpenAPI 页 / JSON-Schema 驱动的表单会把它渲染成帮助文本，那里 description 就是读者可见层，改它就是对层修复。

**缺陷所在层本轮不可变更时**——已冻结的版本（§6）、或那一层根本不在你控制下（缺陷在第三方的字段名里）——本轮的交付是：在你能改的层做补偿（投影层重命名、渲染层标签映射），**加上**点明残留、由谁在何时在正确层修。已冻结版本是它的一个实例：本轮只改 description 不算修好，只算把修正推迟，且**已发布的那份文件本身不再触碰**（§6）——修订说明必须点出下一版本的字段变更，否则仍按未修处理。

flag：
- 一轮修订只改了 description / 注释 / 文档，而原问题是"读者读错了"或"坏值没人拦"。
- 修订说明写着"已阐明语义"，但缺陷所在层没有任何可检的差别。

自检：缺陷在哪一层？这次修订在**那一层**留下了什么可检的差别——界面上的可见差别，或此前被接受的值现在被拒？都说不出就是没修。

## 5. 形状之外靠写入端

**约束语言（JSON Schema 的 pattern / type / enum 一类）能表达"长什么样"，不能表达"指向的东西真的存在""两个字段互相自洽""这个引用在那个 commit 上解析得开"。**这些要在写入路径上校验，否则一个形状合法而语义为空的值会被接受，并在不可变记录里固化成死引用——它在写入时不报错，在需要它的那天才失效。

**引用在写入时不可解析、或在写入路径上解析代价不可接受时**（前向引用、离线写入、非单调可见性；高吞吐摄入按每条事件一次远端解析会把可用性换给校验），按上游的第二分支处理：用伴生字段声明"未能判断"这个可观察状态、以及由谁在何时完成解析验证——而不是让形状校验冒充语义校验，也不是硬校验到吞吐塌掉。

flag：
- 一个引用字段只有 pattern 约束，写入端不验其可解析 / 存在。
- 两个字段描述同一事实的不同侧面（计数与清单、声明与实测），schema 没有、写入端也没有一致性校验。
- 把"pattern 通过"当成"值有效"。

自检：一个形状完全合法但语义为假的值，会在哪一步被拦下？答不出就是没有拦。

## 6. 演化即接手

**改动是显式的，被它带走的东西是隐式的**：字段守护的不变量、历史值的合法性、按版本地址引用它的消费者——这些都不会报错。

- **删字段带走它守护的不变量。**删改前先问：现有代码里有哪些检查以这个字段为条件？这些检查的目的还在不在？还在的话谁承担？
- **改名后旧名仍被接受**（约束语言默认不拒未声明的键），于是新旧两套值可以同时进入记录并互相矛盾。
- **收紧取值域使历史值非法**；**把 optional 改成 required** 使历史记录集体不合规。
- **一旦发布到版本化地址即冻结。**形状变更必须走新版本，包括"只是放宽一个 pattern"这种看起来向后兼容的改动。版本号只增不复用：同一地址在不同时间返回不同 schema，是审计与缓存的最坏情形。"查不到有人引用"**不构成豁免**——镜像、HTTP 缓存与 vendored 副本不可观测。**形状的**原地修改只在该地址从未对外发布过、或该版本被显式声明为不稳定预览时成立。冻结禁的是**静默**原地变更；已发布版本本身有害而必须撤回或订正时（泄露、或某取值会让消费者错误处置数据），带公示与记录地撤回 / 订正是另一种动作，走它，不走静默改写。

flag：
- 删了字段，而以它为条件的校验、分支、路由随之消失，没有替代。
- 改了 schema，却漏掉依赖旧形状而**不会自动报错**的东西——它们不因改名失败，只在下次有人跑时失败。
- 为一个小修正原地改已发布版本的 schema。

自检：这个字段现在被哪些代码当作条件？删掉之后那些条件怎么办？这次改动会让哪些已存在的值变得不合规？

## 7. 必填性看恢复成本

**一个字段"可选"，说的是语法；读者听到的是"以后再补也行"。当补不了时，这个词就是错的。**记录不可变、字段不参与去重身份、下游已消费、源已删除无法重算——任一条成立时，漏填的恢复成本可能是重发一个完整版本，甚至无法恢复。

语法上无法必填时（需兼容无该概念的交付），把终局性写在读者会读到的地方，并**区分"不适用"与"忘了填"**：按上游，合法缺席只能由目标自身的显式声明确立，判不出即按覆盖降级处理——也就是当作"忘了填"而非"不适用"。

**生产者在写入时合法地不知道该值时**（异步补齐的下游标识、跨系统才能确定的归属），正确解法是显式的未知态字段 + 谁在何时补齐（同 §5 的第二分支），**不是必填 + 哨兵值**——`unknown` / `-1` / `""` 与真值在界面上不可区分，而缺失至少是诚实的。

flag：
- 字段标为可选，而漏填后的补救路径是"发一个新版本"或"改不了"。
- 可选性的理由是"有些交付没有这个概念"，但没有任何字段区分"不适用"与"忘了填"。

自检：如果发布后才发现这个字段填错或漏填，恢复要做什么？做不到就不能只说"可选"。

## 8. 断言对实例取证

读 schema 文件发现不了消费界面上的问题——读它在"呈现正确"与"呈现错误"两种情形下输出相同。

**任何关于"值长什么样"的断言（pattern、示例、检查步骤、文档里的形状描述）必须对真实产出的实例核对过**，不用手写的示例——手写实例会带上作者以为的形状。凭对构造逻辑的记忆写下的判据会错，而且错得比原缺陷更隐蔽：它读起来更具体、更专业，因此更难被怀疑。

**交付前要在消费界面上看过实例**，覆盖到你要为其宣称可读性的每个界面。门槛不是"看一次"，而是**必须张开这两个维度**：

- **每一类交付各取一个实例**——同一字段在两类交付里语义不同，只有并排看才显形。
- **让多个交付在同一界面上共现**——多个交付坍缩成一个节点，单个实例的界面上看不到。

**三层观察（值 / 关系 / 结构）按界面形态取**：界面是网页时方法见 `web-ui-observation.md`；非网页面（manifest 文件、API、日志、CLI 输出）三层取 值 / 字段间关系（计数与清单是否自洽、引用是否指向真实位置）/ 记录与节点结构（多个交付是否坍缩）。

**消费界面不可达、或首次生产前尚无真实实例可取时**，显式把这个缺口交决策者裁决（阻塞还是接受），不得静默跳过；接受时把界面观察记为交付后必须补的义务，并在结论里标注未接地。

flag：
- 检查步骤描述了值的形状（"以 X 结尾""包含 Y"），而没有对照过任何真实实例。
- 只在 schema 文件或渲染代码上验证过，没有在消费界面上看过（该契约的 dump / manifest 文件本身就是消费界面时不算——那时它就是读者读到的那个面）。
- 用"schema 校验通过"代替"消费界面上呈现正确"。
- 只取了一类交付的一个实例，就宣称接地完成。
- **某个字段在该界面上根本不显示**——渲染端忽略了它，schema 里有、读者看不到。

自检：我关于这个值形状的判断，来自真实实例还是来自我对代码的记忆？我有没有在读者实际读到的那个面上看过它？

## 9. 多处承载要有权威和拒绝点

§3 判完删不删；判下来该留的从这里接手。**多出来的每一处承载都要回答两件事：谁权威，不一致的值在哪一步被拒。**§3 那条删侧 scope 同样适用这里——存在理由是"源侧有它"的承载不按本条判回删除。

指定唯一权威，把另一处标注为投影——**标注要落在读者那个面渲染的那一层**（名字，或同屏的伴生字段）。只写在 `description` 关键字、外部文档或作者脑子里等于没标（同 §4）：读者屏上仍是两个值并列，没有一位信息告诉他哪个是投影。

再让不一致的值**写不进去**。两种形态：由权威在写入时构造派生（`b = f(a)`），或写入路径上的断言。**两者都按拓扑判，不按单点代码判**——`b` 在这份契约里的**全部**写入者是否走同一个 `f`、`a` 是否只有一个来源。多个生产者各自派生（不同脚本、不同 stage、常驻旧代码的 worker）时逐处都"无分叉"，合起来仍会分叉。共享写入库、单一 stage 实现、摄入网关都算那个必经点，上千个独立 worker 经同一个摄入口仍然有点；生产者个数本身不是判据。**必经点也按承载层判**（同 §3）：某一层只有一个写入者，不等于它上游那层也只有一个；"现在只有一处写它"是快照，"以后不会有第二处"才是要论证的属性——论证不出就按有多个写入者判。

只能在写入**之后**发现不一致的不算强制，除非那道检查是所有写入者必经的闸门、且失败即阻止那一步。**"不可再拦"按该值第一次离开写入方、被别的东西保存或再消费的动作定位**——返回给调用方、落盘到别的进程会读的地方、进任何跨 run 复用的存储、导出、注册都算；一条链上有多个这样的动作时取**最早**那个，不按"交付时刻"。说不出该动作上游的写入者集合，就按没有闸门判。"约定它们一致"从来不算。

强制落不下去时：

- **写入之后没有再次强制的时机**——判据是**这份承载在写入之后还会不会被任何写入者重写**；不会，读者手里那一份就不跟着权威变，此时"标注为投影"反而主动误导（读者以为它会跟着变）。§7 那四条是常见成因、不是充分条件：命中其中一条而该值仍会被下一批覆盖（`latest-row-wins` 的 store、下游已消费但本契约仍在重写）时归下一支。**这一支不是删除，且优先于下一支**：拷贝不追随权威时，删掉并不能让读者拿到该事实。名字要暴露这个值**凝固在哪一刻、来自谁**（`declared_*` 一类），并在能触及的生产点上做生成时核对；核对代价不可接受、权威当时尚不存在（前向引用）、或**凝固时刻与来源本身说不出**（含 §3 转来的那一类）时，走 §5 的"未能判断 + 谁在何时"，而不是回退到删除、也不是编一个时刻。
- **拷贝仍会追随权威，但写入路径上没有必经且能拒绝的点**——**回到单一 home**：不存第二遍，或让投影只由唯一权威生产者产出。两条路都不可行时不自行裁定，走「优先级与冲突裁决」的逃生阀。

flag：
- 两处存同一事实，而写入端不强制一致。
- **读者在他要为其宣称可读性的那个面上，分不出哪个权威、哪一处是投影**——schema 完全没说，与只在 `description` 里说了，是同一条的两种形态。
- **第二份拷贝落在读者的比对单位够不到的地方**——他比对的是字段值整体，藏在复合值子串、对象地址 / 文件名、或面向人散文里的那份他不会去核对，漂移因而无人发现（版本号既在 URN 又在 URL；时间既是 `created_at` 又是分区路径）。

最后一条该取消的是读者比对不到的**那份承载**，不是他比对得到的那个字段。承载被别处强制存在而取消不了时（§6 要求地址带版本、命令串里的 id 拿掉命令就跑不了），退回上面的写入端强制。

自检：权威是谁，标注在读者看得到的那一层吗？**这份承载写完之后还会被重写吗**——会，就说出不一致的值在哪一个动作之前写不进去（"我们有测试"要能说出它拦在哪一步；答不出那一步就是还没强制）；不会，就说出名字交代了凝固在哪一刻、来自谁，谁在何时做生成时核对（说不出就走 §5 的"未能判断 + 谁在何时"）。

## 反例改写（artifact facet contract v1→v5，2026-08-04）

一份预处理交付物的元数据 facet，消费界面是 lineage web UI。v2 的一次修订**只改了两条 description**，用来消解 `clip_count` 的歧义（标签库里是 clip 行数，源视频盘点里是 3 个完整视频）。作者视角问题已解决，实际效果为零——UI 渲染的是字段名和值。

| 现象 | 违反 |
|---|---|
| 计数字段一名两义，靠交付类型区分 | §2 |
| UI 上唯一的位置字段指向只有 manifest 的空目录 | §2 |
| `-dirty` 后缀把"不可复现"这个例外编码进 commit 值本身 | §2 |
| 上游引用同时存在于 `inputs[]` 与一个元数据字段，声明"必须一致"而不强制 | §3 成本 1 → §9（无拒绝点，v3 回到单一 home） |
| `dataSource.uri` 指逻辑名家目录、`data_roots[]` 指版本字节，两个位置值并存而 schema 没说哪个权威——写 eval 脚本的人据此断言错了目标 | §9 flag 2 |
| 契约版本既编在 schema URL 路径里又是一个字段；两处 eval 写死 `/1/` 而契约已到 v3/v4，三轮迁移无人发现 | §9 flag 3（比对单位够不到） |
| 聚合字段与它的来源数组在同屏并列，写入端强制一致因而不会漂移，但两者的计算关系只写在 schema description 里，界面上看不出 | §3 成本 2 |
| `location_kind` 与 `data_roots[].kind` 同屏并存——前者是后者的便利聚合，由工具强制因而无漂移、关系也可查，读者仍无法一眼看出存在计算关系，得回头问作者两者什么关系才敢用 | §3 最小性优先 |
| 只改 description；且就地改在已发布版本上 | §4 / §6 |
| `path@40hex` 形状合法即通过，路径未被跟踪也接受，成为死引用 | §5 |
| 删 `stage` 时，以它为条件的"值须与 --stage 一致"校验一起消失 | §6 |
| 三份 schema 均无 `additionalProperties: false`，旧名仍能进记录 | §6 |
| **缺一个区分生产者的字段**，所有交付在图上坍缩成一个作业节点 | §1（反向） |
| 表格列结构的原生槽位空着，列信息哪儿都不在 | §1 |
| 列信息不参与去重身份 + 记录不可变 → 漏填无法补，却只标为 optional | §7 |
| 修 bug 时新写的判据"路径须以版本结尾"与真实值不符（版本在倒数第二段） | §8 |

v3–v5 逐版按上述判据重做后，同一批交付在 UI 上的列数从 0 变为 33、多个交付不再坍缩到同一作业节点、位置字段指向真实源根。**这些差别只在真实消费界面上可见**——读 schema 文件无论多仔细都发现不了。
