# review-cli-output

审核对照 `~/.claude/references/cli-output-review-principles.md`（**P0** 读者情境与视图分段、P1–P7）与其配套的 `~/.claude/references/human-facing-message-principles.md`（§1–§4）——**两档一起读**，判据全部住在那里，本命令只负责流程与证据纪律。展示与提问风格遵循 `~/.claude/references/deep-discuss-style.md`。

## 输入与证据边界

- 必需：`$ARGUMENTS` 中粘贴的终端输出，或包含该输出的 capture 文件路径。没有实际输出时先请用户提供；只有脚本而没有输出不能替代本命令的用户视角证据。
- 可选：output owner 的定位提示。**output owner** 指负责生成该输出、因而应承载修复的 artifact——它就是共享档逃生阀所称"消息 owner"在终端通道的实例。仅当 capture 或执行上下文能把输出可靠绑定到当前项目时，才在审查后定位；否则保持 review-only。

## Gate 与封锁范围

命中 gate 只封锁**依赖该前提**的部分，其余照常——**不是整体中止**：

| Gate | 封锁 | 仍然要做 |
|---|---|---|
| 没有实际输出 | 全部 | 先向用户索取；只有脚本不算 |
| 输出无法可靠绑定到项目 · owner 定位不了 · 合适的 owner 不可改 | 落地与复验 | 审查照做，按「交付」以 review-only 形态给出 |
| P5 的契约 authority 缺失或歧义 | **仅**涉及状态词 / 退出码 / stdout-stderr 分流语义的那几项修复 | 其余修复照做——措辞、换行、分组、结论前置这类无取舍项不受影响（P5 原文即局部停止） |
| 目标无法安全执行、或无权在目标环境执行 | 该状态的 capture 构造与该部分复验 | 把未覆盖的态列为未核实项后继续，别把静态推断写成已通过 |

任一 gate 命中 → 交付里逐条列出未核实项，**不宣告通过**。

## 输出类型 × 判据入口 × 必须覆盖的状态集

类型判定见 P2。**状态集是取证义务，在下面第 1 步就要用**——不是只在复验时才需要：

| 类型 | 判据入口 | 必须覆盖 / 构造的状态 |
|---|---|---|
| **action 型** | P0、P1、P3、P5、P6、P7 + §1–§4 | already-ok、installed/updated、skipped、blocked/failed，以及适用时的部分成功或提前停止 |
| **status 型** | P0、P1、P4、P5、P6、P7 + §1–§4 | 健康、降级、不可用、**未测 / 探测失败**（P4 的「四态可分」那一问；末态最易漏，且它正是共享档 §2 结论作用域的核心） |
| **两者都要**（如 `status --repair`） | 上两行判据入口的并集 | 上两行状态集的**并集**，另加"修复后的状态报告是否反映本轮动作结果" |
| **查询报告型**（`list` / `show` / `diff`） | P0、P1、P5、P6、P7 + §1–§4（**不套骨架**） | 无状态态可枚举；覆盖空结果与典型非空结果 |

P0 对四型一律适用——包括用途轴归档（该视图承载状态结论还是本身即测量/排障产物）与"未分段混合体即一项 finding"，后者不依赖任何骨架成立。

## 工作流

### 1. 取证与审查

**只读输出这一条先立**：审查阶段不读 output owner 及其实现源码（含产生该输出的子进程与依赖库），也不因知道实现意图而替含糊输出补义。带 `output-owner-hint` 调用时同样不得先打开它确认——hint 只用于第 3 步。这能防止实现知识掩盖用户实际看不懂的地方。

**契约接地（冻结 finding 前完成）**：P1 的整体例外与 P5 的状态词 / 退出码 / 流分流三类判据，成立与否取决于契约而非输出文本。读该输出的 published contract（README、`--help`、文档）与（若有）machine consumer 的契约，**仅**用于裁决这几类 finding；不读实现。契约缺失或歧义 → 按上表**只**停这几项，不把猜测硬化成 finding，其余审查与修复照常。

**审查序列**：P0 判用途轴与视图分段 → P2 判类型并按上表取判据入口 → 走对应骨架与其余判据。

**capture 覆盖**：按上表构造或索取状态集；**构造需要产生副作用时先走第 2 步的执行副作用闸门**，别在取证阶段就把安装器或部署脚本跑掉。拿不到时列为未核实项——但注意分工，别因缺态搁置本可当场判定的项：

| 在 healthy 一份上就必须判完 | 需要降级 / 未测 capture |
|---|---|
| 结论位置（是否在末行）、维度命名是否为实现术语、版式层面的主次（明细与结论是否同权同位） | 四态可分、结论作用域是否越界、非健康维度报的是影响还是内部状态名及动作是否明确（P4 第 3 问）、异常项在实际渲染下的突出度 |

交付：简明 verdict、按该类型对应可判读单元逐项的判读表（执行单元 / 被检查维度 / 查询结果分组）、无法回答的问题、按用户影响排序的 finding。形式服从内容，不强制套统一模板。

### 2. 决策

存在真实取舍时用 `AskUserQuestion`：

- **P1 的接口迁移**：把机器格式移到 `--format=kv` / `--json` 之后会波及既有 machine consumer → 先 grep 出真实消费者，把"消费者清单 + 迁移路径 + 不迁的代价"作为选项。别自行判定"有人在解析所以不能改"——那是要 surface 的迁移成本，不是豁免。
- **P5 的兼容取舍**：状态词、退出码、stdout/stderr 分流的语义变更。
- **读者情境归档判不准**（P0 的用途轴两义，如 `status --verbose`）：可提问时交用户；无提问通道时**把两种归档与各自结论并列写进发现清单交 owner，禁止自行裁定**——归档挑反会让整批 finding 失效，而交付里不会暴露它是猜的。
- **执行副作用**：需要真跑目标或改动真实服务状态才能构造 capture 时（安装器、部署 / 迁移脚本，或为造"降级"去停服务），先列出"将运行什么 / 影响哪个环境 / 回滚方式 / 不跑则哪些态列为未验证"再问。副作用完全限于一次性沙箱时才自决。
- **多候选 owner**：候选 ≥2 且持久性不同（生成器 vs 已渲染产物、上游 vendored vs 本地 wrapper）时，把候选清单 + 各自"改这里会不会被下次生成覆盖"作为选项。改错一侧会让修复静默失效且自认为成功。

没有真实取舍的措辞、换行、分组、结果汇总由 agent 直接完成。

### 3. 落地

修改 output owner，使输出解决已核实 finding。**迁移类修复的写入范围含用户已批准清单上的 machine consumer**，不止 owner 本身。修复用户可见结果层，保留必要诊断信息但让它从属于对应单元（P6）。

### 4. 复验（仅在第 3 步发生了修复时）

未执行修复（review-only、或未定位到 owner）→ 跳过本步，直接交付审查结果与未核实项。

**重新 capture 修复后的输出，再次只按该类型的判据入口判断**；实现代码本身不能作为输出已清楚的证据。核对真实退出码、继续/停止边界，以及未执行或未覆盖范围与输出是否一致。发生过接口迁移时另核 **machine consumer 迁移后的实际执行结果**，不可执行则进未验证项。仍有 finding 就继续修复和复验。

## 交付

当前 verdict、按类型对应可判读单元的结果、remaining finding；若执行了修复，补充修改的 output owner 与 consumer、实际验证结果、未验证边界；若未修复，说明命中了哪个 gate。

**无条件执行**（含 review-only 终态——那恰是只有 finding 没有修复路径、判据缺口最值得上报的场景）：若审查发现现有判据未覆盖某类输出问题，用 `AskUserQuestion` 把「是否改进 `cli-output-review-principles.md`（通道无关的部分改 `human-facing-message-principles.md`）」作为一项决策交用户拍板——判据缺口是高杠杆发现，附带提及会被略过、同类坑复发。（本仓未收录专审 meta-原则的 `/custom:review-principles`，改后的判据档不再另跑一轮 meta-原则审查。）
