# review-schema

输入 (`$ARGUMENTS`)：schema 文件路径或项目根（默认当前工作目录），可附加提示（如"schema 在 schemas/、消费界面是 :8933 的 lineage UI"）。下称被审对象为 **schema**。

审核对照 `~/.claude/references/schema-design-principles.md`（下称**判据档**）。它与 `~/.claude/references/human-facing-message-principles.md` 的分工、术语（消费方 / 消费界面）、以及判据冲突与发现严重度的两个排序，都由判据档自身定义——本命令不复述，只编排。

## 工作流

```
定位 ─→ 接地 ─→ 审查 ─→ 决策 ─→ 落地 ─┐
         ↑                              │
         └──────── 有改动则回到接地 ─────┘
```

接地是循环的一个节点，不是一次性前置：修复引入的错误判据只有重新接地能挡住。终止条件唯一——**落地未产生改动即终止**（用户已裁决保留或延期的发现不计为待处理）。

两个 gate 会封锁部分环节，命中时按此表处置，不静默降级：

| Gate | 封锁 | 仍然要做 |
|---|---|---|
| 不适用（无本进程外的消费者 / 无人读字段名与值） | 全部 | 报告不适用并结束。**判不准按适用处理**，不得据此终止——判据见判据档「范围与证据面」 |
| 消费界面不可达且用户选择接受 | 接地的界面观察、落地后的复验 | 审查/决策/落地照做；复验记为交付后的 live 义务；结论标注未接地、**不宣告通过** |

展示与提问风格遵循 `~/.claude/references/deep-discuss-style.md`（本命令自身适用；不下发给 subagent，见「反模式」）。

### 0. 定位

一份 schema 的问题分布在四个面（下表四行），缺任一面都会漏判——只审契约定义本身会系统性错过写入端的语义校验与消费方的空槽位：

| 面 | 找什么 |
|---|---|
| 契约定义 | schema 文件、类型定义、字段常量表；有版本时列出**全部已发布版本** |
| 写入端 | 构造与校验该 schema 的代码——形状之外的语义校验、跨字段一致性、未声明键的处置 |
| 消费方 | 渲染它的界面与代码，以及它原生就有而可能空着的结构槽位 |
| 跟随物 | 文档、示例脚本、行为 eval、手工脚本——**尤其不被自动化收集的那些**（改名不会让它们报错，只在下次有人跑时失败） |

另需一项**没有上游能提供、只能现场产出**的输入：**消费者角色 × 每个角色要完成的事**（取数、复现、审计、排障）。判据档 §1 的正反两向都由它支撑——尤其"该有的字段缺了"只能由它发现；没有它，审查只能判"现有字段对不对"。

第 0 步枚举出多于一份人读契约、或该 schema 有多个交付类型时，把候选整理成 `AskUserQuestion` 让用户选定审查对象与接地实例；**多交付类型时至少取两类**，否则"同一字段在两类交付里语义不同"结构上不可见。只有一个候选时不问。

### 1. 接地

判据档 §8 要求对真实实例取证并在消费界面上看过；本步是它的执行位。

- **取真实产出的实例**，按上一步选定的交付类型各取一个（不用手写的示例）。
- **在消费界面上看过**：三层观察按界面形态取，方法见判据档 §8。
- **把 schema / 文档 / 检查步骤里所有"值长什么样"的断言逐条对照实例**。
- **重新接地时若"产出新实例"本身不可逆**（有版本、记录不可变、发布即冻结——产出一条新实例等于消耗一个版本号或在共享存储里落一条记录），经 `AskUserQuestion` 定产出方式：① staging / dry-run 写入端产出（不占版本号）② 切真实新版本产出（代价：版本号只增不复用）③ DEFER——记为发布前必须补的接地义务。契约无版本或可重发（API 响应、可重放事件）时不必问，直接产出。

把实例、界面观察结论、断言核对结果带进下一步——subagent 必须对真实数据判定，而不是对 schema 推理。

### 2. 审查（每条原则一个 subagent，并行）

判据档的**每条原则各 spawn 一个 reviewer 并行**审查整个 schema 面，确保每条获得充分注意力。用 readonly 类型是因为 subagent 的契约就是"报发现、不改文件"，而被审对象常是不可变记录——越权写入不可撤销。通道按 `~/.claude/references/delegation-policy.md` §Transport selection 判；走 in-process 时用 `general-purpose-readonly` 且**不传 `name`**。

每个 subagent 的输入：

- 判据档全文（相邻原则提供边界；明确告知只应用指定那一条原则）
- `~/.claude/references/human-facing-message-principles.md`——**每个 subagent 都给**：它整档 binding，判据档「三个上游」表标的是每条的主要出处、不是分发边界，按那张表裁剪分发会让某几条原则拿到空壳。用途是为你负责的那条原则提供判据，**不要把纯上游违反当独立发现报出**，除非它构成你那条原则的一个实例
- 第 0 步的四面清单（含全部已发布版本）与消费者角色 × 决定
- 第 1 步的实例、界面观察结论、断言核对结果

每个 subagent 只输出其负责**那条原则**下的违反 / borderline 发现（定位到具体字段 / 文件 / 行），给出最小通用修法，**不修改文件、不发 `AskUserQuestion`**。

汇总去重，标注每条发现来自哪条原则，按判据档的**发现严重度序**排列。

### 3. 决策

整理为 `AskUserQuestion`，附你的判断与理由。三处注意：

- **不预设修复让用户照单全收**；真取舍（字段命名、要不要切新版本）是用户的。
- **一个发现要否决另一个时**，先独立核实它依赖的存在性事实——subagent 会臆造"某字段 / 某校验存在"。
- **改动落在已发布版本上时先摆出代价**，判据见判据档 §6。

审查发现判据档本身有缺口（某类问题判据档任何一条都覆盖不到）时，把「是否改进判据档」作为一项决策交用户拍板——只在报告里附带提及会被略过，同类坑复发。（本仓未收录专审 meta-原则的 `/custom:review-principles`，改后的判据档不再另跑一轮 meta-原则审查。）

### 4. 落地

按用户选择改动四个面：**契约定义 / 写入端 / 消费方 / 跟随物**（跟随物含不被自动化收集的 eval 与手工脚本）。只改契约定义会留下不一致。

改完后按顺序：

1. 回到第 1 步重新接地（新实例 + 再看消费界面）。**写入端的语义校验类修复要单独验**：一个合法实例在"校验接进去了"和"没接进去"两种情况下输出相同，必须另喂一个此前会被接受的坏值，确认它现在被拒。
2. 回到第 2 步完整重跑。
3. 未产生改动则终止：交付里列出用户保留或延期的发现，并按 `~/.claude/references/durable-solution-carriers.md` 给出各自去向。

## 反模式

- **合并 subagent**：不要因 schema 小或原则相关而把多条塞进一个——独立性保证的是跨原则交叉发现不被单个上下文污染。
- **重跑 prompt 不中立**：重跑给 subagent 的 prompt 必须中立重审，只给新实例与新观察结论，**不带上一轮改了什么 / 想达成什么**，也不把"确认 fix 生效"当任务。否则 subagent 从审查者变成修复的辩护者，而它恰好挡不住修复引入的错误判据。
- **把 `deep-discuss-style.md` 下发给 subagent**：该档教 "skip when borderline" 且要求用 `AskUserQuestion`，与 subagent 的契约（报 borderline、禁止提问）正面冲突，会反向抵消并行 fan-out 的目的。borderline 的裁剪在主 session 汇总时做。
