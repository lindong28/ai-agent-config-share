# review-session-progress

只读分析**另一个** session 的进展与健康度，产出一份让用户能决定「要不要介入、怎么介入」的报告。

## 不要在本命令里执行

| 情形 | 去处 |
|---|---|
| 只要效率账与 ETA，不要进展分诊 | `/custom:review-session-efficiency` |
| 分析**当前**对话自身 | **两条命令都不受理**——它们的 frontmatter 都声明 `analysis-target: third-party`，交付物是关于**另一个**执行体的报告，Stop 系判官闸据此把报告里的未完成项默认判给被分析对象。拿它们分析自己会让那条豁免发在错误的对象上。此前这一行写的是「同上（它的证据范围本就是当前对话）」，与 `review-session-efficiency` 的 frontmatter 直接矛盾，2026-08-24 经用户裁决按 frontmatter 为准订正 |
| 用户描述不出 session id，只记得聊过什么 | `/custom:find-claude-session` 定位后回本命令。**它默认只搜当前 cwd 派生的那个 project 目录**，目标跑在 worktree 或别的仓时它会以「没这个 session」的形状失败——那种情形直接用下面的全域定位 |
| 任务已结束、要复盘 harness | `/custom:review-agent-harness` |
| 看不出这些工作在改产品的哪一部分、做完后架构与能力会变成什么样 | `/custom:map-program-architecture` —— 把工作项逐条落到模块、显示改造前后差异的 HTML 地图。比本命令重得多（要读两棵树、逐项回代码取证），不适合每小时跑；本命令看进展，那条看全局 |

## 用户要的答案

用户的原话是：**目标是什么、已经完成了哪些工作、还差哪些工作、目前正在做哪个工作、整体进展是否顺利、是否存在需要我们介入的地方**。六问都要答，缺一项就没回答他的问题。

**你的角色是 leader 的第二双眼睛，不是审计员。** 他看 CLI 最新输出看不出这个 session 完成了什么、在做什么、还差什么，才来问你；他要的是**据以决定动不动手**的判断。

他背后真正的不确定是：**"是 Claude Code 的问题，还是我低估了工作量？"** —— 所以「没问题，就是工作量确实大」是一个**合法且必须可达的结论**。被叫来找问题的 agent 会倾向于找到问题；这里要抵住。

**「符合预期」的定义**（用户给的，不是你临场定的）：**目标在被逐步完成、遇到的问题在收敛、已耗时相对这个任务的难度与工作量是合理的**。三条都成立即符合预期，此时正确的报告是「顺利」，而不是一份它修过什么的缺陷清单。反过来说：**non-trivial 的开发任务在评审或实验里发现问题是常态，不预期任何人或 agent 一次写对，也不预期问题必须在设计或代码评审阶段全部发现**——所以「抓到了 N 个问题」既不是不符合预期的证据，也回答不了顺不顺。能回答的是这些问题的**趋势**。

## 输入契约

`$ARGUMENTS` = session UUID 前缀（可选）+ 关注点（可选）。

- **缺 uuid** → 列出候选让用户用 `AskUserQuestion` 选，不要静默挑一个。**排除当前 session 要按 `$CLAUDE_CODE_SESSION_ID`，不要按 mtime**——并发 session 会让 mtime 指错，而排除失败的产物是一份「分析自己」的报告，六问照样答得出来、没有任何读数会反常（判据与取不到 id 时的处置见 `/custom:review-agent-harness`「编排流」2a）。
- **给了关注点** → 用它约束重点，但六问照答。
- **任何 `--flag` 可出现在任意位置**；命中后从关注点里剥掉再用，否则它会作为关注点去"约束重点"。**剥掉的 token 不认识就在 §7 点名**（本命令只认 `--since-last` 与 `--verify-deliverable`）——剥掉又不报，等于把一个拼错的 flag 变成「用户没打过」，两者产出逐字节相同；拼错 `--since-last` 时脚注会老老实实填 `全量`，读起来毫无异常。
- **给了 `--since-last`** → 只报增量。切点 = 上一份报告 §3 里那个最后活动时间，**原样引用、不另行推导**；那份报告须是本对话里针对**同一 session uuid** 的。各槽在增量模式下按什么范围写，见「输出」表后的「增量模式下各槽的范围」——那里六问逐条有值，别在这里凭印象定。
- **切点取不到 → 回落全量、在 §1 说明**（新 session、已压缩只剩概述、或上一份报告是别的 session 的），不得猜一个窗口。判据是「切点取不到」而不是「没有上一份报告」：压缩常留下"报告写过"这个事实却丢掉那个时间值，那种情形按前者才落得进来。
- **给了 `--verify-deliverable`** → 除六问外，额外走下面「目标交付物验证模式」。
- **只有这个 flag 会让本模式自己跑起来**——它有副作用、有成本，所以要一个显式动作。**这不等于不许理解意图**：从关注点判出用户想验交付物时，别拿关键词表当判据自行开跑（`~/.claude/CLAUDE.md`「模式匹配只用于有 spec 的对象」把自由文本归判官），也别装作没看见——按那条的处置交判官，然后用 `AskUserQuestion` 问一句。
- **台账**（`plans/<program>/` 下的 `program.md` / `journal.md` / `state.md`）的根目录不由用户给，也别猜当前 cwd：取 transcript 里首个含 `cwd` 的条目，并记下 `gitBranch`——台账缺失时用它说明目标跑在哪条分支 / worktree 上。台账不存在是常态，属 optional，缺失时回落 transcript 并在报告里标明（连同分支）。

## 定位 transcript

**不要只找 cwd 派生的那个目录。** session 可能跑在 worktree 里，落在与主 checkout **并列的另一个** project 目录下。目录名的派生规则是观测所得、不是官方契约（同一项目按不同子目录 cwd 启动会派生出不同目录），**别去拼它**，直接全域找：

```
find ~/.claude/projects -maxdepth 2 -name "<prefix>*"
```

**再查一次它是不是 compaction fork**：逐行 JSON 解析、按字段取 `forkedFrom`（**不要 grep 字面量**，正文讨论过这些字段的 transcript 会假阳性），数**去重后的父 `sessionId` 个数**，不是携带该字段的记录数（实测一次 fork 会让 3097 条记录各带同一个父指针）。父档存在**不等于**子档被截断：拿子档的起始 `timestamp` 与条目数去比父档，子档起点更晚或重叠区更少才是真丢，此时两档都要读。实测 `b00dac76` 是 fork 但无损（起点相同、7776 条 > 父档 6140 条），照「fork 即危险」报警会是假警报。`forkedFrom` 多数不挂在 `compact_boundary` 记录上，别只找那一类。

**命中数不为 1 是常态，必须处置**：起过 subagent 的 session 会同时返回 `<uuid>.jsonl` 与同名目录（后者装 `subagents/` 与 `tool-results/`）——只取 `.jsonl`。0 命中就停下如实报告，不要退回猜测；≥2 个 `.jsonl` 命中用 `AskUserQuestion` 让用户选。选错 session 会让整份报告全错，且错得毫无自证。

## 证据与深度

| 阶段 | 触发 | 产出 |
|---|---|---|
| 浅层 | 默认全做 | 台账、用户指令主线、新鲜度、委派普查、产出普查 |
| 深层：逐轮核实 | 见下节「计数只定读多少轮」条款 | 那几轮各抓到了什么 |
| 目标交付物验证 | `--verify-deliverable`（默认不跑） | E1 / E2 / E3，见「目标交付物验证模式」节 |

`--since-last` 不是这张表的新一行，是**加在全部阶段之上的一个作用域轴**。**各阶段与各槽按什么范围取，只有两处权威**：槽的范围见「输出」表后的「增量模式下各槽的范围」，脚注各格的范围见「取证脚注怎么填」的抬头。**这里不复述它们**——同一条规则写第三遍就会漂，而漂掉的那一遍读起来和对的一样。

**证据不足终态（贯穿全部步骤的合法出口）**：任何一步取不到证据时，报出「未核实 + 缺什么 + 查了哪里」，既不回落猜测，也不因此拒绝回答其余各问。**「不适用」和「未核实」都是合格答案，不是没做完**——下面各处的降级写法都是它的实例。

**先量规模再决定读法**——可以到 100 MB+（实测本机最大 205 MB），整读会烧光 context。**行数不是规模量**：实测 9661 行 / 28 MB 与 1836 行 / 205 MB 并存，一行可以是一个 200 KB 的工具输出。用**字节数 + 带 `timestamp` 的条目数 + 时间跨度**。

浅层：

1. **台账优先于 transcript**（项目若有自己的状态入口一并读）—— 它们是 agent 自己维护的当前态，比从 transcript 重建便宜且准。transcript 用来核台账没说的。读数：台账最后更新时间、task 表条目数——**台账停更而 session 仍在跑，本身就是一条信号**（它记的状态已经不是当前态，后面每一问都不能再以它为准）。
2. **用户指令主线**。噪声主要不来自那几个显眼的字符串，而来自 **harness 注入**：抽 `type=user` 时只取 `content` 里 `type == "text"` 的块（自然排除 `tool_result`），并滤掉 `isMeta === true`。**`isMeta` 这一条比任何 marker 清单都有效**——实测某 session 用 `Stop hook feedback` / `<task-notification>` / `<system-reminder>` / `<command-message>` 四个 marker 滤完仍存活 49 条，其中 41 条是 `isMeta` 注入、真人指令只有 8 条。marker 只是例子，不限于此。
   **自己算出「原始 `type=user` 条目数 → 存活条数」并对照**：存活数与会话时长严重不成比例，本身就是提取口径坏掉的信号，而不算这个比就看不出来。比例反常时按 §7 报，正常时只进取证脚注（见「报告写给谁」）。目标 session 若 compact 过，同一条用户指令会重放，按内容去重后再计数。
3. **新鲜度**：最后一条**带 `timestamp` 的**条目的时间，及其距今多久（末行可能是无 timestamp 的 bridge 记录）。这一个读数同时回答「是不是卡住了」，也告诉用户这份报告有多新——分析一个仍在跑的 session，读的是移动靶。
4. **委派普查**。**权威源是 `<session>/subagents/*.meta.json`，不是主 transcript 里的 `Agent` 调用**：嵌套委派（`spawnDepth ≥ 2`）原理上不出现在主 transcript，而它们往往正是评审轮。实测一个 session 主 transcript 数出 3 次、盘上 5 份，漏掉的 2 条全是 `general-purpose-readonly` 的对抗评审——**偏的方向正好让"过度审查"看起来不存在**。两处数目不等时报出差值，别取其一。`agentType` 含 `readonly` 的即只读评审，比从 description 猜准。（具名委派另存为同级 top-level session 文件，不进 `subagents/`；拓扑见 `/custom:review-agent-harness` 「编排流」第 2 步 2a。）

**还有第三条通道，不在上面任何一处**：走后台 Bash 的**外部 agent**（`codeagent-wrapper --backend codex` 一类）——它既不产生 `Agent` tool_use，也不写 `subagents/`。数它要扫 `tool_use` 里 name 为 `Bash` 的 command，**新派与 `resume` 分开计**：`resume` 次数就是评审复核轮数，正是评审量判断的直接输入。**实测一个 session 在前两处都是 0、第三处是 87 新派 + 57 resume**——只报前两处会给出「零委派」，而真相是 144 次。所以三处**都要数**，脚注按 `Agent/盘上/后台` 三个数写；某一处为 0 是读数，不是可以省略的理由。
5. **产出普查**：从 transcript 的 `tool_use`（Edit / Write / NotebookEdit / 写型 Bash）抽出被改动的文件路径，按是否落在台账根目录内分两堆。落在根目录**外**的那堆是下节 BINDING 追溯的输入——没有这一步，那条追溯没有指称对象。

## 报告写给谁：内部读数默认不出场

这个命令做两件事，**它们的读者不同**：

| | 读者 | 归宿 |
|---|---|---|
| **取证纪律** —— 提取口径、fork 检测、委派两处差值、规模量（字节 / 条目数）、逐轮核实的逐条内容、阶段归属的逐条判定、BINDING 追溯的逐条 | 你自己，为了不下错结论 | **不进正文** |
| **判断** —— 完成了什么、在做什么、还差什么、顺不顺、要不要动 | 用户 | 正文 |
| **目标交付物读数** —— E1 与它的可转交读数块 | 用户（它直接改变"要不要动手"） | 正文（§4 + §6） |
| **本次覆盖的窗口** —— 增量切点 | 两边都要：用户要知道这份报告覆盖了哪一段，你要知道各格按什么范围取 | **§1 正文一句** + §8 那一格（全文唯一跨两个归宿的读数） |
| 同上的 E2 / E3 —— 覆盖缺口信号 | 你自己 | 脚注；**命中不一致 / 有塌缩维时升 §4** |

**判据：这个读数会改变用户的决定吗？** 提取口径正常时不改变任何决定；坏掉时改变一切（意味着整份报告不可信）。规模量同理：它决定的是**你怎么读这份 transcript**，不是用户怎么决策。

**但「不进正文」不等于不留痕。** 正常读数落进报告末尾**一行取证脚注**（§8），异常读数升进 §7。两个出口都不给，「跑了全部取证且全部正常」与「一条都没跑」产出的字节就完全相同——而那正是本文件通篇在防的失败形态，不能由它自己犯。**别用「不写」去省掉「不跑」。**

**这份报告是 status 型的面向人输出**，骨架按 `~/.claude/references/cli-output-review-principles.md` 的 **P4「结论在哪、四态可分、异常项可定位」**——结论第一眼可见；过程与诊断详情可以证明结论，但不能代替结论。

## 评审量与介入信号的判定

用户点名的三类是**过度的审核、钻牛角尖、执行超过任务所需的工作**——这是例子不是分类学，不限于此。

**准入闸三条，缺一条就不进这一节**：

| 判据 | 不满足时它该去哪 |
|---|---|
| ① 只能由用户解 | 你自己做得完的，是转嫁不是 choice——不写 |
| ② 这件事**没在他刚看过的那几屏 CLI 输出里明说过** | 他刚读到过的——不写 |
| ③ **等目标 session 自己走到那一步，代价不再为零**：它已停下等这件事、正朝错误方向持续消耗、线上 / 对外有持续损害、或**一个不可逆动作即将发生**（马上要 push、马上起一次昂贵的生成跑） | **会阻塞但还没阻塞的**（未 push 的 commit、待批的下一阶段授权、还没轮到的机器）写进「还差什么」当前置条件，**不进本节** |

用户要的是「**要不要立刻主动介入**」。①②满足而③不满足的事项**看起来最像介入项**，实际是在替他排一个他还不需要排的队。

**③ 有一个反向失效面，必须单独判**：上面「等它自己走到那一步」预设了目标 session **还在往前走**。它**已停止、已结束、或空转不再前进**时这个前提不成立——那些前置条件永远等不到，只剩用户能动手，于是**全部回流本节**。而这恰是本命令的高频触发场景（「跑了很久、看不出在做什么」里有一大块就是它已经停了）。判据用槽 3 的最后活动读数，别凭 transcript 末尾的语气。

**但那个读数自己有一条同形面**：一次长时间的单个工具调用（跑测试、跑生成、等远端）期间 transcript **不产生新条目**，与「真的停了」在最后活动时间上完全一样。判停滞前先看末条目是不是一个**未返回的 `tool_use`**，并对照该 session 平时的工具调用节奏；两者分不开时按「**活性未核实**」处理，不按已停止——误判停滞会让前置条件项一次性全部回流本节，产出一份最大化告警的报告，正是本节刚修好的那个失败的镜像。

**本节可以为空，空是好消息。** 判定为无需介入的事项一律不写——包括「无需介入：X、Y」这种列举，那只是把不合格项换个说法收了进来。整节为空时写一句「无」。

> ⚠️ **代理判据条款**——轮次数、委派次数、工具调用数都是代理判据。
> 「评审 11 轮」这个读数，在"评审在空转"与"评审每轮都抓到真缺陷"两种情况下**完全相同**——它区分不出你正要下的那个结论。
> **能区分的检查只有一个：逐轮读那一轮实际改了什么 / 抓到了什么，判断它是不是真缺陷。** 台账 journal 通常逐轮记了；没记就去 transcript 里找那几轮的往返。
> 源对话里，agent 带着全部规则仍然用轮次数下了"钻牛角尖"的结论，逐轮核完发现**每一轮都抓到了实质缺陷**，其中三条漏了就会带 bug 上线。

**所以在评审量 / 返工量这个判断上，计数只用来定读多少轮，不用来决定读不读。**（诊断证据管道本身的计数不受此限——存活比、委派差值不是在判审得多不多，而是在判提取有没有坏；那些**必须照做**，但按上面「报告写给谁」只进脚注或 §7。） 凡存在评审 / 返工轮就逐轮核实；轮次多而 journal 缺失时，抽读**首轮、末轮、任意一个中间轮**并写明抽样口径。**报告里任何关于评审量 / 返工量的判断——包括判"正常"——都必须有逐轮读数支撑**；没核就写「未核实」，既不写正常也不写过度。

逐轮核完之后，把读数落到**收敛轴**上——要判的不是「抓到了几个问题」，是**这些问题在朝哪个方向走**：

| 逐轮读数 | 诊断 | 建议 |
|---|---|---|
| 每轮抓到的是**新的**实质缺陷，严重度与数量递减，送审稿一轮比一轮干净 | **收敛，符合预期**——这正是 non-trivial 任务的正常形态 | 不介入，报告写「顺利」 |
| 多数轮只有元发现 / 重复同一风险域，且没有产出实际改动 | 确是过度审查 | 给评审轮次设上限 |
| 每轮都抓到真缺陷，但同一条 finding 反复以不同身位出现（换一层再犯同一个） | **发散；且不是审太多，是送审稿自验不足**——2 轮能解决的花了 5 轮 | 杠杆在送审前取一次读数，**不在减少评审**。此时叫它"少审点"会让那些缺陷直接上线 |
| 轮次不足以算趋势（少于 2–3 轮），或读数不构成单调方向 | **趋势未定** | 报出已读到的内容与轮次数，**不下顺 / 不顺的结论**。别让它落回第一行 |

**趋势判得出来时，第一行是默认预期而不是例外。** 判不出来时走第四行——**没有兜底行的表会把所有不匹配的读数吸进第一行**，那是假阴性，与旧版的假阳性一样坏。

**阶段归属**：收敛轴判的是 findings 的走向，它判不出第二件事——这些工作该不该在这个阶段做。两者正交，一个完美收敛的循环照样可以整轮在做下一阶段的事，所以这是与收敛轴并列的第二个必答问题。它**不是**「符合预期」的第四个条件（那三条是用户给的），而是其中第三条「已耗时相对难度与工作量是否合理」的证据之一。

**适用面**：目标 session 跑的是多阶段流程的**前段**（create-plan → execute-plan、spec → plan、设计 → 实现）。判据是**存不存在一个信息更多的下一阶段**——那是**本阶段做与下一阶段做的代价差**的唯一来源。两条无对象路由，任一成立即写「不适用」：**没有下一阶段**（就地写就地评），或**本 session 无评审 / 返工轮**（没有可判的对象）；两条同时成立时报前者，它信息更多。判不准时按适用处理。

判归属要的不只是 findings 本身：「本阶段，值得」与「下一阶段」两行问的是「下一阶段撞上它的**那一刻**已经付出了什么」，所以还要那份**被评审的 plan** 的步骤顺序、以及其中哪些步骤不可逆或含长跑 / 建置。**它不是上面输入契约里的台账**——路径从产出普查的写调用、或 transcript 里对它的读取取得，直接只读打开它；台账缺不缺与这一项无关。走抽样支时按抽样范围回答。取不到时按 §8 写「未核实」；只有部分条目取不到时把那几条排除出分母、在 §7 点名。两种都别拿「归属未定」顶替，那一格是**判过**、三行都不明确命中。

**按行序取首个命中**（前三行不互斥）：

| 代价差 | 阶段归属 |
|---|---|
| 下一阶段无权决定——需用户裁决、改承诺面 / scope | 本阶段，必须 |
| 下一阶段抓得到，但那时代价已不可回收：照字面实施且验证全绿仍失败、不可逆动作已发生、长跑或建置已付出 | 本阶段，值得 |
| 下一阶段一定会撞上它，且撞上时**还没有付出不可回收的成本** | **下一阶段**——在本阶段做它是错位，不是严谨 |
| 三条都不明确命中 | **归属未定**——不因判不准就升到「本阶段，必须」；计数规则见 §8 |

**第三行的判据是代价，不是失败响度。** 同一个路径写错，implementer 五秒内撞上时代价确实近零；落在 `deploy.sh` 或一次五小时的生成跑上，它照样立刻失败，但失败前的建置买不回来——那是第二行。（`/custom:review-plan` 曾在 `bounded TODO` 里据「必然立刻大声失败」立过一个类目又整条撤回——那个下沉档本身还在，撤的是它的第三类。这条反例是撤回的两条独立理由之一，另一条是容器语义：命令名写错是**修正**，不属于「细化或补全」。）

那个流程自己的下沉档（如 `/custom:review-plan` 的 `bounded TODO`）触发了几次，是个便宜的注意力线索，**不是判据**——恒为 0 与「真的每条都属本阶段」取值相同。定归属的始终是上表逐条走一遍。

**这一问答得出「归属正常」，和「顺利」一样是合法结论**，它不是新开一扇找问题的门。判为错位时报的是**哪几条、占多少**，而修法是让那些工作流到下一阶段、**不是减少评审轮次**（那个处方归收敛轴表，由它自己的行判）。这条修法要不要成为介入项，照常过 §5 的三条准入闸**逐条判**——③写不出就只留在 §4。

**「执行超过任务所需」同样要证伪，不能看着像就报。** 与本任务目标无关的产出（典型是跑产品任务期间改 `~/.claude/` 下的 reference / skill）**可能正是 BINDING 义务**——Harness Issue Capture 要求记账、长期解决方案载体要求落进 git-tracked 的最窄共享 scope，都会产生仓外改动。逐条打开那些改动，判断它能否追溯到一条 BINDING 政策或用户当轮的显式要求：**追溯得到就不是超范围，是义务**。两堆的条数进脚注（见上「报告写给谁」）；正文里**只出现追溯不到的那些**并给出改动路径，全部追溯得到时这一项在正文里不占位置。

**效率账 / 成本分类的判定口径**沿用 `~/.claude/commands/custom/review-session-efficiency.md`「审计方法」的成本五类表。ETA 不在本命令范围内（description 已把它路由给那条命令）——不要顺手给剩余时间估计。**只借判据，不借它的输出结构与处置动作**：报告顺序以下面「输出」为准。

## 目标交付物验证模式（`--verify-deliverable` 时才走）

**术语**：本节的**目标交付物** = 被审 session 造出来的那个产品。frontmatter 里的"交付物"指的是**本命令自己产出的报告**，两者不是一回事——那一行 stop-gate 要读，别动它。

**为什么有它**：本命令其余部分的证据面全是 transcript + 台账 + 评审轮，**没有一槽指向被审 session 的产品**。实测代价：连续多次用本命令分析同一个 session，全部没发现它已部署交付物的两个功能缺陷（不看图、不会说话），缺陷由同事实际使用时报出；分诊者甚至引用过被审方「12/12」当质量证据——那 12 次同一张图、均无对白，两个缺陷维度上**方差为零**。

**全部闸通过才调用**。任一不过即不调用，按 §8 填对应态。**闸只管 E1**——E2 读文档与代码、E3 读被审方自己的读数，两者都不碰那个交付物，因此**不受闸约束，无论闸过没过都要做、都要填**：

| 闸 | 不过时 |
|---|---|
| ① **定对象**：它是什么 · 它自称的**消费者通道**在哪 · **它自称吃什么**（schema / 签名 / 请求体字段，**逐维抄下**——E1/E3 的"维"由它定义，别靠直觉枚举） | `未核实(<三项里缺哪一项>)` |
| ② **形态适配**（见下表） | 见下表各行 |
| ③ **安全属性**（见下表，逐条要有肯定依据） | `未核实(<哪一条>)` |
| ④ **候选唯一**：同一交付物出现 ≥2 个入口（staging/prod、新旧端口）时，用 `AskUserQuestion` 让用户选 | 不静默挑一个 |
| ⑤ **线上 / 共享实例，调用前问一句**：判定该实例是线上、共享或第三方可达时，用 `AskUserQuestion` 把已推出的东西摆给用户——对象与通道 · 四属性各自读数 · 预计调用次数与输入取值——预填推荐项让他一键确认。**本地 / 一次性实例不问** | 用户不确认即不调用，`未核实(线上实例未获确认)` |

**为什么 ④⑤ 问用户而不自己判**：前三闸判的是**交付物自身的属性**，从文档与 schema 里推得出来；④⑤ 判的是**该不该现在碰这个实例**，取决于只有用户握有的事实（哪个是生产、同事此刻在不在演示、是否事故窗口）。本文件对更便宜的歧义已经设了闸（缺 uuid、≥2 个 transcript 命中都要问）——那些选错只是报告错、可重跑；这里选错是对第三方系统发起真实且不可撤回的调用。

| 目标交付物形态 | 怎么办 |
|---|---|
| 可调用服务（HTTP 一类） | 已实测形态，照下面走 |
| 可调用 CLI | **实验性，逐实例未核实**；无输入的 CLI 满足不了逐维取值要求，如实说 |
| 库 / 文档 / 数据集 / 模型权重 | **本模式未覆盖**，`n/a(本模式未覆盖：<类型>)` |
| **以上都不匹配** | **形态未定** → fail-closed 不调用，`n/a(本模式未覆盖：<你判定的类型>)`。没有这一行，新形态会被吸进第一行，等于授权去调一个从没评估过安全面的东西 |

| 安全属性 | 肯定依据长什么样 |
|---|---|
| 幂等 | 文档 / schema 明写，或同一请求可重放的证据。**推不出就是判不准** |
| 费用与配额 | 写出单次调用的**费用量级与计量口径**；量级判不出即判不准。（这两条是同一个计量面，一起判） |
| 不改**业务**状态 | 只读端点、或文档明写不产生副作用 |
| 已知副作用面 | 目标侧日志、缓存、惰性初始化**一定会**被你触发——这几项不受上面三条约束，但要在报告里点名 |

四条各自的依据写不出即 fail-closed。**通过侧也要留读数**（见「自检」），否则「四条都查过」与「没想这事直接调了」字节相同。

三项证据，**地位不等，不得聚合成一个绿灯**：

| | 地位 | 内容 |
|---|---|---|
| **E1 消费者通道读数** | **唯一有资格的验收证据（必要非充分）** | 以消费者身份实际调用。**方法归** `~/.claude/references/evidence-sufficiency.md`——消费者是谁、通道的哪一层、是不是同一个可寻址位置、中间有没有代理 / 缓存、多消费者怎么算，在「完成断言的观察通道由交付物的消费者决定」那一条；**逐维取值数怎么写、以及"塌缩的那一维正是交付物主语时必须补样本"**，在「报通过率时」那一条。**两条都要读，本节不复述** |
| **E2 声明 vs 实现边界对账** | **覆盖缺口信号，不是验收证据** | 并置**对外声明**（README / 交付报告 / description / schema）与**实现里的自陈边界**（docstring、常量、显式布尔字段），报不一致。实测原型：代码里 `pixels_available_to_current_writer: False` 与交付报告开篇「你手上有首帧图 + 一句动作描述」同时存在了一整天 |
| **E3 被审方自验样本的维度方差** | **覆盖缺口信号，不是验收证据** | 被审 session **自己的**自验读数，在①抄下的每个维上变化过没有 |

**E1 的样本量按维判，不按总数判**——具体规则在上面那条指针里，别在这里另写一份。事故读数 `5/5（5 种请求 / 3 张图）`在"取两个不同取值"这种跨维口径下是通过的，两个缺陷照样穿过去——所以口径必须逐维。

**跑完要做的那一步，缺了它前面全白做**：把 E1 的**产出**逐条对上目标交付物**对外声明的每一句功能主张**（E2 已经把那份声明收集好了），报**哪一句没有在产出里兑现**。调用次数、状态码、逐维取值数都答不出这一问——那两个动因缺陷只有在这一步才看得见。

**E2/E3 为什么不是证据**：零方差只证明自验没覆盖该维——**无缺陷的系统用单一样本同样零方差**；两份自陈文本也可以一致地错误或过时。它们能指出"这里没被测过"，指不出"这里没问题"。

**E1 的读数也只覆盖它实际跑过的样本与你写出来的条件**。**任何情况下都不要写「目标交付物通过 / 没问题」**——写你跑了什么、看到什么、哪些条件没覆盖。

**判出的功能缺陷照常过 §5 三条准入闸逐条判**，过闸即进 §5、并按 §6 附上可转交读数块。闸③（对外有持续损害）在本模式下通常由「已交付、有人在用」直接成立，写清它此刻为什么成立。

## 只读边界

不 stop / resume 目标 session，不改它的代码、plan、台账或证据，不替它跑评审或测试。给目标 session 的一切动作都经用户之手。

**`--verify-deliverable` 不是这条的例外，它落在这条之外**：它做的是**以消费者身份使用**那个交付物——与"代目标 session 跑它自己的评审或测试套件"是两件事，后者仍然禁止。跑它的单测、validator、自验脚本都属于后者：那是 executor 侧读数，与消费者通道**同形失败**（上面那个 12/12 就是这么来的）。

## 输出

对话内直接输出，**不落盘**。**开头一句判定，主体控在一屏**；细节按需展开，不预先倒给用户。

| # | 槽 | 内容 |
|---|---|---|
| 1 | **一句话判定** | 进展符不符合预期 + 要不要立刻介入。后面每一段都是它的展开 |
| 2 | **已完成 / 还差什么** | 用它自己的 task 表；没有就从 transcript 重建并**标注这是重建值**。开头一句引它自己原文写的**目标**（目标是进展的量尺，不单独占一节）。「还差什么」里逐项写各自的**前置条件**——它在等什么事件，含准入闸③不满足、此刻不需要用户动手的那些；要靠用户才发生的照写，那是信息。够不够格进 §5 由三条准入闸判，不在本栏判 |
| 3 | **此刻在做什么** | 附**最后活动时间（写成 ISO 绝对值）及距今多久**——绝对值不可省：它是下一轮 `--since-last` 的切点来源，只写「距今 3 小时」的话下一轮无从引用。停滞或已结束时，这一条就是本槽的全部答案，且它同时告诉用户这份报告有多新 |
| 4 | **进展是否顺利** | 收敛轴结论 + 阶段归属结论 + 一句**「已耗时 vs 已交付工作单元」**的对照，明说它支持「工作量确实大」还是「存在可纠正的浪费」。举证**最多 1–2 轮**，不罗列缺陷目录。无评审 / 返工轮时写「本 session 无评审 / 返工轮，据 X 判定」，不要编。阶段归属**不适用**时本槽不写它、痕迹落 §8；**未核实**时按上「报告写给谁」升 §7，写清缺什么、查了哪里。顺利就说顺利。**E1 取到读数时它是本槽的必需证据之一**——「顺不顺」不能只由过程读数（评审收敛、阶段归属）作证，那正是漏掉产品缺陷的那条路。**本次启用了本模式、而任一闸未过因而 E1 不存在时，本槽显式写出「产品侧未取到读数 + 卡在哪道闸」**（未启用本模式时本槽不提 E1，痕迹落 §8）。**这一项的 owner 是本分析 session 自己，不适用 frontmatter `analysis-target` 的第三方归属**——本模式是全文唯一会把「我自己没做完的事」写进正文的地方，不点明它，判官会按 marker 把它默认判给被分析对象，不得只用过程读数收尾、也不得拿 E2/E3 顶替（它们顶不了，见该节） |
| 5 | **需要介入的地方** | 只收过了三条准入闸的，按紧急度排，每条写清**③为什么此刻成立**——写不出这一句的，删掉它。**可以为空，为空写「无」** |
| 6 | **指令草稿 / 可转交读数块** | §5 非空**或 E1 取到了读数**时出（绑读数、不绑 flag——闸未过时没有现场读数可贴，绑 flag 会逼出编造）。草稿只覆盖 §5 里的条目，不引入新议题。有 E1 读数时，**单列成可整块粘走的一块**：原样的输入、原样的产出、你判它对不对——**原样贴，不加工、不套 `【】`**。它补的是 harness 仓 `docs/issues/harness-issues.md` 里 `HARNESS-20260823-8a91` 记的那个断点（现场读数取到了却没随指令一起交回目标 session）——本块即它记的候选修法 |
| 7 | **异常项** | **仅当取证纪律有项目异常 / 未核实 / 输入里有没认出来的 token 时才出现**；写清哪一项异常、报告的哪部分因此不可信。正常时整节不写 |
| 8 | **取证脚注** | 末尾**一行**，无条件出现：`增量切点 <值> · 条目数 · N→M · 委派 a/b/c(+r 复核) · fork <去重父数> · 逐轮核 k 轮 · 阶段归属 x/y(未定 z) · 仓外 x/y(已扫 N 次写调用) · 目标交付物验证 <态>`。**每格填法见下节「取证脚注怎么填」**——那一节是这一行的唯一契约，别在这里凭印象填 |

### 增量模式下各槽的范围

`--since-last` 改的是**范围**、不是**问哪几问**：六问照答，一问不减。下表逐槽给值——**一格都不留空，判为「不受窗口影响」也要写出来**，因为散文形态下漏掉一槽和写清一槽读起来一样。

| 槽 | 范围 |
|---|---|
| 1 一句话判定 | 全量结论；**并在此声明本次覆盖的窗口**——§8 那一格是取证读数、不承担把范围讲给用户听的职责，正文里没有第二处说得清「这份报告覆盖了哪一段」 |
| 2 目标 | 不受窗口影响——它在窗口之前，是量尺不是进展 |
| 2 已完成 | 窗口内 |
| 2 还差什么 | **全量**——窗口化的待办读起来像「快做完了」 |
| 3 此刻在做什么 | 不受窗口影响（它问的就是「此刻」） |
| 4 进展是否顺利 | 结论按窗口叙述；**收敛轴与阶段归属的逐轮读数按全量取**——窗口内常不足 2–3 轮，只看窗口会让结论系统性退化成「趋势未定」 |
| 5 需要介入 | **全量**——准入闸③判的是「此刻是否成立」，与窗口无关。上一轮报过而此刻仍成立的**照报并标「续」**；漏掉它正是这份报告最不能出的错 |
| 6 指令草稿 | 随 §5 |
| 7 异常项 | 全量 |
| 8 取证脚注 | 见「取证脚注怎么填」 |

## 取证脚注怎么填

它不是给用户读的判断，是让「跑了且正常」与「没跑」在字节上分得开——所以**每格填值，不填对勾**：`fork ✓` 这类恒真标记在跑过与没跑过时字节相同，等于没写。**判不出分数时整格改为原因读数**；空写 `n/a` 在判过与没判时字节相同。**缺哪一项就写缺哪一项，别留空、别编**。**分母缩小必须标出来**，不标就与全量态字节相同、还会放大错位占比。

**增量模式下只有 `增量切点` 与 `条目数`/`N→M` 按窗口计（后者括号带全量总数），其余各格一律全量。** 别把窗口推广到全部：`fork` 按设计就是全文件读数（它要回答的是「父档要不要一起读」，窗口化会让一个真 fork 报成 `fork 0`），`目标交付物验证` 是此刻取的读数，`委派`/`仓外` 是管道完整性读数——窗口化它们只会让两态分不开，正好与本节的目的相反。

| 格 | 怎么填 |
|---|---|
| `增量切点` | 没给 `--since-last` 填 `全量`；切点取到填 `<ISO 切点>(=条目 #N)`；取不到填 `全量(--since-last 无切点：<实际原因>)`——**原因照实写**，别套用固定串。`(=条目 #N)` 不可省：它把这一格从「我说我记得」变成可复核的读数——编出来的时间戳落不到 transcript 的任何一条上，`#N` 也对不上同行的 `条目数` |
| `条目数` / `N→M` | 规模量；提取口径的原始数 → 存活数。**切点取到时**两者都按窗口内计，另在括号里带全量总数 |
| `委派` | `Agent/盘上/后台(+r 复核)`；某处为 0 是读数，照填 |
| `fork` | 去重父 session 数 |
| `逐轮核` | `k 轮`；抽样支写明「抽样」 |
| `阶段归属` | `错位条数/已判条数(未定 z)`——z 计入 y、不计入 x，否则 `0/8` 在「八条都清楚属本阶段」与「八条都判不出」时字节相同。抽样支写 `x/y(抽样，未定 z)`（轮数由同行 `逐轮核` 承载，**别在这里另造一个数**）。部分条目排除出分母写 `x/y(排除 m，未定 z)` 并在 §7 展开。判不出整格改 `n/a(无下一阶段：<该 session 走的流程>)` / `n/a(无评审轮)` / `未核实(<缺什么>，详见 §7)` |
| `仓外` | `x/y(已扫 N 次写调用)`；空态 `0/0(已扫 N 次写调用)` |

`目标交付物验证` 一格，**按行序取首个命中**：

| 情形 | 填 |
|---|---|
| 没给 flag | `未启用(可加 --verify-deliverable)`。此时「定对象」根本没跑，**别去判形态** |
| 给了 flag，形态未覆盖 | `n/a(本模式未覆盖：<类型>)` |
| 给了 flag，其余闸未过 | `未核实(<卡在哪道闸、缺什么>，详见 §7)`——**缺什么写什么，别硬塞成安全属性** |
| 全部闸通过且已调用 | `E1 n 次 @<消费者通道的可寻址位置> · <维:取值数 · …> · E2 x/y 不一致 · E3 <逐维方差 或 n/a(原因)>` |

末行那几个量：**`@` 后面那个位置是承重的**——没有它，「走了消费者通道」与「跑了目标自己的 validator」字节相同，而那正是本模式要防的第一件事。`<维:取值数>` **逐维写**，跨维总数会让「12 次调用全用同一张图」读起来像样本充足。`E2` 带分母（`0/0` 即自证无对账对象）。`E3` 取不到写 `n/a(被审 session 未公开自验样本)`。

**已知 waive**：本格无独立程序核验，漏填仍无人拦——理由见 harness 仓 `docs/adr/20260823-7c14-review-session-progress-deliverable-verification.md` 的「Waive」。

## 指令草稿 / 可转交读数块

**指令草稿**——一段可直接粘贴给目标 session 的话：

- 需要用户拍板的地方用 **`【】` 标出并填好推荐默认值** —— 用户不同意就改那几个字，其余照发。
- 若本次分析**推翻了用户此前给目标 session 的某个指示**，草稿里必须显式撤回它并给出替代规矩。不撤回的话，目标 session 会继续执行那条已知错误的指示，而它是从用户嘴里出去的、agent 不会自行质疑。
- 涉及路径 / 机制时，写成"让它自己判并报出来"，而不是替它假设一条你没独立核过的路径。

**可转交读数块**（E1 取到读数时）：原样的输入、原样的产出、你判它对不对。**原样贴**——不加工、不套 `【】`、不改写成草稿口吻；它的价值就在于目标 session 能拿它跟自己的读数直接对账。

## 自检

交付前**自己**逐条填读数，填不出即未做。**这张表本身不进正文**——它是取证纪律，归宿见「报告写给谁」：正常读数压成 §8 那一行脚注，异常项升进 §7。

入选判据是**没有这张表就会静默漏掉**——已被「输出」槽强制的项不重复列。

| 检查 | 该填什么 |
|---|---|
| 提取口径没坏 | 原始 N → 存活 M；委派两处数目及差值 |
| fork 已查 | 去重父 session 数；有父档时子档与父档的起点 / 条目数对比 |
| 评审轮的判断有逐轮读数 | 核了哪几轮、各抓到什么 / 「无评审轮」/ 「未核实」三选一 |
| 仓外改动已做 BINDING 追溯 | 两堆各几条；追溯不到的那些的路径（无仓外写入则写「无，已扫 N 次写工具调用」——这半句是空态下唯一能把「扫过、确实没有」与「根本没扫」分开的读数） |
| 草稿与用户旧指示的关系 | 引用那条被推翻的指示 / 「未发现相关旧指示，查了哪一段」/ 「本次未产出草稿」 |
| 目标交付物验证那一格填了 | 四行里的哪一行 + 据什么填的。**没跑也要填**——这一格的存在意义就是让「没跑」可见；空着它等于把本模式恢复成不存在 |
| （给了 `--since-last` 才填）切点是引来的、不是想出来的 | 引自上一份报告 §3 的原值 + 它落在 transcript 第几条（`#N`）+ 那份报告是不是同一个 uuid 的。**编一个像样的时间戳与真引用在读数上同形**，这一行是唯一能把两者分开的地方 |
| （给了 flag 才填）安全属性四条各自的肯定依据 | 幂等据什么、费用与配额据什么、不改业务状态据什么、副作用面点了哪些名。**写不出即 fail-closed**——不写这一行，「四条都查过」与「没想这事直接调了」字节相同 |
| （E1 跑了才填）E1 没被 executor 侧读数顶替 | 走的是消费者通道还是 executor 侧读数（单测 / validator / 目标自验脚本，类的界定见「只读边界」）；**逐维**取值数；哪些条件**没**覆盖 |
| （E1 跑了才填）产出对上宣称了 | 对外声明的每一句功能主张，逐句在产出里兑现了没有、**哪一句没兑现**。只答调用次数与状态码不算做过这一步 |
