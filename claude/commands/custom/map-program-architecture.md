# map-program-architecture

## 流程

输入解析〔候选不唯一→问〕〔两侧 ref→问〕 → 取证 → 找接合面〔必答 2 答「无」则跳过〕 → 范围缺口检查 → 产物〔已有产物→问〕 →【自验 gate】 → 交付〔走 server 时另跑 `remote-web-delivery.md` 的交付前自验与点击回执〕

**取证不足出口**（全程共享）：答不出、找不到、判不准时，显式写「未核实」或「无」，并写出查了哪里。不推断填空，也不把没查完的问题转交给读者。

**自验 gate 判未完成时的出口**：不进入交付，回到输入表补齐对应输入；确属不可得（baseline 不可考等）则降级交付，但产物摘要首行与交付打印必须写明「本次未覆盖介入判断（缺 X）」。这是上一条出口的下游——「未核实」是合法落笔，但落在必答 5/6/7 上就不再是合法交付。

## 读者与目的

读者是这个 program 的 leader——他有工作项清单与进度报告。

目的不止于「理解」，而是让他能判断要不要介入。这决定了选材：**能改变他决定的信息进正文**，不能的降级。

## 输入

**工作项** = 输入里最细的那层可独立验收单元（plan 的 task / 台账条目 / 清单单行），一次 program 内取值统一。下表四项全部必需；`argument-hint` 只给出 program 侧的定位方式，其余三项开工时补齐。

| 必需 | 取法 |
|---|---|
| 工作项清单（哪一份权威、共几条） | `plans/<program>/` 的 task 表优先。只给了 session UUID 前缀时，用 transcript 枚举工作项与它们声称改了什么，再逐项回代码验证；定位不到就停下如实报告，不要按 mtime 猜。用户直接口述时让他指出清单在哪——**没有清单就停下要**，不要自拟一份：逐工作项落位、依赖判断与自验闭合三项全靠它 |
| program 的目标陈述（要达成什么能力、有无可量化指标） | plan 的目标节 / 台账首条 / 用户口述。取不到按取证不足出口，并声明必答 2 的能力侧与范围缺口检查降级为未核实 |
| **两侧 ref**：改造前 baseline 与改造后 checkout | 差集有两个操作数，两个都要锚定：各给 repo 路径 + 具体 ref（branch / commit / worktree），脏工作树须声明未提交改动计入哪一侧。baseline 是**用户侧持有的事实**（哪一刻算 program 开始只有他说得准）——枚举候选（program 起始 commit / plan 目录首个 commit / 用户指定 tag）用 `AskUserQuestion` 确认。**任一侧取错时产物长得完全正常**：差集照样非空、抽查照样落得到源文件，只是全部归错侧 |

program 的 `plans/` 未必与被改造系统同仓。解析出的候选 program 不唯一时（UUID 与口述两支默认属此），把候选连同各自的 `plans/` 路径与工作项数用 `AskUserQuestion` 摆出来确认再开工——选错的重做成本是整份地图，且产物会落进另一个 program 的目录。

`[关注点]` 可选：给了就用它约束详略与取材重点，必答照答、一条不减。

## 必答

读者拿到产物后必须能答出下面每一条。三种落笔，语义不同、不得互相顶替：填值 / 「无」（确实不存在，附依据与查了哪里）/ 「未核实」（存在但本次没查到，附查了哪里）。

| # | 必答 | 不合格的形态 |
|---|---|---|
| 1 | 这些工作全部完成后，目标系统的架构长什么样 | 只有模块名清单，没有它们怎么连起来 |
| 2 | 哪些模块负责 program 要达成的那个能力，哪些负责支撑体系（测试、评测、工具链）；不涉及支撑体系时写「无」 | 按目录结构分组，而不是按职责 |
| 3 | 模块之间靠什么绑定——调用关系、数据契约、版本或身份约束、门禁（API / interface 只是其中几种，见 `## 找接合面`） | 只画箭头不标传什么 |
| 4 | 哪些模块是 program 之前就有的，哪些是本次引入的 | 凭叙述断言，没有两棵树的读数 |
| 5 | 每个工作项对应哪个模块——落不到必答 2 那张模块清单上的即**孤儿项**，单独列出；**反过来也要标**：必答 2 清单里没有任何工作项落在其上、而 program 目标需要它变化的模块，与孤儿项同为介入信号 | 用「属于评测体系」这种粗到任何工作项都落得下的粒度；或只做单向 |
| 6 | 架构与能力在 program 前后的区别 | 只列文件增删，答不出「原来做不到什么、现在做得到什么」 |
| 7 | 工作项之间的依赖与先后：哪些必须先落地、当前计划的顺序与之冲突的列出来；无冲突写「无」 | 按清单顺序复述，没有判断过依赖 |

架构位置 = 必答 2 枚举出的那张模块清单里的某一项。

## 取证

**已落地的部分**以代码、配置与契约文件为准，agent 的叙述（transcript、进度报告、台账正文）只作索引；**计划中的部分**只有计划文本可依据——写明依据的是哪一份计划的哪一条，并靠状态标记与已落地的部分区分开。

这不是保守起见：实测中信息量最高的几处发现全部来自绕过叙述直接读代码与契约文件，而叙述里没有它们。

新旧边界靠两棵树对比得出，不靠「新增了 X 个模块」这类说法。列两侧 ref 的同一位置，差集就是答案——实测一次，叙述说不清的边界，`ls` 两棵树的同一目录当场给出数量级差异。

## 找接合面

**必答 2 答「无支撑体系」时本节整体不适用**，写「不适用（依据：必答 2）」即可——没有支撑体系时"两者之间应当有绑定"这句话没有指称对象。

答出了支撑体系时：它与目标系统之间通常有一条把两者绑定起来的接合面——版本闸、schema pin、身份锚、CI 门禁。找到它，产物的信息密度会跳一个台阶：它同时回答必答 2、3、5，并且能验证范围划得对不对。实测一例：评测体系用全文件摘要钉住了一批生产文件，而那批文件正好就是改造任务要动的那几处——这条对应关系不在任何叙述里，是读契约文件读出来的。

确实找不到接合面时写明「无」，那同样是结论：两者松耦合，改动不会被自动拦截。「无」比「未核实」承重，证据义务只多不少——列出查过的位置（CI 配置、manifest、pin 文件、schema 目录各写路径或 glob）与各自的读数，并说明这次搜索为什么足以区分「不存在」与「没找到」。

## 范围缺口检查

program 的目标里若有可量化的差距，逐个问：弥合它所需的改动，落在本次改造范围内吗？

判据要能在两种成因下给出**相反读数**（`~/.claude/references/evidence-sufficiency.md`）。选不出这样的判据就按取证不足出口写明未核实，不要把「可能是 A、也可能是 B」交出去——那是一个看起来负责任、实则要读者自己去查的问号。

实测一次：面对「参照系统比我们多 N 倍」，第一版就写成「可能是源覆盖不足、也可能是筛选过严，这条可以查」交了出去；补查时改用一个在 A / B 下读数相反的直接量，一次定死是 B，推翻了作者自己原本的担忧。

## 产物

单文件 HTML，自包含。落点默认 `plans/<program>/`；无此结构时落目标项目 `docs/`。该路径已有本 command 的产物时先 `AskUserQuestion`：整份重生成 / 保留人工标注做增量 / 另落新路径——不静默覆盖，上一轮由人工判断得出的标注与孤儿项说明重生成即丢失。

**沿用**：页面与写作两面取 `/custom:create-delivery-report` 的「页面」「写作」两节，本文件不另发明取值。两处例外——该命令「写作」节的四值状态那一条由下面的状态标记替代；被继承的 `reading-instance.md` 排除判据是 scan-vs-read，本产物的**正文**（必答的文字答案）是 read、适用，而**模块关系图块**读者是扫不是读，按该档的不可压缩子元素例外全宽处理、不进正文列。

**本命令新增 · 状态标记**：用两个正交标记，不要挤进一张单列清单——**引入方**（已有 / 本次）× **进度**（已落地 / 未落地）。读者的范围判断看第一个、进度判断看第二个；挤在一起时「本次引入但还没写」这类格子会塌，而那正是最需要与已落地的引入分开的一格。两个标记各自的取值都要在图上写得出记号，不能只靠颜色区分。未落地项的架构位置是计划不是事实，行文的确定性要跟着降。

## 自验

按行导入 `/custom:create-delivery-report` 的「交付前自验」节，除下列四项外全部照跑：

| 排除项 | 为什么本产物无对应物 |
|---|---|
| Quickstart 逐步实跑 | 本产物无 Quickstart |
| 清单覆盖四类 | 本产物无交付物清单。别与状态标记混为一谈，那是两回事 |
| 无裸路径 | 作为**入口**出现的路径仍须可点；作为**证据坐标**出现的 `文件:行号` 与 glob 不计入——glob 指不到单个 blob |
| 每条边界有来源（仅判断的那一半） | 本产物无边界节，故「三个来源各自产出」无对象；可注入的那一半照跑，判定对象改为「无」与「未核实」条目 |

该节末尾按行名分「可注入 / 判断类」的尾块，其**分类**只覆盖导入行，但它「每一行都要有失败证据」的总则对下表同样生效。走 server 交付时，`remote-web-delivery.md` 自带的「交付前自验」与「点击回执」一并生效，那是另一份。

| 检查 | 判据 |
|---|---|
| 七条必答逐条答得**合格** | 逐条摘录产物里的答案原文，并说明它为什么不是必答表第三列所写的那种不合格形态。写出 A/7 合格、B/7 写「无」、M/7 未核实，`A + B + M = 7`。必答 5、6、7 记为未核实时判未完成，走流程节的那个出口 |
| 工作项清单闭合 | 写出三个数：工作项总数（附清单出处）、已落位、孤儿项。三者不闭合判 fail——写地图之前就漏掉的工作项不在任何一个桶里，只有这个等式抓得到 |
| 取证来源零容忍 | 每条「无」与「未核实」都带「查了哪里」，无来源的条数应为 0。删掉其中一条的来源，看这一行变不变红 |
| 两侧 ref 都经确认 | 写出各自的 repo + ref 与确认形式（baseline 侧须是 `AskUserQuestion` 的选项与用户选的那一项）。自行取值或未确认判 fail——**这条失败对其余每一行都不可见**，差集照样非空、抽查照样落得到源文件 |
| 关键断言可回溯到代码 | 每条抽样写三段：产物里的断言原文 → 文件:行号 → 从那一行读到的原文。新旧边界与接合面各占一条，它们最容易从叙述里抄来而不自知 |

## 交付

按 `/custom:create-delivery-report` 的「交付路径」选，并实际验证一次。交付后打印：

```
产物:      /abs/path/<stem>.html
链接:      <http 链接或已用的交付方式>
必答落位:  1→§x 2→§x … 7→§x
「无」结论: <逐条，附依据与查了哪里>
未核实项:  <逐条，附查了哪里>
两侧 ref:  before=<repo@ref，确认形式> after=<repo@ref>
```

## 反模式

只列前文规则推不出来的失效形态：

- **照抄 agent 的叙述结构**——进度报告按时间组织，架构地图按结构组织。前者每一段单独看都成立，所以这条错误不会在检查中自己暴露。
