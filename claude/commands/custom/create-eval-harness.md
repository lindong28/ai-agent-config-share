# create-eval-harness

为一个 **prompt 驱动的语义判断组件**建（或扩展）一套带标签 eval，并用它把组件的 prompt 迭代到达标。

这类组件（stop-gate 的 LLM 判官、内容分类器、路由 prompt、抽取 prompt…）的行为由一段语义 prompt 决定——**读代码验证不了**，只能靠"喂真实输入、看真实判定"的 eval 钉住。

## 何时使用

何时触发与不适用范围见 description；其中"不适用纯生成类"的判据是：无 per-case 客观或用户可定的期望判定。

## 输入

| 带来什么 | 为什么必需 |
|---|---|
| 目标组件 + 它的**真实调用 / 判定接口**（怎么喂输入；判定从哪读 **+ 怎么解读**：值→判定映射，如 exit 0=ok·2=flag / 返回值 / HTTP 码 / 分支名；或抽取场景：抽出结构从哪读 + 与 gold 的比对规则） | eval 必须打真实 artifact（见不变量），得知道怎么调它、怎么读+解它的判定 |
| 触发这次的**误判观察**（哪个输入被判错、应该判成什么） | 它是首条场景 + 其反向场景（见下方双向守卫）的种子；"应该判成什么"是用户拥有的行为契约 |

缺真实调用接口 → 先和用户确认怎么端到端调该组件，**别拿离线抄的 prompt 凑**（会漂移，见不变量）。

## 方法（lens，不是步骤）

**eval 的标签 = 组件的行为契约**。每条场景标一个 `期望判定`（该 ok 还是该 flag / 走哪个分支），这个期望来自**用户对该组件期望行为的立场**。标签有歧义时先用 `AskUserQuestion` 和用户确认，别自己替他定。

把方法钉死的几条不变量：

| 不变量 | 为什么（都是踩出来的，非显然） |
|---|---|
| **双向守卫**：每个可能判定都要两侧场景——该出它的（should-fire）和不该出它的（should-not-fire，即某条种子场景的**反向场景**）都要有；二元组件下即 must-fire（漏报守卫）+ must-pass（误报守卫） | 只测一边会"修了一侧却放过另一侧"——stop-gate 第一版只调松判定门槛，离线看着好，真实组件上把真该 fire 的漏报 2/3，是反向场景才抓到 |
| **打真实 artifact**：runner 喂**真实组件**、读它的**真实判定接口**，绝不另抄一份 prompt 离线跑 | 离线抄的 prompt 会与部署的漂移——离线全绿、真实漏报。只有测部署态才算数 |
| **离散判定 + 通过率**：判定是离散的（ok/flag、exit 0/2、分支名、抽取结果是否匹配期望），不是数值分；LLM 判官有随机性 → 每场景跑 N 次看**通过率 + 阈值**，不看单次 | 单次采样不可靠；通过率才反映这个随机判官的稳定性 |
| **fail-open 守卫**：判定依赖缺失（LLM key / 配置 / 上游服务未就绪），或单次调用 fail-open（超时 / 解析失败 / 异常）——该次结果不可信，runner 必须识别并排除或报错，绝不当作真实判定计入通过率 | 非判定不能算判定：依赖缺失时 eval 假性全绿；单次 fail-open 静默回落、被错当成真实 ok，让 ok 场景通过率虚高（stop-gate 判官超时即 exit 0、被 runner 读成 ok） |

## eval 套件落点与形态

与目标组件**就近**：`<组件目录>/eval/<组件名>/`。含三件：
- `scenarios/` — **数据，独立文件可扩展**（加一条 = 丢一个文件，不改 runner）；每条带 `期望判定` + 一句"为什么守这条"；反向场景也要有。
- runner — 喂真实组件、读真实判定、每场景跑 N 次、出通过率 + 阈值、达标退 0 否则非 0。
- `README` — 怎么跑（含依赖要求）、怎么加场景（强调反向场景）、指回本命令讲方法。

**worked example**（形态参考，本仓不收录判官闸的场景集，见仓内 `docs/scope-policy.md`）：判官 hook 的 eval —— runner = node 打 hook 读 exit code；场景 = `# expect:` / `# note:` 头 + transcript。**形态随目标组件而变**——python 分类器 → python + 返回值；HTTP 服务 → 请求 + 响应码；抽取 prompt → 比对抽出结构与 gold。别硬套 stop-gate 的 node/exit-code 形态。

## 迭代

改组件的 prompt → 重跑套件 → 通过率达标即停。**改 prompt 不靠直觉，靠套件红→绿**。新发现的误判 → 加成新场景（连同它的反向场景）→ 持续扩展套件。

**N 与阈值**：起步 N≥5、通过率阈值 0.8（worked example 用值）；达标线本质是用户对这个随机判官的风险容忍度，拿不准先用 `AskUserQuestion` 和用户确认、别自定。

## 输出
- 该组件的 eval 套件（上面落点）；
- 迭代到达标的组件 prompt（直接改在组件源文件里）；
- 末尾跑一遍 runner，贴通过率结果。
